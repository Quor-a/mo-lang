# pkgv2 —— 包管理器的升级 / 依赖 / 完整性校验

`examples/pkgv2.mo`（v1.156）—— 一个**在安卓原生（ARM64）上可执行**的包管理器，
在 v1.155 的 `pkgmgr.mo`（装 / 列 / 查 / 执行 / 卸）之上，补上了一个包管理器
真正该有的三件事：

| 能力 | 实现 | 失败时 |
|---|---|---|
| 版本比较与升级 | `vcmp()` 按 `.` 分段比数字 | 降级返回 **-1**，不静默覆盖 |
| 依赖解析 | DFS 后序拓扑排序 | 环返回 **-2** 并置 `CY`；依赖缺失返回 **-2** |
| 完整性校验 | FNV-1a 32 位逐字节 | 篡改后 `verify` 返回 **0**，不是"仍然通过" |

```bash
bash tools/android_native.sh examples/pkgv2.mo /tmp/pkgv2
adb push /tmp/pkgv2 /data/local/tmp/pkgv2
adb shell /data/local/tmp/pkgv2
```

产物是**静态 ELF、不链 libc、不需要 fork/exec/git** —— 手机里没有的东西，一个都不用。

## 一、概念来源

| 机制 | 出处 | 主流语言的支持情况 |
|---|---|---|
| 语义化版本比较 | Semantic Versioning 2.0（Preston-Werner 2013） | 几乎全是第三方（npm/cargo 是包管理器自带，不在语言里） |
| 依赖拓扑排序 | Kahn 1962 / DFS 后序 | 同上 |
| FNV-1a 哈希 | Fowler–Noll–Vo 1991 | C++ 有 `std::hash` 但实现未规定；其余靠库 |

三个都是"每个包管理器都要写一遍、但没人把它放进语言"的东西。这里全部手写，
好处只有一个：**失败形态可控** —— 降级、环、篡改都必须响，不能悄悄过。

## 二、判据为什么这样写

判据的关键不是"能不能跑通"，而是**能区分"真做了"和"碰巧"**。

**升级后 run 的返回值必须从 42 变成 45。** 包的 CODE 从 `6*7` 换成 `5*9`。
只改版本号而 CODE 没换的话，run 仍旧输出 42 —— 那样根本测不出"真的升级了"。

**降级被拒后，版本仍是 2.0.0、run 仍是 45。** 若降级被静默接受，run 会变回 42。
这一条和上面那条合起来，才把"版本比较生效了"钉死。

**拓扑序按整行比对，必须是 `libC libB app`。** 这是**后序**：依赖排在前面。
若实现成"按声明顺序"或"前序"，会得到 app 在最前 —— 装的时候它的依赖还没装。
只查"顺序里包含 app"分不出这两种。

**篡改后 verify 必须是 0。** 篡改方式是**重写 CODE 但不动清单**。
前后字节码长度都是 13 字节，所以一个"只看长度"的假校验会照样通过 ——
M3 变异就是专门验这一点的。

**环检测返回 -2，且 `CY == 1`。** 若只是"遇到访问中的节点就跳过"，
`resolve` 会返回一个**缺项的顺序表**和退出码 0，看上去装成功了。
所以 `CY` 这个标志是独立的第二条判据。

## 三、实测（`make pkgv2test`，40 项）

ARM64（Unicorn 模拟 + 自制 syscall 表）与 x86-64（真机、真文件系统）**各跑 20 项**：

```
[1] install libC  ret=0        [4] run 1.0.0     out=42
[1] install libB  ret=1        [4] upgrade ret   =0
[1] install app   ret=2        [4] ver after     =2.0.0
[2] topo n        =3           [4] run 2.0.0     out=45
[2] topo order    =libC libB app
[3] verify app    =1           [5] downgrade ret =-1
                               [5] ver after     =2.0.0
[6] tamper verify =0           [5] run after     out=45
[7] cycle ret     =-2
[7] cycle flag    =1
[8] missing ret   =-2
pkg ok = 1
```

两端都跑，是因为这类缺陷**只在一端暴露**：v1.155 修掉的 getdents64 就是
x86 上恰好正确（217）、ARM64 上发成了 add_key。只跑一端等于没验证号表翻译。

## 四、🔴 两个坑

### 一、同一个包被注册了两次，`install` 的返回值错位

第一版在 `main` 里先 `reg()` 三个包、再 `install()`，而 `install` 内部
**也会** `reg()` —— 于是每个包进表两次，`install` 返回 3/4/5 而不是 0/1/2。

不报错、不崩溃，装包、列目录、执行**全部正常**。只有"装到第几个"这个判据
失去了意义 —— 而它恰好是后面拓扑序断言的基准（`ORD[0]` 是不是 libC）。

修法是让注册只由 `install` 完成。教训记在源码注释里：**同一个动作在两个地方
各做一次，症状不会指向重复本身。**

### 二、C 生成器不支持返回 `ptr` 的函数

```mo
fn pkb(i: i64) -> ptr { return &PKB + i * 16; }
```

生成 `struct ptr_t pkb(...)`，报 `incomplete result type`。改成在调用处
直接写 `&PKB + i * 16` 就好了 —— 传地址可以，返回地址不行。

## 五、变异验证（`make pkgv2mut`，6 / 6 被捕获）

| 变异 | 改回的缺陷状态 | 变红 |
|---|---|---|
| M1 降级保护失效 | 2.0.0 → 1.5.0 被静默接受 | 9 项 |
| M2 upgrade 不重写 CODE | 版本号变了、跑出来仍是 42 | 9 项 |
| M3 校验和只看长度 | 篡改前后长度相同 → 验不出 | 5 项 |
| M4 环检测失效 | 循环依赖被接受，顺序表还少一项 | 7 项 |
| M5 顺序表倒着填 | 拓扑序变 `app libB libC` | 5 项 |
| M6 依赖缺失静默跳过 | 装一个依赖不存在的包，返回成功 | 5 项 |

## 六、已知限制

- **包注册表上限 8 个包**，包名 16 字节、依赖串 32 字节；超了 `reg` 返回 -1
  （不静默截断）。
- **依赖只在内存里解析**，没有跨会话的锁文件；进程退出后注册表就丢了，
  下次启动靠读磁盘上的 MANIFEST 重建（本版没做，`install` 才写表）。
- **`upgrade` 不做回滚**：写 CODE 成功、写清单失败时，包处于中间状态。
- **校验和只覆盖 CODE**，不覆盖 MANIFEST 自身。
- **依赖版本不做约束**：`deps` 只有包名，没有 `>=1.2` 这类区间，
  因此也不会出现版本冲突检测。
- VM 只有 5 条指令（HALT / PUSHI / ADD / PRINT / MUL），够演示，不够当真运行时。

## 七、打包分发：包本身就是一串可打印字节（v1.158）

前三节假设"包已经在本地文件系统上"。安卓上没有 git、没有仓库，
包怎么到达？`pack` / `unpack` 把它变成一串字节：

```
MOPK1|<name>|<version>|<deps>|<len:8位hex>|<code:hex>|<ck:8位hex>
```

能走剪贴板、二维码、串口、HTTP body —— 任何渠道。

**长度字段不能省**：只靠 `\0` 判结尾的话，传输被截断是看不出来的，
半个包会被当成完整包装上，run 出错误结果却不报错。所以 len 段必须
与实际 hex 长度逐字符核对。

**判据里最关键的一条**：先把磁盘上的 CODE 删掉再解包。删掉后 run 必须
是 -1，解包后必须回到 42 —— 否则"解包成功"可能只是改了内存注册表。

两个"改了却没改到因果链"的坑（都表现为测试仍然通过）：

1. **数漏一个空段**：deps 为空时 `1.0.0||0000000d` 里两个 `|` 之间仍占
   一个段。按 `len=段3、hex=段4` 写，实际是 `段4/段5`。三个负例**全部
   碰巧通过**，因为改错了位置、坏掉的是别的字段，碰巧触发了预期错误码。
2. **两条 `if` 互相抵消**：把 `else` 拆成两条 `if`，第二条把第一条刚改的
   值又改了回去 —— 什么都没改，unpack 照样成功。必须先读出原值再分支。

## 八、下一步
