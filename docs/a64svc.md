# a64svc —— 自举 aarch64 的**特权级分离**

`examples/a64ld.mo` 之前只能产出"整段代码一个权限"的镜像：谁都能碰硬件、
谁都能改异常向量表。那不叫系统。

`tools/a64svc/main.s` 把它分成两层：

```
EL1  内核：拥有硬件（UART）、异常向量表、自己的栈
EL0  用户：只能通过 svc 请求服务，碰不到硬件，改不了系统寄存器
```

下面**没有 Linux、没有 libc、没有安卓**：只有一块 CPU、一个 UART、一张
异常向量表。每条指令的机器码都由墨语言写的汇编器 `examples/a64as.mo` 算出，
链接由 `examples/a64ld.mo` 完成。

```bash
make a64svctest    # 31 项断言
make a64svcmut     # 6 个变异，6/6 被捕获
```

裸机里跑出来是这样（`kern64run.py --exc 1`，模拟器实现的是**硬件**）：

```
MO-SVC        ← 用户经 write 系统调用打印
W OK          ← 合法指针：write 成功
P OK          ← 越界指针被内核拒绝（-EFAULT）
TRAP VBAR OK  ← EL0 写 vbar_el1 被陷入，且 VBAR 仍是原值
T OK
TRAP VBAR OK  ← EL0 写 tpidr_el1
M OK
TRAP VBAR OK  ← EL0 读 esr_el1
R OK
U OK          ← EL0 直写 UART 无效（那个 'X' 没打出来）
EXIT
```

诊断行：`svc=9 trap=3 eret=12 uviol=1 usp=0x... ksp=0x...`

---

## 为什么这些数字有意义

诊断计数不是照抄实现，而是**从源码结构独立数出来**的：

| 计数 | 期望 | 怎么数出来的 |
|---|---|---|
| svc | 9 | 7 次 uputs + 1 次越界 write + 1 次 exit |
| trap | 3 | vbar_el1 / tpidr_el1 / esr_el1 三条特权指令 |
| eret | 12 | 9 + 3，每次陷入各返回一次 |
| uviol | 1 | 用户那次直写 UART |
| usp − ksp | 4096 | `.bss` 里两个栈各 `.zero 4096` |

## 六个判据层，各抓一类缺陷

| 层 | 抓的是 |
|---|---|
| ① 汇编 + 链接产出（含 `msr sp_el1` 被识别） | 新助记符没被识别、静默跳过 |
| ② 产物里 svc/eret/msr/mrs/strb 的**编码**真的出现 | 助记符落到别的分支 |
| ③ 向量表 2KB 对齐 | 对齐没生效，入口错位后跑飞却不报错 |
| ④ 端到端逐行输出 | 指令合法但语义错 |
| ⑤ 诊断计数 | 走的是别的路径、碰巧也对 |
| ⑥ **关掉 `--exc` 必须没有输出** | 这些性质其实是程序自己碰巧做到的 |

第 ⑥ 层是反向判据。实测 `--exc 0` 时一条输出都没有 —— 所有输出都依赖
模拟器按 ARM ARM 补的异常模型，而不是"程序碰巧能跑"。

## 本轮挖出的东西

### ① `msr sp_el1` 汇编器不认识，模拟器也不实现

内核想指定**自己的**栈只能用 `mov sp, x0`。加上助记符 + 模拟器支持后，
`msr sp_el1, x0` 才真正生效，于是"内核栈在哪"第一次成为可断言的事实
（`ksp` 与 `usp` 相距 4096）。

### ② 我自己又犯了一次"加法 vs 按位或"

`MSR 底字 = 0xD5100000 | (sysreg << 5)`。我按**加法**算出
`msr sp_el1 == 0xD5284120`，于是断言"`w >> 20` 会溢出到 0xD52，
`is_priv_sys` 漏了一整个分支"，还写了一段很自信的注释准备"修"它。

实际反汇编出来是 `0xD5184120` —— `0xD5100000` 的 bit20 **本来就是 1**，
按位或上去不会进位，`w >> 20` 恒为 `0xD51`(MSR) / `0xD53`(MRS)，
原实现是对的。

`kern64run.py` 顶部关于 `SPSR_MSR_BASE` 的注释里**早就记过这个错**，
我还是犯了一次。**差点把一个正确实现改坏，并附上一份错误的理由** ——
这比漏掉一个缺陷更值得记，因为它会污染后来读这段代码的人。

### ③ 用户能绕过内核直接打硬件

模拟器原本不区分访问 UART 的是 EL0 还是 EL1，于是用户只要 `strb` 到
`0x09000000` 就能说话 —— `svc` 形同虚设。

真硬件靠 MMU 权限产生 data abort；这里简化成丢弃 + `uviol` 计数。
简化不等于没验：自检六故意让用户写一个 `'X'`，若隔离失效输出里就会
多出 `XU OK`。

### ④ `is_priv_sys` 的覆盖只有一条指令

原来的自检只试 `msr vbar_el1`。补上 `msr tpidr_el1`（MSR 的另一半用法）
和 `mrs esr_el1`（MRS —— 原来自检**根本没覆盖读**）。

MRS 的哨兵必须放在**目标寄存器**上：第一版我把 0x1234 放 x9、
`mrs x10, esr_el1`，mrs 真执行了也看不出来。

## 变异验证 6/6

| | 改坏什么 | 红 |
|---|---|---|
| M1 | svc 的返回地址用上一条指令 | 15 |
| M2 | eret 不恢复 PSTATE | 13 |
| M3 | 陷入时不切内核栈 | **1** |
| M4 | EL0 特权指令不陷入 | 12 |
| M5 | EL0 直写 UART 不拦 | 4 |
| M6 | 汇编器把 svc 的机器码算错 | 4 |

**M3 只红 1 项**，冗余度薄：唯一的盯梢就是 `usp − ksp == 4096` 这一条。
改 `take_sync` 之前应先补断言（例如让内核在栈底放哨兵并校验它没被动过）。

## 已知限制

- **没有 MMU**：EL0/EL1 的隔离靠模拟器的约定，不是页表。EL0 仍能读写
  内核的**内存**（只有 UART 被拦）。
- **EL0 违规 → 丢弃而非 data abort**：真硬件会陷入并给出 `EC=0x24`，
  这里只记数。
- `spsr_el1` 用影子值（Unicorn 没这个寄存器），`eret` 按它恢复 PSTATE。
- 只实现了同步异常（svc / 被陷入的系统指令）；IRQ、数据中止未接。
- 单核、无抢占、无进程概念，只有一个用户线程。
- 只在 CPU 模拟器里跑过，**未经真实硬件**。
