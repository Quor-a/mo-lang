# a64irq —— 自举 aarch64 的 **抢占式多任务** + **指令中止**

## 为什么必须有这一层

`a64mmu`（v1.173）把 EL0/EL1 的隔离交给了页表，但它自己的已知限制第一条写着：

> **只实现了数据中止，指令中止（EC=0x20）没做** —— 用户跳进内核代码会直接让
> 模拟器报取指错误而不是陷入内核。

而且那一版里任务是**协作式**的：`svc exit` 之后才切下一个。所谓"多任务"只是
顺序调度，没有"被抢走 CPU"这回事。这一层补上两件事：

1. **取指中止**（EC=0x20），并且和取数中止（EC=0x24）**分开报**；
2. **定时器 IRQ 抢占**：任务不主动让出也能被切走。

```bash
make a64irqtest    # 41 项断言（八层判据）
make a64irqmut     # 6 个变异，6/6 被捕获
```

## 实测：抢占开着 vs 关掉

同一份镜像，只差 `--tick`（0 = 关定时器）：

```
--tick 512                    --tick 0
  MO-IRQ                        MO-IRQ
  A0 B0 C0                      A0 A1 A2 A3 A4
  A1 B1 C1                      B0 B1 B2 B3
  A2 B2 IP                      IT C0 C1 IP
  B3 A3 A4 IT                   ALLDONE
  ALLDONE                       V OK
  V OK
irq=18  svc=12  eret=32      irq=0   svc=12  eret=14
```

左边是**轮转**（A 的相邻两次迭代之间只隔两个任务），右边是**跑完再换**。
差别只由定时器引起，代码一行没动。

## 判据分八层，缺一层就漏掉不同类别的缺陷

| 层 | 判据 | 抓的是 |
|---|---|---|
| ① | 汇编 + 链接产出 | 根本没产出 / 新助记符没被识别 |
| ② | `ldr w0,[x1]` 必须是 `0xB9400020`（size=10） | 编成 64 位（本轮真缺陷） |
| ③ | `mov x0, sp` 编成 `add`(0x910003E0) 而非 `orr` | 栈顶变 0（本轮真缺陷） |
| ④ | capstone 第三方反汇编核对 | 编码自洽但不符合规范 |
| ⑤ | 端到端逐行输出 + 交织关系 | 编码合法但语义错 |
| ⑥ | 两类中止各恰好一次 | 拦了但分不清是哪种错 |
| ⑦ | **反向**：`--tick 0` 必须毫无交织 | 所谓抢占其实是 exit 后的顺序调度 |
| ⑧ | 内核栈必须是内核自己登记的那个 | 抢占用了用户栈 |

## 五个真缺陷，都不报错

**一、函数里再调函数，忘了先保存返回地址。** 结果程序原地打转，只打出第一行
`MO-IRQ` 就再也不动。`bl` 会覆盖 `x30`，而外层还没用它。

**二、公共小工具函数顺手用了调用者还没用完的寄存器。** 任务入口地址被改成别的
数字，系统一启动就跳到错误的地方。

**三、读 GIC 用了 64 位。** GIC 的寄存器都是 32 位的，`ldr x10` 会顺带把**下一个**
寄存器（正好是 EOIR）读进来。第一次 EOIR 还是 0 所以看不出来，第二次就变成
`0x1E0000001E` —— **第一次对、第二次错**，最难归因的那种。

**四、抢占时没保存/恢复标志位（PSTATE）。** 被中断的那个判断偶发走错，症状是
计数序列跳号。

**五、`mov x0, sp` 编成了 `orr x0, xzr, xzr`（读零寄存器）。** 栈顶读到 0，第一次
写内存就飞到地址最顶端。判据③专门盯它。

## 🔴 我自己犯的错：把判据改"简洁"了，结果它失效了

原本"栈有没有混用"的判据是**比对内存里的标记**。我改成比对**当前栈顶**——
看起来更直接，实际让判据失效了：因为期望值也是从栈顶算出来的，**栈顶错了期望值
跟着错，两者照样相等**，缺陷永远测不出来。

改回用**固定常量**做期望值之后，相关的两条变异（M3 只保存前 16 个寄存器、
M4 切换时不换用户栈）立刻被抓出来。

> 这条单独记下来：**判据里的期望值如果由被测路径自己算出，等于自己验自己。**

## 反向判据为什么写成"B0 在 A4 之后"而不是"没有 B0"

关掉定时器时，A 跑完 `exit` 之后仍会**顺序**切到 B，B/C 照样会跑。
所以"没有 B0"这条会失败——而失败的原因是我把判据写错了，不是代码错。
判据只能是**顺序**：A 必须一口气跑完，`B0` 排在 `A4` 之后。

同理，正向的"交织"不能只断言 `B0` 在 `A1` 之前：**内核不发 EOIR 的话第一次
IRQ 之后就再也进不来**，于是 A 一口气跑完、B/C 顺序接上，那也满足
"B0 在 A1 之前"，看着照样像交织。所以额外断言 `irq >= 8`（基线 18）。

**只打一次不算抢占。**

## 变异验证 6/6

| 变异 | 结果 |
|---|---|
| M1 IRQ 不应答 EOIR | 2 项红 |
| M2 调度器不推进 cur | 4 项红 |
| M3 只保存前 16 个寄存器 | 9 项红 |
| M4 切换时不换用户栈 | 6 项红 |
| M5 两类中止不分（只报权限） | 2 项红 |
| M6 中止后不杀任务 | 4 项红 |

## 已知限制

- **只有虚拟定时器一个中断源**，没有外部中断、没有优先级、没有中断嵌套。
- **没有真正的调度策略**：固定轮转，不看优先级、不做时间片记账。
- **中止一律杀任务**，没有"内核代为修复后再放回"的路径（缺 SIGSEGV 式交付）。
- `eret` 之后不检查 `spsr` 的 `M[3:0]` 是否真回到 EL0。
- 只在 CPU 模拟器里跑过，**未经真实硬件**。

下一步最自然的是**中断优先级 + 嵌套**，或者**睡眠/唤醒**（让任务能等事件
而不空转）。

## 依赖与静默跳过（v1.174 实测补记）

判据第 ④ 层「capstone 第三方反汇编核对」**依赖 `pip install capstone`**。
缺库时脚本记为**跳过**并打印提示，不算通过也不算失败 —— 这个设计是诚实的，
但它有两个后果此前没被注意到：

**一、本机此前一直没装 capstone**，所以 v1.171 ~ v1.173 报告里写的
「编码全部经 capstone 独立反汇编核对」**实际是跳过的**，那层核对一次都没执行过。
摘要里写的是 `37 通过 / 0 失败 / 4 跳过`，而我对外说成了「41 项全过」——
**跳过的 4 项被我算进了"通过"**。装上 capstone 后重跑，`41 / 0 / 0`。

**二、项目里没有任何地方声明这个依赖**（无 `requirements.txt`，README /
CLAUDE.md 均未提及）。于是在任何一台新机器上解包跑测试，这 4 项（a64mmu 是
6 项）**默认就少一层**，而摘要仍显示 `0 失败`。验证层存在、设计正确、但从未
真正执行 —— 与 autodiff 那次（FD 检验和点积检验本来就能抓 bug，却从没人跑）
是同一个模式，只是这次的载体是"外部依赖缺失"。

修法两条，都已落地：

- 新增 `requirements.txt`，声明 `capstone`（`pip install -r requirements.txt`）
- 两份文档都写明缺库时跳过几项，不把跳过算作通过

**给后来者的提醒**：看到 `N 通过 / 0 失败 / M 跳过` 时，M 不是 0 就等于
"有 M 项没验"，不要写成"全部通过"。
