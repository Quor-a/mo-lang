# 多级 checkpointing（1.85）：RAM / SSD / 网络

## 概念来源

Stumm, P. & Walther, A. (2009) "Multistage approaches for optimal offline
checkpointing", SIAM Journal on Scientific Computing 31(3), 1946–1967.

1.84 做了两级（RAM + 磁盘）。**那篇论文的正文主体是多级**：各级有各自的
容量与 IO 代价，快照要按容量与代价分配到各级。

实现现状：Firedrake 的 `checkpoint_schedules` 只有两级
（`TwoLevelCheckpointSchedule` / `MultistageCheckpointSchedule`）；
PyTorch / JAX 连一级的 Revolve 都没有。

## 🔴 多级有价值的前提：中间级容量有限

```
level 0  RAM    容量 c0（小）   IO 代价 0（主前向顺手存）
level 1  SSD    容量 s1（中）   IO 代价 w1
level 2  网络   容量 ∞          IO 代价 w2 > w1
```

便宜的 SSD 装不下时，溢出的快照才落到网络。

**若所有非 RAM 级都无限，只用最便宜那一级就够 —— 多级毫无意义。**
第一版两边都用「无限容量」，结果 1/2/3 级代价完全相同（都是 126），
多级看起来没有任何价值。加上 SSD 的容量约束 `s1` 后才出现区分度。

## 模型

把 `l` 步分成 `N` 段，段起点 `BK[0..N-1]`，按索引顺序分配到各级：

| 段起点索引 | 存哪 | 代价 | 容量 |
|---|---|---|---|
| `i < a0` | RAM 槽 `i` | 0（主前向顺手存） | `a0 <= c0` |
| `a0 <= i < a0+a1` | SSD | `2·w1` | `a1 <= s1` |
| `i >= a0+a1` | 网络 | `2·w2` | ∞ |

段内用剩下的 RAM 槽做 Revolve 递归。

```
T(N, a0, a1) = 2·a1·w1 + 2·(N-a0-a1)·w2 + Σ_i cost(seg_i(l,N), c)
c            = MK_C0 - a0 - (N > a0 ? 1 : 0)      # 末尾的 1 是临时槽
```

退化关系（都写成了断言）：

- `N <= a0` → 纯 RAM（1.83 的 Revolve）
- `s1 = 0` → 两级（1.84 的 Multistage）
- 三级 ≤ 两级 ≤ 一级（SSD 是网络的便宜替代）

## 实测（tape 49 步，c0 = 4，w1 = 1，w2 = 4）

| 配置 | N | a0 | a1 | 重算 | 总代价 | 相对纯 RAM |
|---|---|---|---|---|---|---|
| 一级（纯 RAM） | 2 | 2 | 0 | 126 | **126** | — |
| 二级（+网络） | 5 | 1 | 0 | 73 | **105** | −17% |
| 三级（SSD 容量 2，溢出） | 5 | 1 | 2 | 73 | **93** | −26% |
| 三级（SSD 容量 8） | 9 | 1 | 8 | 53 | **69** | **−45%** |

「溢出」那组 SSD 用满 2 个、其余走网络 —— 这是多级最核心的场景，
测试里断言 `a1 == s1` 且网络 IO > 0，否则算没测到。

SSD 太贵时（`w1 = 16`）自动退回不用 SSD，代价回到 105。

## 🔴 两个真 bug，都是"看起来对"的那种

### bug 1：σ_0 的网络副本让多级看起来毫无价值

第一版把外部加载的段起点存进**槽 0**，于是覆盖 σ_0；被迫再往网络存一份
σ_0 副本（+`2·w2`）。这笔开销大到让**所有**外部存储方案都输给纯 RAM ——
1/2/3 级代价清一色 126，多级像是个没用的想法。

正解：另给一个**临时槽 `a0`**。σ_0 的槽 0 永不覆盖，副本根本不需要。
代价是段内少一个槽（`MK_C0 - a0 - 1`）。

### bug 2：临时槽被段内递归立刻覆盖（加了校验才发现）

存好外部起点后没把 `AD_CKN` 推到 `a0 + 1`，段内递归第一个分配的槽
**就是** `a0`，立刻把刚存的 σ_p 覆盖掉。

这个 bug 在 144 个配置的梯度比对下**全部"通过"** —— 是加了
「槽内容与期望位置必须一致」的校验（`AD_CKERR = 6`）才暴露出来的：

```
修正前：144 配置，err=6 触发 78 次
修正后：144 配置，err=0
```

> 梯度对不代表状态对。快照调度这类问题，必须校验**中间状态**，
> 不能只看最终结果。

## 🔴 "代价更低"不等于"算法更优"

修正过程中试过一个变体：`mk_slot` 不留临时槽（`c = MK_C0 - a0`）。
它的代价**更低**（126 → 97 → 85 → 60），梯度也全对。

看起来是更优的算法。加上**槽预算约束**（`AD_CKMAX = MK_C0`）后：

| 版本 | 144 配置结果 |
|---|---|
| 留临时槽（本实现） | 梯度不一致 0，err 0 |
| 不留临时槽 | 梯度不一致 **129**，err **129**（`err=2` 槽耗尽） |

它只是**偷偷多用了 RAM 槽** —— 违反了用户设定的内存预算，不是算法更优。

这是本项目反复出现的主题的新变体：前几轮是「结果照样好 ≠ 没问题」，
这一轮是「**性能更好 ≠ 算法更优**」。判断"更优"之前，先确认约束没被绕过。

## 验证

1. **梯度一致性**：每个配置与完整反向逐值比对（参考梯度非零 24 个，
   若 sigmoid 饱和导致梯度全 0，测试立即判无意义）
2. **DP 与实测一致**：`ad_mk_total() == ad_mk_time()`（IO 计数 + 重算步数）
3. **IO 次数**：`IO_ssd == 2·a1`、`IO_net == 2·net`
4. **单调性**：三级(s1=8) ≤ 三级(s1=2) ≤ 二级 ≤ 一级
5. **退化**：`s1 = 0` 时与两级结果完全相同
6. **参数扫描**：144 个配置（c0 × s1 × w1 × w2）全部 err=0、梯度一致

## 接口

```mo
ad_mk_cfg(c0, s1, w1, w2)     # RAM 槽数 / SSD 容量 / SSD 代价 / 网络代价
ad_backward_multik(loss)      # 按最优分配反向
ad_mk_time()                  # DP 预测总代价
ad_mk_total()                 # 实测总代价（重算 + Σ IO×代价）
ad_mk_n() / ad_mk_a0() / ad_mk_a1()
ad_mk_io1() / ad_mk_io2()
```

## 限制

- `c0 <= AD_CKMAX(6)`；tape 超 255 步报错
- 慢级快照写全部 `AD_N` 个槽（最多 2048），非增量
- 代价用**计数模型**（IO 次数 × w），不是真实计时 ——
  定点小 workload 上噪声大于效应（1.79 的教训）
- 只支持能重算值的算子（conv/pool/gmax 等明确报错 1，绝不静默跳过）
