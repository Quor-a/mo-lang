## 概念来源

UAX #15：NFD（规范分解）、NFC（分解后重组）。C/C++ 标准库完全没有
（只能靠 ICU）；Go 与 Rust 要装第三方（x/text、unicode-normalization）；
Java 有 `java.text.Normalizer`、Python 有 `unicodedata.normalize`，
但都绑在运行时自带的完整表上、不可裁剪。

四条规则（本实现的全部难点）：

1. **递归分解**：U+1E14 → U+0112 U+0300，而 U+0112 → U+0045 U+0304。
2. **规范排序**：每段「基字符 + 组合记号」内按 ccc **稳定**排序。
3. **阻挡规则**：记号 C 若前面存在 `ccc(B) >= ccc(C)` 的记号 B，则 C 不得组合。
4. **Hangul 算法化**：U+AC00..U+D7A3 的 11172 个音节不进表，按公式现算。

## 实测：与 Python 的全量比对

```
NFD 比对 12822 条，不一致 0
NFC 比对 12791 条，不一致 0
因递归分解路径或 NFC 组合结果超出覆盖段而排除 75 条
```

覆盖面：U+0000..U+017F、U+0300..U+036F、U+0384..U+03FF、U+1E00..U+1EFF、
U+1100..U+11FF、U+AC00..U+D7A3 全部单码点，外加 540 条多记号序列
（6 个基字符 × 9 个记号 × 9 个记号，用来逼出排序与阻挡规则）。

**期望由 Python 现算，不落在仓库里** —— 换机器、换 Unicode 版本都能重算，
不会出现"期望文件陈旧但仍全绿"。

## 🔴 第一次跑测试就抓出的两个真缺陷

### 一、规范排序把循环变量当退出标志 → 记号被覆盖

`un_reorder` 原写法用 `k = i` 表示"找到插入位置"，于是收尾那句
`UN_D1[k+1] = cj` 永远落到**段首 i+1**，把已有的记号覆盖掉。

```
U+1E14（Ḕ）的 NFD   应为 0045 0304 0300
                    实得 0045 0300 0300   ← 0304 被 0300 覆盖
```

不报错、不崩溃，只是结果里少了一个**不同的**记号 —— 而且两者 ccc 都是
230，看起来完全合理。

> 这与 `lib/ac.mo` 同一轮修掉的插入排序是**同一个模式**：拿循环变量当
> 退出标志，就把索引毁了。同一个写法在两个独立模块里各错一次。

### 二、Hangul 音节分解正确、重组失败

U+AC00 的 NFD 是 `1100 1161`（对），但 NFC 仍是 `1100 1161`（错，应为 `AC00`）。

根因：U+1161（V）与 U+11A8（T）的 **ccc 都是 0**，在原实现里走的是
「新的基字符」分支，压根不会去尝试组合 —— 而 Hangul 组合逻辑其实早已
写在 `un_comp_pair` 里，只是没人调它。

修法：单独抽出 `un_hangul_pair()`，在 `ccc == 0` 分支调用。之所以不直接
调 `un_comp_pair`，是为了避免把相邻的两个普通基字符误组合起来。

## 已知限制（都没静默）

- 覆盖段之外的码点一律置 `UN_UNK` 并返回 -1
- **递归分解的中间产物若落在覆盖段外，分解会停在那里**：U+1E1C 的完整
  NFD 需要 U+0228 的分解，而 U+0228 不在表内，于是得到 `0228 0306`
  而不是 `0045 0327 0306`。全量比对里这类共排除 75 条，**是显式排除
  并报数，不是混入"不一致"也不是放宽判据**。
- NFC 需要**二阶组合**时（如 `0041 0308 0304` → U+01DE）同样受此限制
- 不做 NFKD / NFKC（兼容分解）
- 输入 ≤ 64 码点，输出 ≤ 512
