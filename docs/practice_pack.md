# 实战：二进制打包与结构化错误

版本 1.12.0（2026-10-09）

## 起因

一次外部评审把墨语言误认成了另一个同名的动态脚本语言，
给出的建议里大半基于错误前提（VM、GC、class、async）。
但筛掉不成立的之后，有**两条是真命中**的：

1. 有 `byte` / `load8` / `htons`，却没有 `pack` / `unpack` ——
   协议解析、文件格式解析全靠手拼 `load8(p) + load8(p+1)*256`，
   又啰嗦又容易把字节序写反。
2. 错误处理只有"打印并退出"和"静默返回 0"两种，
   缺**结构化错误**。

这两条都正中墨语言的定位（底层能力 + 消灭静默失败），所以照做了。

## 新增 lib/pack.mo

```
b/B = 1 字节    h/H = 2 字节    w/W = 4 字节    q/Q = 8 字节
```

便捷函数 `unpack_u32le` / `pack_u32be` / ... 共 20 个，
外加格式串驱动：

```mo
let n: i64 = unpack_fmt(&B, ">w h b", &OUT);   # 一次读完三个字段
```

**踩到的设计错误**：第一版让前缀 `<` `>` 和字母大小写**都**表示字节序，
于是 `">h"` 到底是按 `>` 大端还是按 `h` 小端？语义冲突。

与 Python struct 对齐后修正：前缀管字节序，**大小写管有无符号**。
这个错误是靠测试逼出来的——`">w h b"` 解出了错的值。

**另一个**：格式串里有空格时（`"w h b"` 这种可读写法），
第一版把空格当格式字符 → 整串判非法。已支持空格分隔。

## 新增 lib/err.mo

统一错误码 + 消息 + 位置：

| 码 | 含义 |
|---|---|
| `E_IO` / `E_FOUND` | 打不开 / 找不到 |
| `E_RANGE` | 越界、长度超限 |
| `E_FORMAT` | 魔数不符、解析失败 |
| `E_NOMEM` / `E_ARG` | 分配失败 / 参数非法 |

```mo
if read_file(&path, &buf, cap) < 0 {
    print(err_msg());     # "cannot open file"
    print(" @ "); print(err_where()); print_nl();   # "@ read_file"
    return err_code();
}
```

`err_wrap(code, msg, where)` 是"设置并返回 -1"的简写，
让失败路径能写成一行。

**推广策略**：先只改 `fs.mo`，且**返回值语义完全不变**（失败仍是 -1），
只是额外记录原因。所以既有调用方一行都不用改就能拿到诊断。
这是能安全铺开到其余 17 个库的前提。

## 实战验证：examples/wavinfo.mo

纯靠单元测试测不出"给一个真 WAV 能不能解析对"，所以写了这个应用。
它是 `pack.mo` 的实战验证：WAV 是小端、定长、chunk 嵌套——
正是没有 pack 就很难写的那类格式。

实测（44100Hz / 立体声 / 16bit / 1 秒）：

```
format    : PCM
channels  : 2
rate      : 44100 Hz
bits      : 16-bit
byterate  : 176400 B/s
data      : 176400 bytes @ offset 44
duration  : 1.00 s
```

三种错误路径都给出**具体**原因：

| 情形 | 输出 |
|---|---|
| 文件不存在 | `error[6] no such file @ stat_size` |
| 不是 WAV | `error[3] not a RIFF file @ walk` |
| 被截断 | `error[2] RIFF size exceeds file size (truncated?) @ walk` |

### 抓到的容量 bug

初版把整个文件读进 64KB 缓冲再校验，于是 176KB 的 WAV
被判成"截断"。修正：头部只需前几十 KB，
真实大小用 `stat_size` 单独取，两者分开校验。

> 校验要用真实大小，解析只需局部数据。把它们混为一谈，
> 就会把"只想看个头"变成"必须塞得下整个文件"。

### WAV chunk 的对齐陷阱

chunk 数据按 2 字节对齐，奇数长度后要跳 1 个填充字节。
少了这一步，遇到奇数长度 chunk 就会把填充字节当成下一个 chunk id。

## 后续：一次外部实战暴露的两处缺失

外部用墨语言写真实程序（qylog）时撞到两个问题，经定位：

1. **`let p: ptr = buf;` 生成的地址是错的** —— 真因不是"指针下标不支持
   写入"，而是**缺数组到指针的退化**。`&buf` 一直正常，所以对照一下就能
   把范围从"下标代码生成"缩小到"数组当值用"。已修（1.13.0）。
   教训：先找一个"已知能用"的近似写法做对照，能立刻砍掉一半搜索范围。
2. **`dir_next` 的 `ty` 形参收了却从不写入** —— 调用方拿不到条目类型。
   已修。

顺带补了 `dir_list` / `dir_list_max` / `dir_list_type` 批量接口。
用 `vec`（动态增长）收集而不是填充固定缓冲，是从根上消除
"条目数超过缓冲"这一整类问题——实测 147 个条目曾直接越界段错误。
