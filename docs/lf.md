# 无锁数据结构与危险指针（lib/lf.mo）

## 概念来源

三条都是**有出处的算法**，不是惯例：

| 算法 | 出处 |
|---|---|
| Treiber 栈 | R. K. Treiber, *Systems Programming: Coping with Parallelism*, IBM RJ 5118, **1986** |
| Michael–Scott 队列 | M. M. Michael & M. L. Scott, *Simple, Fast, and Practical Non-Blocking and Blocking Concurrent Queue Algorithms*, PODC **1996** |
| 危险指针 | M. M. Michael, *Hazard Pointers: Safe Memory Reclamation for Lock-Free Objects*, IEEE TPDS 15(6), **2004** |

**为什么值得单独做**：三者都**没有进任何主流语言的标准库**。Java 只在 JDK 内部用
（ConcurrentLinkedQueue），C++ 只有 boost::lockfree / folly，Rust 只有 crossbeam。
危险指针更极端——它是**用户态内存回收协议**，主流运行时要么有 GC 不需要，要么藏在库里。

## 设计取舍：节点是槽位下标，不是指针

墨语言没有泛型、也没有顺手的堆分配器。所以节点是全局数组的**槽位下标**，
`head/tail` 打成 `(tag, idx)` 的 64 位字（IBM 标记指针），一次 CAS 同时比较两者。

- `LF_NEXT[i]` 存纯下标；ABA 防护由 head/tail 的 tag 负责。
- 空闲槽位本身也是一把 Treiber 栈（`LF_FREE`），所以**分配一个节点也是一次无锁出栈**。

## 🔴 本轮最阴的坑：CAS 返回值高 24 位是垃圾

`__atomic_compare_exchange_8` 真正返回的是 **bool（1 字节）**。按 SysV ABI
只有 `AL` 有定义，`EAX` 的高 24 位是垃圾。而墨语言对 `extern ... -> i32`
的调用序列末尾是 `cltq`（按符号位扩展 EAX→RAX），于是垃圾被带进 RAX：

```
实测：C=0、期望=100000（必然不匹配）
    原始返回值 = 199936     ← 非 0，看起来"成功"
    实际结果   C 未变、E 被写回 0   ← CAS 语义本身是对的
    r & 255   = 0           ← 才是真正的返回值
```

后果不是"跑不通"，而是：**每一次失败的 CAS 都被当成成功**。调用方以为自己
拿到了那个槽位 → 同一个槽位被两个线程各分配一次 → 空闲链表出现自环 →
`LF_NEXT[s] == s`，栈永远弹不完。不报错、不崩溃。

**实测证据**：4 线程 × 20000 次 CAS 自增

| | want | got |
|---|---|---|
| 修前 | 80000 | **65626** |
| 修后 | 80000 | **80000** |

而单线程下常被"eax 恰好为 0"掩盖——`lf_cas` 单线程自测是绿的。

## 🔴 v1.132：不再依赖 ABI 未定义行为（双通道）

`& 255` 是**正确**的做法，但它仍然依赖"AL 之外的位无意义"这一前提的补集——
一旦有人抄错、或者 libatomic 换实现，危害就回来了。v1.132 把成功与否的
**主键换成 `LF_EXP` 有没有被改写**：

```
CAS 成功 ⟺ *p == exp
失败时 libatomic 必然把 *p 的实际值写回 LF_EXP
⟹ LF_EXP[tid] == exp ⟺ 成功        （充要，且完全不依赖返回值）
```

于是 `& 255` 从"决定生死"降级为**交叉校验**：两条通道不一致就置 `LF_DUAL`
计数并响出来。这样即使返回值通道再坏一次，语义仍然正确，只是不再静默。

**这同时解决了"M1 抓不到"的问题。** v1.131 报的"M1 被捕获 10/15"是错的——
真实情况是：单线程下 eax 恰好干净，`& 255` 与否**完全等价**，15 项断言全绿；
只有并发下偶尔撞上垃圾才会显形（守恒 `ok=-1` 偶发）。新增的确定性场景
（必然失败的 CAS 循环 200 次）实测 `rsum` 也是 0 —— 200 次里一次都没撞上。

而 5 万次失败 CAS 里垃圾出现率约 **8.5%**（`dual ≈ 5849 / 69119`）：

| | dual |
|---|---|
| 基线 | **0** |
| M1（去掉两处 `& 255`） | **4961 ~ 6154** |

> 偶发不是"测不出来"，是"样本不够"。把观测计数加进去，偶发就变成了可测的数字。

顺带实测到一个副作用：M1 下无锁栈耗时从 ~22ms 涨到 ~190ms ——
`LF_DUAL++` 落在失败热路径上（每线程数万次），多线程写同一 cache line 争用。
故该计数**只在检测到不一致时才写**，正常路径零开销。

## 两个可复现的静默缺陷场景

`examples/lfbench.mo` 把二者做成了**受控交错**（不是碰运气撞出来的竞态）：

**ABA**（栈里 1/2/3，读 head=3、next=2，中途别人 pop 3、回收、复用同一槽位推回）

| | commit | 剩 |
|---|---|---|
| 有 tag | 失败(0) | **3** |
| 无 tag | 成功(1) | **2** ← 丢了 3，重复了 2 |

**UAF**（pop 出的槽位在还被引用时被回收复用）

| | 读到的值 |
|---|---|
| 不保护 | **999**（已被新数据覆盖） |
| 危险指针保护 | **3**（回收被挡住） |

## 吞吐实测（4 线程 × 20000 次 push+pop，2 核）

| | 耗时 | CAS 失败 |
|---|---|---|
| 无锁栈 | 76–177 ms | ~54000 / 80000 |
| 互斥锁栈 | **4–12 ms** | — |
| 无锁队列 | 78–192 ms | ~17000 |

**无锁比互斥锁慢 5–20 倍**。原因不是实现差，而是线程数(4) > 核数(2)：
CAS 失败后是**自旋重试**，在抢占式调度下大量重试白烧 CPU；互斥锁让出 CPU。
这是一条**反直觉但可复现**的结论——"无锁更快"只在**线程数 ≤ 核数**时成立。

## 验证

```bash
make lftest     # 18 项断言（守恒/ABA/UAF/CAS 双通道/吞吐）
make lfmut      # 三个变异
```

守恒判据是**数字**：push 4000，drain 必须正好 4000，`missing=0 dup=0 oob=0`。
漏或重都只表现为数字不对，不报错。

变异（v1.132 实测，基线 18/18）：

| 变异 | 结果 |
|---|---|
| M1 去掉两处 `& 255` | 17/1 —— `dual` 从 0 涨到约 5000 |
| M2 去掉 `lf_scan` 的危险指针检查 | 17/1 —— UAF 场景失灵 |
| M3 让 `lf_mk` 不打包 tag | 17/1 —— ABA 场景失灵 |

`lfmut.sh` 自身踩过四个坑，脚本里都有防：备份放 `/tmp` 会被沙盒回收；
`out=$(cmd | tail -1); rc=$?` 取的是 `tail` 的退出码恒为 0；被强杀后下一轮
基线被上一轮变异污染；以及"改了点东西"不等于"改到那条因果链"。

## 已知限制

- 槽位固定 4096、线程最多 8、每线程 3 个危险指针、64 个待回收槽；超出返回 -1，不静默。
- 确定性 CAS 场景只循环 200 次，**不足以**稳定撞上垃圾高位（实测 rsum 恒 0）；
  真正稳定的判据是并发后的 `dual` 计数（5 万次失败里约 8.5% 撞上）。
- `LF_DUAL / LF_CASFAIL / LF_NALLOC / LF_NRETIRE / LF_NRECLAIM` 是**非原子**计数器，只作观测。
- 无锁容器没有良定义的 `size()`，故不提供。
- 依赖 libatomic：`molink.sh` 借 `gcc -print-file-name=libatomic.so` 问出路径再交给 ld。
- 队列出队每次退役一个旧哨兵，与入队分配一个配平；值在 CAS **之前**、保护之下读取。
