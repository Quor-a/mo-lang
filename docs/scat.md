# scat —— str 的 `+` 拼接与生命周期

墨语言 v1.121.0。

1.118 让 `str` 成为一等类型（`==` 比内容），1.119 补齐字典序，1.120 补 `\xHH`。
**唯独 `+` 一直没做**，理由写在 `docs/str.md` 里："需要分配器与生命周期"。
本版把这个缺口补上。

```
let a: str = "abc";
let b: str = "def";
let c: str = a + b;      # c == "abcdef"，a 与 b 都不改动
c += "ghi";              # += 同样是拼接
```

## 为什么 `+` 比 `==` 难：它必须分配

`==` 只读取，`+` 要**造出一个新串**。而造出来的东西归谁释放？三条路：

| 方案 | 代价 | 失败时的表现 |
|---|---|---|
| 每个结果单独 free | 漏一个就是泄漏 | **不报错、不崩溃**，内存一路涨到某天 OOM |
| 永不释放（bump） | 长跑程序把 brk 一路推高 | 同上，只是涨得更快 |
| **region（本版）** | 不能单独回收某一个对象 | 要回收只能整批，但**不可能漏** |

region 这条路线对标 Tofte & Talpin 1994 的 region inference（ML Kit）、
Cyclone 的 region（Grossman 等，PLDI 2002），以及 Rust 生态的 arena / bumpalo。
**它不是 GC**：不需要 tracing、不需要引用计数、不需要写屏障。

选它的理由是第一条的失败模式最危险 —— 泄漏是静默的，
而 region 把"忘记释放"从一类错误直接消掉：根本没有单个对象可释放。

## 接口（`lib/scat.mo`）

```mo
scat_cat(a, b) -> str    # 新分配一份，入参不改动
scat_dup(s)    -> str    # 复制进 region
scat_reset()             # 丢弃本批全部对象，但**保留**内存供复用
scat_len(s)    -> i64    # 求长（O(n)，本文件自带，不依赖 str.mo）
scat_used() / scat_cap() / scat_n()
scat_copy()    -> i64    # 累计复制字节数
scat_mov()     -> i64    # brk 移动次数
scat_err()     -> i64    # 分配是否失败过
```

**`reset` 保留内存**是刻意的设计：把容量也归零的话，下次拼接要重新
`brk`，那跟"永不释放"没有区别。测试里 `reuse-mov` / `reuse-cap`
专门盯这条 —— 只测 `used == 0` 证明不了复用。

## 一个必须说清的取舍：朴素拼接是 O(n²)

`s = s + "x"` 循环 n 次，每次都要把已有前缀重抄一遍。实测复制字节数
**精确等于 n(n+1)/2**：

| n | 累计复制字节 |
|---|---|
| 100 | 5050 |
| 200 | 20100 |

n 翻倍、复制量 4 倍。这不是"感觉上会慢"，是量出来的数字
（`tests/130_scat.mo` 的 `copy-100` / `copy-200` / `quadratic` / `not-linear`）。
要线性得换 rope 或写时复制，本版**没有做** —— 先把语义做对。

## 🔴 修掉的静默缺陷：`+=` 走的是地址相加

`str` 的 `+=` 此前落到通用复合赋值 → `g_add()`。两个字符串地址相加在
机器层面完全"合法"：

- 结果落在未映射内存 → **段错误**（实测 exit 139）
- 结果恰好落在已映射内存 → **静默**给出一个偏移后的串，不报错也不崩

第二种才是最坏的：程序照常跑，输出看起来像字符串。
现在 `+=` 与 `+` 都走 `g_str_cat()`，类型不匹配一律明确报错
（`str 只支持 '+='` / `'+=': str 只能拼 str` / `'+=': 非 str 不能拼 str`）。

## 本库为什么一个库都不 import

`str.mo → arena.mo → heap.mo → str.mo` 会形成**循环依赖**，
于是所有只 import str.mo 的示例全部编译失败。所以 `scat.mo`
自己写了一遍 strlen / 拷贝，分配直接用 `brk`。

## 判据：五个变异全部被捕获

只看 "ran 41, failed 0" 什么也证明不了 —— 断言可能压根没参与判断。
`tools/scatmut.sh` 逐个把实现改坏：

| 变异 | 结果 |
|---|---|
| M1 编译器 `+` 退回地址相加 | exit 139 |
| M5 编译器 `+=` 退回地址相加 | exit 139 |
| M2 库侧不写结尾 NUL | failed 6 |
| M3 reset 把容量也归零 | failed 2 |
| M4 复制计数写死为 1 | failed 5 |

M5 第一版**没验到点子上**：把 `if ty_kind(clt) == 10` 改成 `if 0` 之后，
str 的 `+=` 落到 else 分支被类型检查挡住 —— 编译期就报错、`out.elf` 没生成，
脚本照样判"被捕获"。可那验的是"类型检查存在"，不是"拼接是对的"。
改成只换运算（`g_str_cat()` → `g_compound`）才回到真实缺陷状态。

> **变异必须直接回到缺陷状态。"改点东西然后看它失败"是不够的。**

## 已知限制

- **朴素拼接 O(n²)**（见上，有数字）
- **不支持 `str` 数组与 `str` 结构体字段**：这两处的 `+=` 分支同样写了，
  但语言层面还不支持这两种声明，所以**无法测到**，不声称已验证
- `scat_len` 是 O(n)
- region 不能单独回收某个对象
- 不做 UTF-8 校验（在 `lib/utf8.mo`）
