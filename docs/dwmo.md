# dwmo —— 墨语言自己写的 DWARF 校验器

`tools/dwmo.mo` → `bin/dwmo`，验证 `-g` 生成的调试信息是否真的对得上机器码。
`make dwmotest` 会让它和 Python 版 `tools/dwvar.py` 跑**同一份源码**生成的 elf，
两份都必须通过。

## 为什么要重写一遍

`dwvar.py` 干的是同一件事，但它是 Python，而且要借 `readelf` + `objdump`。
也就是说：调试信息是自己生成的，验证器却不是 —— 自包含生态在这一环是断的。

dwmo 直接读 ELF 二进制，全程不调任何外部工具：

| 环节 | dwvar.py | dwmo |
|---|---|---|
| 找节 | readelf | 自己解析 ELF64 节头表 |
| 读 DIE | readelf 文本 + 正则 | 自己解析 `.debug_abbrev` 再按 form 读 |
| 找 `[rbp+off]` | objdump 反汇编 | 自己写指令长度解码器 |
| 读 CFI | readelf | 自己解析 CIE/FDE 与 DW_CFA 流 |

## 比 Python 版多一条断言

Python 版把字节块丢给 objdump，objdump 是黑盒 —— 它说有 `[rbp-8]` 就有，
没人验证它扫得对不对。

dwmo 自己解码，于是可以断言：**线性扫描的指令边界必须精确落在 `high_pc`**。
任何一条指令长度算错，末尾就对不上。这是对"扫描本身"的校验，
而不是只校验扫描结果。

## 三个坑

1. **REX.B 必须排除**。`rm==5` 在 `REX.B=1` 时是 **r13** 不是 rbp。
   漏了会把 r13 的偏移当成 rbp 的，"偏移能在机器码里找到"就变成**假通过**。
2. **`ref4` 的基准是 `.debug_info` 段起始**（含 `unit_length`），
   不是 CU header 之后。差 11 字节，表现是"类型 DIE 未找到"。
3. **DIE 的偏移要记在读 abbrev code 之前**。记成之后的位置，
   所有类型引用都对不上。

## 限制

- 指令长度表覆盖常见指令；遇到无法解码的会返回负值并判失败，不静默跳过
- `.debug_frame` 只取 `initial_location` / `address_range` / CFA 寄存器
- 不解析 `.debug_line`（行号表的校验仍在 Python 版）

## v1.97：扫真实大程序（bin/moc 本体）

### 为什么必须换被测对象

`run_checks()` 是针对小测试程序写死的（fib / addup / Point 这些具体名字）。
对着 bin/moc 一条也对不上 —— 于是"dwmo 是对的"这个结论的**覆盖面一直只有
那 20 行源码**。小程序函数体短、指令种类少，解码器里写错的分支可能
根本没被走到。

新加 `-s` 模式：只做与被测程序无关的通用校验，对任何 -g 产物都成立。

```
== dwmo -s（扫 bin/moc 本体）==
  函数（subprogram 带代码）  355
  解出的指令条数            43798
  覆盖 .text 字节数         142500
  收集到的 [rbp+off] 偏移数 937
  跳转/调用目标检查数      5418
  目标不在指令边界上的     0
通过 7 / 失败 0
```

### 🔴 核心发现：边界落在 high_pc 是**必要但不充分**

我一直把"线性扫描的边界必须精确落在 high_pc"当作对扫描本身最强的校验。
**实测推翻了这一点。**

把 1.95 修过的 `mod == 3` 分支去掉（`sub rsp,N` 多算 1 字节）：

```
  解出的指令条数            42704   ← 确实变了
  OK  每个函数的指令边界精确落在 high_pc   ← 仍然通过！
```

逐条打印指令长度才看清原因：

```
正确: 1 3 7 4 3 1 4 3 4 4 6 ...
变异: 1 3 8 3 3 1 4 3 4 4 6 ...
      边界: 0 1 4 11 15 ...
            0 1 4 12 15 ...   ← 第 15 字节处重新对齐
```

**解码器会自同步**：多算 1 字节后，下一条少算 1，两三条之内又对齐了。
于是总和 = hi-lo、末尾也精确落上 —— 只看末尾，bug 被完全放过。

### 补一条独立的不变量：跳转目标必须落在指令边界上

直接跳转/调用的目标是链接器按**真实**指令长度算出的绝对地址，
它不依赖我们的解码器。目标必须落在扫出来的某条指令边界上；
解码器一旦错位，边界集合整体偏移，目标就落空。

```
  跳转/调用目标检查数      5418
  目标不在指令边界上的     4      ← 变异后，被捕获
```

### 再加一层：与 objdump 逐函数比对（`-S`）

`-S` 逐函数输出 `lo hi 指令数`，`tools/dwbig.sh` 拿 objdump 当独立参照：

```
  函数数            355
  dwmo  指令总数    43798
  objdump 指令总数  43798
  ✓ 逐函数指令数与 objdump 完全一致
```

注意定位：**dwmo 自己不调 objdump**（否则就不叫自包含了）。
这是测试时拿外部反汇编器当独立参照，用来证明 dwmo 的结论可信。
没有 objdump 的环境自动跳过。

### 三层检测能力的实测对比

两个变异，都是 1.95 修过的**真** bug（不是人为构造）：

| 检查 | 变异1（mod==3） | 变异2（group3 立即数） |
|---|---|---|
| 边界落在 high_pc | ❌ 放过 | ❌ 放过 |
| 跳转目标落在指令边界 | ✅ 捕获（4 处落空） | ❌ 放过 |
| 与 objdump 逐函数比数 | ✅ 捕获 | ✅ 捕获（29 个函数不一致） |

**结论：单一断言不足以证明解码器正确，三层才够。**
而且这三层是递补的 —— 上一层放过的，下一层才抓到。

### 容量上限显式化

扫大程序时 DIE 数轻松破千，越界时墨语言只报 `index out of bounds`，
没有上下文，看不出是 DIE 满、FDE 满还是 abbrev 满。现在逐容器显式报错
（MAXD 4096 / MAXF 4096 / MAXAB 256 / MAXR 512），并置 `CAPERR`
让调用方退出，而不是带着**静默截断**继续跑出看似正常的结果。

> 静默截断是这里最危险的一类失败：报告会少报，但看起来完全正常。


## .debug_line —— 行号表（`-l`）

### 为什么值得单独做

`.debug_info` 里的 `DW_AT_decl_line` 说"函数定义在第几行"，
`.debug_line` 说"哪个地址属于第几行"。这是**两条独立生成**的通道：

- 前者在 `parse_func()` 里记下 `K_LINE`
- 后者靠 `dbg_mark()` 在语句边界登记 `(代码偏移, 行号)`

两条对不上，gdb 就在函数定义行下不了断点 —— 而**编译和运行都不会报错**。
在 1.98 之前，这两条通道之间没有任何校验。

### 抓到的真缺陷

`dbg_mark()` 唯一的调用点在 `parse_stmt()` 开头。而 `fn xxx(...)` 的
**函数定义行不是语句**，根本不经过 `parse_stmt`。于是：

```
行号表实际从函数体第一行开始，函数入口地址处没有记录
→ bin/moc 里 355 个函数有 290 个的定义行不在自己的行号记录里
```

举个具体的：`fn sv` 定义在第 266 行，但行号表里 `[0x4000f1, 0x400146)`
这段（横跨 `gv` 尾部和 `sv` 入口）被标成第 263 行。266 根本不存在。

修法是新增 `dbg_mark_at(ln)`，在 `parse_func()` 里**发射序言之前**调用
（此刻 `K_CLEN` 正是函数入口偏移）。行号必须显式传入 —— 到函数入口时
`K_LINE` 已经走到参数或函数体了。290 → **0**。

### 独立的第三方确认

readelf（不是 dwmo）解码同一份 elf：

```
修复前:  263 @ 0x4000f1    267 @ 0x400146     ← 262、266 缺失
修复后:  262 @ 0x4000e2    263 @ 0x4000f1    266 @ 0x400133
```

### 八条断言（对任何 -g 产物成立，不是针对测试程序写死）

| 断言 | 在 bin/moc 上 |
|---|---|
| 解析出行号记录 | 5908 条 |
| 以 end_sequence 正常收尾 | 1 个 sequence |
| 所有地址落在 .text 内 | 0 越界 |
| 地址单调递增 | 0 回退 |
| 每条记录落在某个函数 `[lo,hi)` 内 | 0 落空 |
| end_sequence == 代码末尾 | 4337771 == 4337771 |
| 每个函数至少一条记录 | 0 个空函数 |
| 定义行出现在自己的记录里 | **0**（修复前 290） |

覆盖率 99%（143241 / 143291 字节；开头 stub 无行号）。

### 状态机是完整的，不是"只解析自己生成的那三种操作码"

当前 moc 只发射 `copy / advance_pc / advance_line / end_sequence`
这四种。**但校验器实现了 special opcode、extended、standard 全套**，
并且未知 standard opcode 会按 header 里的 `standard_opcode_lengths`
跳过参数。

这是刻意的：如果校验器只认自己生成的那几种，将来改用 special opcode
时它会**跟着一起错**，那就不是独立参照了。

### 变异验证

把行号比较改成 `decl_line + 1`，`-l` 立即失败 —— 说明这条断言对
"差一行"敏感，而不是只看"有没有记录"。

### 已知限制

- `MAXL = 8192` 条记录上限，超出显式报错（当前 5908，余量不大；
  扫更大的程序需要调大）
- 不解析 `.debug_line_str`，不支持 DWARF v5
- 覆盖率用 `end - first_row` 近似，不是逐段求和

## `-L <source>`：拿源码当第三方参照

### 为什么还需要这一层

到此为止，所有检查都在 DWARF **内部**打转。但行号是编译器自己报的、
行号表也是编译器自己生成的 —— 两相比对只能证明**自洽**，证明不了
**对得上源码**。

变异实测最能说明问题：把函数定义行登记进行号表时用的行号整体 `+1`：

```
地址非递增              0
地址不在任何函数内      0
覆盖率                  99%
end_sequence 地址 == 代码末尾        OK
每个函数的定义行都出现在自己的行号记录里  ← 这条红了（291 个）
```

**前面 8 条内部断言全部仍然通过。** 没有任何内部不变量能发现
"整体偏移一行"，而 gdb 会稳稳地停在上一行。

### 校验什么

| # | 断言 | 抓什么 |
|---|---|---|
| 1 | 行号在源文件行数范围内 | 行号基址算错 |
| 2 | 没有行号指向空白/注释行 | 那种行不可能生成代码 |
| 3 | 定义行真的是 `fn` 那一行 | 行号与源码错位 |
| 4 | 定义行里有该函数自己的名字 | 行号对但函数错位 |
| 5 | 源码里没有漏登记的 `fn` 行 | 有函数定义行下不了断点 |
| 6 | **入口行号记录**里写着这个函数 | 专查行号表那一份 |

### 第 6 条为什么单独存在：两条通道

`decl_line` 是写进 DIE 的属性，行号表是**另一份独立数据**。上面那个
变异只改行号表，于是 3/4/5 条（查 `decl_line` 的）**仍然全绿** ——
它们没坏，绿是对的。只有第 6 条报红（355/356）。

反过来也成立：1.98 修的那个 bug（函数入口根本没登记）是第 5 条抓的。
**两条通道各需要各的检查，缺一条就漏一半。**

### 用法

```bash
./bin/moc src/compiler.mo -g moc.elf
./bin/dwmo moc.elf -l -L src/compiler.mo
```

`make dwbig` 已经带上 `-L`（扫 `bin/moc` 本体：356 函数 / 7879 行源码）。

### 实测

```
源文件行数              7879
其中代码行              6161
行号越界                0
行号指向空白/注释行     0
有入口行号记录的函数    356
入口行号里没有函数名    0
定义行里没有该函数名    0
定义行不是 fn 行        0  / 356
代码行未被行号表覆盖    1245
其中疑似函数定义行      0
```

1245 个未覆盖的代码行是 `var` 声明、类型定义之类——它们本就不生成
代码。真正可疑的是其中"像函数定义"的，实测 **0**。

### 变异验证：证明它不是空转

`tools/dwmut.sh`（`make dwmut`）真的去改编译器源码
（`dbg_mark_at(fnln)` → `fnln + 1`），用它造出新编译器、再编译自己，
然后确认 `-L` 报红：

```
== 基线：正常版必须全绿 ==      通过 18 / 失败 0
== 变异版：必须报红 ==
  BAD 没有行号指向空白行或纯注释行
  BAD 源码里没有漏登记的函数定义行
  BAD 函数入口的行号记录里确实写着这个函数
✓ 变异被抓到（-L 非空转）
```

脚本用 `trap restore EXIT` 保证任何退出路径都还原 `src/compiler.mo`。

只看"通过"分不清"真对"和"没检查到" —— 这是本项目反复踩到的教训，
所以校验工具本身也要有自己的变异测试。

### 两个坑

**`strstr` 返回的是下标，不是布尔。** 找不到返回 `-1`，而命中在**行首**
时返回 `0`。所以：

```mo
if strstr(SRC_TMP, needle) < 0 { return 0; }   # 对
if strstr(SRC_TMP, needle) != 0 { ... }        # 漏掉所有行首匹配
```

**`D_NM[]` 存的是偏移，不是地址。** 它记的是 `.debug_str` 里的偏移量，
直接 `print(D_NM[f])` 会拿到一个像地址的数字然后 SIGSEGV —— 表现为
**退出码 139**，没有任何错误信息，很容易误判成"逻辑崩了"。必须写
`print(BUF + D_NM[f])`。

### 已知限制

- 只处理**单文件**源码。`import` 进来的子文件其行号不在主文件范围内，
  目前会落在"越界"计数里（当前为 0，因为 `compiler.mo` 没有 import）
- 源码缓冲 3MB；行表走堆（避开 1.94 踩过的全局区上限）
- 不校验"某个代码行本该生成代码却没生成" —— 1245 个未覆盖行里
  有没有这种，目前只能靠人看"疑似函数定义行"那一项
