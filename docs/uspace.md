# uspace —— 交叉编译出来的最小用户空间

`examples/uspace.mo`

```
bash tools/android_native.sh examples/uspace.mo /tmp/uspace.arm64
adb push /tmp/uspace.arm64 /data/local/tmp/uspace
adb shell /data/local/tmp/uspace
```

验证：`make uspacetest`（两端对照，26 项，脚本 `tools/uspacetest.sh`）·
`make uspacemut`（5 个变异，脚本 `tools/uspacemut.sh`）

## 它回答的是什么问题

「自带运行和执行环境」这句话，用一个能跑的程序证明不了 —— 那只能说明
**这段代码能在 ARM64 上跑**。用户空间要证明的是**它能自我维持**：

```
建根目录 → 写启动脚本 → 读回来 → 逐行解释 → 装包 → 执行 → 卸包
```

全程不依赖 libc / fork / exec / git / 任何已存在的运行时。

所以本程序刻意把启动脚本**写进文件再读回来执行**。若直接执行内存里的
字符串，"读文件"那一段就是死代码，而"能在目标机上持久化状态"恰恰是
用户空间与 demo 的分界线。

## 实测（两端同一组数字）

| 步骤 | ARM64（模拟器） | x86-64（真机） |
|---|---|---|
| 建根 `/mo` | ret=0 | ret=0 |
| 写 init.rc | 113 字节 | 113 字节 |
| 读回 | 113 字节 | 113 字节 |
| 读回逐字节相同 | 1 | 1 |
| 执行的命令条数 | 6 | 6 |
| 装包后执行 | **42**（6×7） | **42** |
| 篡改后执行 | **-6**（拒绝） | **-6** |
| 卸包前 / 后 | 1 / 0 | — / 0 |
| 卸载后再查 | -1 | -1 |

x86-64 端跑在**真文件系统**上，跑完验证 `/mo/hi.txt` 真的留在磁盘上、
`init.rc` 真的被删掉了 —— 这两条证明读写与删除作用在真内核上，而不仅是
模拟器的内存文件系统。

ARM64 端额外断言：全部 6 次 `*at` 调用的 `dfd` 都是 `AT_FDCWD(-100)`。

## 判据为什么这样定

- **写 113 字节 + 读回 113 字节 + 逐字节相同**：只比长度的话，写进去的是
  垃圾也照样通过。
- **命令条数 == 6**：少执行一行也数不出来。第一版正是只跑了 2 条。
- **装包后执行 == 42，且篡改后必须失败**：只断言 42 的话，"VM 压根没跑、
  直接返回常数"也能得到 42。篡改后必须 -6 才堵死这条假路径。
- **卸包后包数减一、且查不到**：只删注册表不删内容（或反过来），都能让
  查询行为不变。

## 三个坑

**一、硬编码字符串偏移量把脚本截断了。** 第一版用
`scopy(&SCRIPTO + 41, ...)` 手工累加偏移，第二段实际长度算错一位，
字符串在中间被 `\0` 截断 —— 于是**写进去 40 字节、读回 40 字节、逐字节
比对也相同，却只跑了 2 条命令**。长度判据与一致性判据全绿，覆盖却是空的。
改用 `sapp()` 追加。这类"数字都对、覆盖为零"的失效，本项目已在 SAM
（v1.141）、CMS（v1.144）各遇到一次。

**二、`atoi` 与 C 标准库冲突。** cfs 后端把墨语言代码落成 C 再编译，
自写 `atoi` 撞上 libc 同名符号（`conflicting types`）。改名 `s2i`。

**三、`syscall` 参数个数上限。** *at 适配会插入一个 `dfd` 参数，所以
`open` / `mkdir` / `unlink` 这几类最多只能给 6 个实参，给 7 个就报
"适配后超出 7 个形参"。`read` / `write` / `close` 不参与适配，不受影响。

## 变异验证 5 / 5

| 变异 | 变红项数 |
|---|---|
| M1 `pk_run` 不做校验和检查 | 2 |
| M2 `pk_del` 不减少包数 | 3 |
| M3 `fnv` 返回常数 | 2 |
| M4 VM 的乘法改成加法 | 2 |
| M5 解释器不执行命令 | 9 |

脚本自带开工自检：源码若残留变异标记则先自愈再取备份 —— 备份取自污染
源码会让"基线没通过"这种假象反复出现（v1.135 / v1.142 各栽过一次）。

## 已知限制

- 路径写死 `/mo`，无 `chroot` 概念，也不做权限检查。
- 启动脚本是源码内嵌的，不是从外部传入（模拟器无 stdin，`read(0)` 恒
  返回 EOF，交互式 REPL 无法端到端验证）。
- 包名最长 31 字节、最多 32 个包、包代码最长 64 字节；超出返回 -7/-8
  响亮失败，不静默截断。
- 命令只有 7 个（`echo` / `write` / `cat` / `install` / `run` / `ls` /
  `del`），每条命令最多 3 个 token。
- 校验和是 FNV-1a，**不是签名**：能发现"被改坏"，证明不了"来源可信"
  （后者见 `docs/pkgsig.md`）。
- 未做依赖解析与版本升级，那是 `pkgv3.mo` 的事 —— 本文件只证明
  "用户空间能自己跑起来并装包执行"。
