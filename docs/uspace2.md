# uspace2 —— 完整用户空间

`examples/uspace2.mo`
构建：`bash tools/android_native.sh examples/uspace2.mo /tmp/uspace2.arm64`
验证：`make uspace2test`（两端对照 55 项）· `make uspace2mut`（7 个变异）

它是 `examples/uspace.mo`（v1.161 最小用户空间）的**完整化**，不是重写。
最小版证明的是「能自我维持」，但它只有 7 条命令、一层平铺的文件表、
无版本无依赖无签名的包表，状态全在内存里 —— 掉电即失，换台机器什么都带不走。

## 补的六件事

| | 最小版 | 这一版 |
|---|---|---|
| 文件系统 | 平铺名字表 | **层次化 VFS**：目录树 + 路径解析（绝对/相对、`.`、`..`） |
| shell | 7 条命令 | **24 条内建命令**、环境变量与 `$VAR`、`$?`、`#` 注释、`;` 多语句、未知命令响亮报错 |
| 包管理 | 装/列/跑/删 | 版本比较、**依赖拓扑 + 环检测**、**签名**（不是校验和）、pack/unpack、升级、拒绝降级 |
| 状态 | 只在内存 | **序列化写盘 + 清空 + 重建**的往返 |
| 跨运行 | 无 | 第二次启动自动进入 **restore** 模式 |
| 错误 | 一个 -1 走天下 | **12 个互斥负数码**，失败能说清是哪一类 |

## 实测（两端同一组数字）

ARM64（Unicorn 模拟器 + 自制 syscall 表）与 x86-64（真跑、真文件系统 `/mo`）
逐项一致，下面只列一份：

```
[sip vectors bad] = 0          SipHash-2-4 官方 16 个向量全对
[nodes] = 4                    根 + /mo + bin + etc
[write motd] = 14              [motd] = MO-USERSPACE-2
[pwd] = /mo/bin                cd 之后路径正确
[order] = liba,libb,app        依赖拓扑（后序）
[run liba] = 6                 [run app] = 42
[tampered] = -12               篡改代码 → 签名不符
[run app2] = 45                升级后（5*9），不是 42
[downgrade] = -8               降级被拒，[still run] = 45
[cycle] = -2                   依赖环被检出
[unpack] = 2 · [bad stream] = -12 · [app survives] = 45
[after clear files] = 0        [restored files] = 5 · [pkgs] = 3 · [envs] = 1
[files match] = 1              [pkgs match] = 1 · [run app after] = 45
[cmds run] = 9                 [unknown cmds] = 1
[rm non-empty] = -11           [rm again] = -1
```

**跨运行**（只有 x86-64 端能验 —— ARM64 端每次运行是新的内存 FS）：

```
第一次  [mode] init      → 真磁盘留下 state.db（331 字节）
第二次  [mode] restore   → [files]=5 [pkgs]=3 [envs]=1
                          [motd] = MO-USERSPACE-2 · [run app] = 45
```

## 判据为什么这样写

- **拓扑序断言的是整个串 `[order] = liba,libb,app`，不是逐行 grep。
  第一版分三行输出、`grep "^  -> liba$"` 逐个检查 —— M1 把后序改成前序后
  三条断言**全绿**，因为「liba 出现在输出里」和「liba 排第一」是两回事。
  改成一条顺序串之后 M1 立刻变红。**
- **签名不符（-12）与校验和不符（-6）分开**：前者报警、后者重传，
  混成一个码会让调用方做错动作。
- **`bad stream` 之后必须 `app survives = 45`**。只断言 -12 的话，
  一个「验签失败就把包删掉」的实现也能拿到 -12，但它同时把装好的包弄丢了。
- **`after clear files = 0`**：不清空就 load，读的是没清干净的残留，
  「重建成功」是自欺。
- **未知命令必须有计数**：否则 shell 静默吞掉错命令，解释器是假的。

## 本轮的真缺陷（都记下来，不粉饰）

1. **`vpath2` 拼出 `//mo/bin`** —— 根节点名字是空串，仍照加一个 `/`。
   长度、可读性都不报错，只有逐字节看才发现多一个斜杠。
2. **升级时手工打补丁改立即数，索引写成 7（正确是 6）** ——
   第二个 push 的立即数是 `code[6..9]`，改到 `code[7]` 得到 `9*256+7=2311`，
   于是 `5*2311=11555`。**数字看着完全正常**，只有和「期望 45」对照才暴露。
   现改为走 shell 的 `upgrade` 命令，不再手工改字节。
3. **`segpos(s, 0)` 恒返回 -1** —— 计数器 `c` 从 0 起、遇到 `|` 才自增，
   `c == 0` 永远不成立，于是第 0 段（MOPK2 魔数）取不到，`unpack` 恒失败。
4. **`sapp` 少写第一个参数** —— 编译器直接报 `too few arguments`（这条是
   被工具抓到的，不是我查出来的）。
5. **`runscript` 返回的 `NCMD` 是全局累计值** —— 直接打印会把 main 里之前
   执行过的命令混进来（17 而非 9）。改为取前后差值。
6. **验签失败时 `p_del` 会删掉已装好的包** —— 一个坏包进来，好包没了。
   改为先备份、失败则**还原**（原子性）。这条是本轮唯一的设计级改动。

## 变异验证 7/7 被捕获

| 变异 | 变红 |
|---|---|
| M1 拓扑改前序 | 1 |
| M2 环检测不置 CY | 1 |
| M3 升级不比较版本 | 2 |
| M4 执行前不验签 | 1 |
| M5 `sv_clear` 失效 | 1 |
| M6 unpack 不验签 | 1 |
| M7 验签失败不还原 | 1 |

其中 M1、M7 第一版**未被捕获**，原因都不是被测代码没问题，而是
**判据/变异设计错了**：M1 是判据只查存在不查顺序；M7 第一版把
`if had >= 0` 改成恒真，行为与原来一致。两个都修好后才变红。

变异脚本只跑 x86-64 端：ARM64 要过 Unicorn 模拟，7 × 完整两端会撞沙盒超时；
关键断言两端都有，完整两端对照由 `uspace2test.sh` 负责。

## 已知限制

- VFS 64 个节点、每文件 64 字节、名字 24 字节；包 16 个、代码 64 字节、
  依赖最多 4 个、环境变量 16 个 —— 超出返回明确负数码，不静默截断。
- 签名是**对称** MAC（SipHash-2-4 + 派生密钥），不是公钥签名：能验签就能签名，
  防不了持有密钥者自己作恶。真要不可抵赖得上 Ed25519。
- 签名段用**十进制**而非 hex：SipHash 是 64 位有符号值可能为负，
  墨语言没有无符号右移，转 hex 得手写二补数 —— 多一处位操作就多一处静默出错。
- 路径写死 `/mo`；启动脚本内嵌（模拟器无 stdin，交互式 REPL 无法端到端验证）。
- `cp` 只支持文件；`rm` 非空目录拒绝（不做递归删）。
- 未在真实安卓设备上跑过（SELinux 禁止应用域执行 `app_data_file`），
  ARM64 端是模拟器 + 自制 syscall 表。
