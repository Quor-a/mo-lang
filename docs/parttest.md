# parttest.sh —— 分批跑测试套件

## 为什么需要它

`tests/run.sh` 一次跑完 201 个用例，在沙盒里会因编译密集触发 502 中断 ——
**不是用例失败，是环境撑不住**。中断之后拿不到任何结论，既不能说通过也不能说失败。

所以把同一个口径切成小批，每批跑完立刻给出「通过 N / 失败 M」并进退出码。

## 用法

```bash
bash tools/parttest.sh 1 20     # 单文件用例 tests/*.mo，第 1~20 个
bash tools/parttest.sh dir      # 多文件用例 tests/*/（含 main.mo 的目录）
bash tools/parttest.sh err      # 编译错误用例 tests/errors/*.mo
```

三类加起来就是 `tests/run.sh` 的全量口径：

| 类别 | 数量 | 判据 |
|---|---|---|
| 单文件 `tests/*.mo` | 153 | 运行退出码 == 首行 `# expect:` |
| 多文件 `tests/*/` | 25 | 同上，入口是目录里的 `main.mo` |
| 编译错误 `tests/errors/*.mo` | 23 | 必须编译失败，且报错含 `# expect-error:` 片段 |

实测（v1.174.0）：**153 + 25 + 23 = 201 通过 / 0 失败**。

## 一个容易写错的坑

目录用例必须把 `main.mo` **改名**成 `test.mo`：

```bash
cp "$d"*.mo /tmp/mot/ && mv /tmp/mot/main.mo /tmp/mot/test.mo
```

编译器无参调用时只认 `test.mo`。漏了这步，25 个目录会**全部**报 `FAIL(编译)`，
25/25 全红 —— 看着像天大的回归，其实只是脚本少了一行 `mv`。

这个坑值得单独记：失败率是 100%，反而容易让人一开始就怀疑脚本而不是代码，
但如果当时真有另一个改动在手上，很容易把两者混在一起误判。

## 与 run.sh 的关系

`parttest.sh` 不替代 `run.sh`，只是它的**分批切面**：判据、临时目录规则（`/tmp/mot`）、
库文件来源（始终取 `lib/` 最新一份）都严格照抄 `run.sh`，不另立一套标准 ——
否则分批跑出来的"全绿"和整批跑的口径不一致，等于没验证。
