# a64ar —— 用墨语言写的 ar 归档器（自举 AArch64 工具链）

配套：`examples/a64ar.mo`（打包）、`examples/a64ld.mo` 的归档分支（按需抽取）、
`tools/a64artest.sh`（27 项断言）、`tools/a64armut.sh`（6 个变异）。

## 一、它补的是什么

`a64ld` 已经能把多个 `.o` 链成可执行 ELF，但命令行上必须**逐个列出每个文件**。
真实项目里库是**一包 `.o`**：链接器只把"真正被用到的"抽出来，没用到的留在归档里
**不进产物**。

ar 归档格式是 SVR4/GNU 的通用约定，`ar` 通常是 binutils 的一员 —— 本轮之前，
这条工具链上"库"这个概念是不存在的。现在：

```
a64as -r a.s  →  a.o ┐
a64as -r b.s  →  b.o ├─ a64ar → libx.a ─┐
a64as -r u.s  →  u.o ┘                  ├─ a64ld → sys.elf → 裸机执行
a64as -r m.s  →  m.o ───────────────────┘
```

## 二、ar 格式（SVR4 / GNU 通用）

```
全局头   "!<arch>\n"                                      8 字节
每个成员 60 字节头 + 数据 + 偶数对齐填充
  name[16]  mtime[12]  uid[6]  gid[6]  mode[8]  size[10]  fmag[2]="`\n"
```

两个最容易静默出错的点：

1. **size 是十进制补空格**，不是十六进制、也不是二进制。写成十六进制的话，
   size < 10 的文件恰好一样 —— 而 `.o` 永远超过 9 字节，所以真错的时候症状是
   "下一个成员头的偏移整体跑飞，读出来的 size 是天文数字"。
2. **成员数据按 2 字节对齐**，奇数长度补一个 `\n`。

本轮三个成员的长度**全都是奇数**（1939 / 1867 / 1875），所以对齐路径每步都走到 ——
如果恰好都是偶数，M3 / M4 这两个变异会失去覆盖。

## 三、实测（27 项断言，两端一致）

| | |
|---|---|
| 归档 | 3 个成员、5872 字节，头逐字段正确 |
| 抽取成员数 | **2**（a 与 b，不是 3） |
| 按需产物 | 搜不到 `ZZ-UNUSED` |
| 全量对照产物 | 搜得到 `ZZ-UNUSED`，且**更大** |
| 裸机输出 | `A` / `B` / `MO-AR` / `SYS OK` |

**"按需"必须有一条全量对照**：只验"产物里搜不到未使用成员"，可能只是字符串恰好
没写进去；只有"用别的方式链一遍就能搜到"才能证明判据本身有效。

## 四、坑

### ① 归档成员的数据偏移是 **68**，不是 60

头前面还有 8 字节 magic。测试脚本第一版写成 `d[60:60+size]`，取到的是头的尾巴，
`e_type` 与 `e_machine` 都是 0 —— 而同一脚本里负责走查成员链的循环用的是另一套
偏移（从 8 起），**两者不会互相暴露**，于是"头字段全对"和"成员内容全错"共存。

### ② **样本顺序**也是覆盖的一部分（M2 一开始没被捕获）

抽取循环**必须迭代**：抽出 a.o 之后，a.o 自己引用的 fnb 才变成 UNDEF。

第一版按依赖顺序归档（a 在前、b 在后），于是第一轮遍历里 a→b 恰好顺着遍历方向，
**不迭代的实现也能抽全** —— 变异改坏了代码，测试 27 项全绿。

改成**逆序归档**（b 在前、a 在后）后才被捕获（9 项变红）：

```
第一轮  m=0 b.o  fnb 还不是 UNDEF → 跳过
        m=1 a.o  fna UNDEF       → 抽出
第二轮  m=0 b.o  fnb 现在 UNDEF  → 抽出   ← 只有迭代才能走到
```

这和"样本量不够"是两回事：**顺序**本身就是覆盖条件。

### ③ AArch64 的 `bl` 覆盖 x30，非叶子函数必须自己存

`fna` 自己还要 `bl puts` / `bl fnb`，如果不先保存 x30：

```
bl puts  → x30 = "puts 之后"
bl fnb   → x30 = "fnb 之后"
fnb 内部 bl puts → x30 = "fnb 里 puts 之后"
fnb 的 ret → 跳回它自己的 ret 后面 → 死循环
```

症状是"打印完 A、B 就停住，后面的 MO-AR / SYS OK 永远不出来"，
**看起来像链接器把后半段代码弄丢了**，实际是调用约定没遵守。
叶子函数（如 `lib.s` 的 puts）不需要，非叶子必须存。

### ④ 墨语言的全局数据总量有上限（约 131072 个 i64）

给 `a64ld.mo` 加 `var ARB: [65536] i64` 之后，编译报：

```
test.mo:75:5: error: undefined symbol 'print' -- try: import 'io.mo'
        print("a64ld: ");
```

**报错指向用户代码，真因却是全局数据太大** —— `import` 进来的符号静默消失了。
二分实测：在本文件现有全局之外，`ARB` 最大只能开到 **26362**（+1 即失败）。

这个限制 v1.166 就遇到过（当时只记了"根因未定位"）。这次测出了边界，但**仍未修**：
本轮靠把 ARB 降到 16384（128 KB 归档容量）并在 `arload` 里显式报错绕开。
越界写进 ARB 会踩到别的全局，症状完全在别处 —— 必须先拦住。

## 五、变异验证 6 / 6

六个变异分别打在六条**不同**的因果链上：

| | 变异 | 失败项数 |
|---|---|---|
| M1 | 链接器不做按需（全抽） | 3 |
| M2 | 抽取循环不迭代 | 9 |
| M3 | 链接器不做偶数对齐 | 8 |
| M4 | 归档器不做偶数对齐 | 10 |
| M5 | 归档器 fmag 写错 | 4 |
| M6 | probe 恒为 0（一个都抽不出） | 9 |

M3 与 M4 是同一条规范的**两侧**（写与读），必须分别变异：只改一侧的话，
另一侧的正确实现会让走查仍然自洽。

## 七、已知限制

- 归档容量 128 KB、最多 16 个成员（超出**显式报错**，不静默截断）
- 无符号索引（GNU 的 `/` 特殊成员），查找是线性遍历全部成员
- 成员名按 GNU 短名风格（`foo.o/`），不支持长名 `/nnn` 形式
- 无弱符号、无 `.a` 嵌套
- 只处理 `SHT_REL` 的 `.rela`；`SHT_RELA` 之外不认
