# aio.mo —— 异步 I/O（epoll reactor + CSP 协程）

## 为什么必须有它

csp.mo 的协程**绑定**在 worker 上（makecontext 的 uc_link 写死该 worker 的
调度上下文）。因此任何一个协程做阻塞 read()，整个 worker 线程连同它上面
**所有**协程一起卡住 —— 有协程没 reactor，等于没有并发。

## 架构

- 一个**专用 poller 线程**跑 epoll_wait（不占 csp worker，也不改 csp_loop
  的死锁检测逻辑）
- 协程里 I/O 未就绪 → `aio_wait()` 注册 fd → `csp_park()` 挂起
- poller 收到事件 → `csp_enq(slot)` 把协程还给它的 worker

## 实测：高并发 HTTP 服务（examples/httpsrv.mo）

8 个 worker 协程、24 个并发客户端线程、每客户端 3 轮、每轮中途延迟：

```
mode=async  workers=8 clients=24 rounds=3 ms=210 nconn=72 req=72 bad=0 qovf=0 perr=0
```

理论下限 3 轮 × 最长延迟 ≈ 90ms，实测 210ms —— 说明 24 条连接确实在 8 个
协程上并发推进，而不是排队。

## 🔴 三个真坑（都不报错、不崩溃）

### 1. EPOLLONESHOT 会永久挂死

ONESHOT 是"投递一次即解除武装"。于是**任何一个事件被漏处理**（事件到达时
等待者刚好已释放）就等于这个 fd 永远不会再有事件 —— 协程永久挂起，不报错、
不崩溃，只是再也不动。

实测：ONESHOT 版本 2 客户端就卡死（req=2/4）。改成**电平触发 + 收到事件
立即 epoll_ctl(DEL)** 后，LT 下漏处理无害（fd 仍就绪，下次还会报），DEL
压住重复上报导致的空转。

### 2. epoll_data 高 4 字节带垃圾

`epoll_data.u64` 读回来高 4 字节不可信：实测读到 `2^32+1`，而写入的是 1。
改用 `epoll_data.fd` 惯用法 —— data 存 fd、读回时**只取低 32 位**，再按 fd
查等待者表。不依赖那 4 个字节是否干净。

### 3. 先 MOD 再 ADD，顺序不能反

ONESHOT 触发后 fd **仍留在** epoll 集合里，再 ADD 返回 EEXIST(-17)，注册
失败 → 协程永远等不到事件。改为先 MOD（未注册则 ENOENT）再 ADD，无需本地
维护"是否已注册"状态。

## A/B 的失败与教训

本轮想用"异步 vs 阻塞"的墙钟时间证明价值，**前两次都没测出差别**，原因都
值得记：

| 版本 | 结果 | 为什么没差别 |
|---|---|---|
| 延迟放在客户端、24 客户端 | blocking 189ms < async 210ms | 24 个客户端延迟同步，等待彼此重叠 |
| 客户端错开延迟、仍 24 个 | async 462ms ≈ blocking 440ms | 客户端数 24 > 协程数 8，服务器永远追不上，数据早已缓冲，没东西可等 |

**结论：只有当服务器容量 ≥ 并发客户端数时，等待才真实存在**，阻塞才付出
代价。这是 A/B 设计本身的坑，不是实现的坑。

## 🔴 v1.124：等待者表漏锁 —— 两个协程分到同一个槽

症状：约 1/5 概率程序永不退出（客户端卡在 tcp_recv，main 卡在 thread_join），
`req` 停在 71/72，不报错、不崩溃。

诊断不是靠猜，靠三条独立计数：

```
co 2 st=7 pk=11 wk=10     ← 挂起次数比唤醒次数多 1，且**没有任何等待槽**
```

每次 `aio_wait` 都在 park 之前把槽置上，槽只可能由 fire-hit 或 close 清掉，
而 close-hit 一次都没发生 —— 于是只可能是"槽被别人抢了"。

根因：`AIO_USED/FD/SL` 整张表**没有锁**。两个 worker 线程上的协程并发调用
`aio_wait`，会分到**同一个**空闲槽：

```
co A: USED[i]=1  FD[i]=FA  SL[i]=A  →  epoll_ctl(ADD, FA)  →  park
co B: USED[i]=1  FD[i]=FB  SL[i]=B  →  epoll_ctl(ADD, FB)  →  park   ← 覆盖掉 A
```

A 就此"带着一个不存在的槽"永久挂起。B 的事件到达时清掉槽、唤醒 B，A 永远
不再有人管。A 那个 fd 还留在 epoll 里，之后报上来也没有槽能对上 —— 表现为
`AIO_SKP` 增长，看起来只是"多了几个跳过事件"。

修法：整张表加 `AIO_LK`，并在**锁内**、park 之前宣告 `CSP_ST[s] = 7`。这个
顺序把"事件先于 park 到达"的窗口彻底关掉 —— poller 要么看到槽还没建（事件
被当 SKP，LT 下下次还会报），要么看到 ST 已是 7（直接入队唤醒）。

> 顺带删掉了 AIO_RDY 那套"准备-挂起"二次检查：加了锁之后那条路径**不可达**
> （变异验证：去掉它，15 次仍全绿）。留着不可达又测不到的代码，正是本项目
> 一直在批判的形状。

## 怎么验证

`tools/aiotest.sh`：编译 `examples/httpsrv.mo`，**重复跑 15 次**，每次都必须
服务完 72 个请求且无挂起。重复是必须的 —— 漏唤醒概率约 1/5，单次通过说明不了
任何事。脚本里还有一条守卫：确认示例确实 `import "aio.mo"`，否则测试会空转。

`tools/aiomut.sh`：变异验证。M1（去掉 `AIO_LK`）被稳定捕获；另两个窗口更窄的
变异未被捕获，如实记在脚本注释里，不假装它们通过。

## 已知限制（都没静默）

- 一个 fd 同时只允许一个协程等待，第二个返回 -2 并置 `AIO_PERR=1`
- 最多 128 个并发等待者
- ~~6 客户端配置下异步会挂住~~ —— v1.124 已修（等待者表漏锁）。
  实测 200 次 × 72 请求全部通过
- connect 仍是阻塞的；只做 read/write/accept
