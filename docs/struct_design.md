# 墨语言结构体设计

状态：已实现（阶段一 · 第 4 周）
日期：2026-10-08

## 1. 语法

```
struct Point {
    x: i64;
    y: i64;
}

struct Box {
    v: i64;
    w: i64;
}

struct Outer {          # 字段可以是另一个结构体（嵌套）
    a: i64;
    in: Inner;
    b: i64;
}

fn main() -> i64 {
    let p: Point;       # 局部结构体
    p.x = 3;
    p.y = 4;

    let a: [3] Box;     # 结构体数组
    a[0].v = 10;

    return p.x + p.y + a[0].v;
}
```

全局结构体：`var g: Pair;`（数据段零初始化）。

## 2. 内存布局

结构体字段按声明顺序紧密排列，每个字段 8 字节（当前所有标量都是 i64）。
嵌套结构体**内联展开**，不是指针。

| 场景 | 布局 |
|---|---|
| 局部结构体 | 栈帧内 `nfields*8` 字节连续，基址为 `off0 = P - 8*(n-1)` |
| 全局结构体 | 数据段内 `nfields*8` 字节，零初始化 |
| 结构体数组 | `n * size` 字节连续，`a[i]` 地址 = 基址 + `i * size` |

## 3. 类型表示

类型统一编码为一个整数：

| 值 | 含义 |
|---|---|
| `0` | i64（标量或数组元素） |
| `>= 1` | 结构体索引 `+ 1` |

存于 `O_STY[sym]`（变量类型）与 `O_STFT[si*32+fi]`（字段类型）。
字节步长由 `ty_size(ty)` 得出：`0 → 8`，否则 `8 * nfields`。

结构体表：

| 区域 | 内容 |
|---|---|
| `O_STN[si]` | 结构体名（intern 偏移） |
| `O_STF[si]` | 字段个数 |
| `O_STFLD[si*32+fi]` | 字段名 id |
| `O_STFT[si*32+fi]` | 字段类型 id |

上限：32 个结构体，每个 32 个字段。

## 4. 代码生成

字段访问统一走「先算地址，再决定要不要 load」：

```
field_chain(ty):
    rax = 基址                     # 由调用方先载入
    while 遇到 '.':
        si = ty - 1
        fi = st_field(si, name)
        rax += fi * 8              # 常量偏移，fi==0 时跳过
        ty  = st_field_type(si, fi)
    return ty
```

- 返回类型 `0`（i64 字段）→ 追加 `mov rax, [rax]` 取值。
- 返回类型 `>= 1`（结构体字段）→ `rax` 里是地址，供后续 `.` 继续展开。

赋值 `p.x = v` 走同一条路径拿地址，`push rax` → 算右值 → `pop rcx` → `mov [rcx], rax`。

### 下标换算

原来数组固定 `shl rax, 3`。支持结构体元素后步长可变，
改为 `imul rax, rax, imm32`（`48 69 C0 imm32`），步长由 `ty_size` 得出。

## 5. 实现中踩的坑（二）：全局结构体被当成局部

第一版实现时，`parse_let` 与 `parse_global` 的结构体分支用了同一段替换文本，
结果全局结构体也走了局部变量路径（`sym_add(kind=1)` + `K_CUROFF`），
在函数里访问全局结构体会生成 `lea rax, [rbp-8]` 而不是 `movabs rax, 0x10000000+off`，
运行即 SIGSEGV。

**只在 main 里用全局结构体不会暴露这个 bug**（main 的 rbp-8 恰好可写），
所以测试必须覆盖「全局结构体在非 main 函数中访问」→ 测试 25。

## 6. 已知限制

- **结构体不能按值传参**，只能传 `&s` 指针后用 `load64/store64` 手动读写。
  按值传参需要拷贝语义，留到类型系统阶段统一处理。
- **没有 `->` 运算符**，指针访问结构体字段要写 `load64(p + 8)`。
- **结构体不能整体赋值**（`a = b` 会报 `cannot assign a struct value`）。
- **结构体数组不支持初始化列表**，`let a: [3] Box;` 之后逐个字段赋值。
  （`i64` 数组支持 `let a: [4] i64 = 5;` 常量填充。）
- **结构体必须在使用前声明**。编译器是单遍的，不做前向类型声明。
- **不支持结构体初始化列表**，`let p: Point;` 之后字段逐个赋值。

## 7. 实现中踩的坑

`i64` 在词法上是**标识符**（kind 1），不是关键字。所以判断字段类型时，
必须先问「是不是 `i64`」，再问「是不是结构体名」，顺序反了就会把
`x: i64` 当成未知结构体报错。

同样的顺序问题在 `let` / `var` 的类型位置上也存在，三处都按
`tok_is("i64") → struct → 报错` 的顺序处理。

## 8. 回归

改动后跑 `bash verify_bootstrap.sh`，三个 Stage 产物 md5 必须一致。
注意 `src/compiler.mo` 本身不使用结构体语法，以保证 Stage0 汇编版 seed 仍能引导。


## ⚠️ 已知缺陷：局部结构体被静态分配（1.94 发现，未修）

第 2 节的表格写着"局部结构体 = 栈帧内 `nfields*8` 字节连续"，
但**实测局部结构体被分配在数据段**，与文档不符。

复现：

```mo
fn rec(n: i64) -> i64 {
    let p: Point;
    p.x = n;
    if n <= 0 { return 0; }
    let r: i64 = rec(n - 1);
    return p.x + r;      # 期望 n，实际被深层调用覆盖成 0
}
fn main() -> i64 { return rec(3); }   # 期望 6，实际 0
```

三条独立证据：

| 证据 | 结果 |
|---|---|
| 递归返回值 | 0（期望 6）；换成 `let p: i64` 得 6 —— 问题只在结构体 |
| DWARF DIE | `p` 是 `DW_OP_addr`（数据段），不是 `DW_OP_fbreg`（栈） |
| 机器码 | 函数体内**没有任何 `[rbp+off]` 访问**，全是绝对地址 |

每个声明点各有一个独立的数据段槽（不同函数里的 `p` 不串味），
所以只是"静态分配"，不是"变成全局变量"。但后果仍然严重：

- **递归 / 重入共享同一份存储**
- **多线程不安全** —— 而 1.54 的结论"局部变量天然线程安全"对结构体不成立

## 1.105 —— 嵌套结构体的布局（两个静默缺陷）

### 缺陷 ①：字段偏移按 `fi * 8` 算

原实现等价于"每个字段都占 1 个槽"。嵌套结构体字段占多个槽，于是它**后面**
的所有字段都被挤到前面去：

```
struct P { x: i64; y: i64; }
struct W { inner: P; b: i64; }

修复前：inner @0（2 槽），b 被算成 @8 —— 正是 inner.y 的槽
        w.inner.x = 1; w.inner.y = 2; w.b = 3;
        => 读回来 1 / 3 / 3   （正确是 1 / 2 / 3）
```

不崩溃、不报错、值还"看着合理"，是最难发现的一类错。

### 缺陷 ②：槽数用 `st_nfields`（只数直接字段）

```
struct W { inner: P; b: i64; }   nfields = 2，实为 3 个槽
```

局部变量/全局变量在数据段只留 2 个 qword，末尾字段写到相邻数据上。实测
`w.b = 3` 把字符串字面量的首字节写成 3、次字节写成 0（8 字节写的低 4 字节），
于是 `print("after\n")` 输出变空——**现象看起来像打印坏了，实际是内存被写穿**。

### 修法

| 用途 | 修复前 | 修复后 |
|---|---|---|
| 结构体大小 | `8 * st_nfields` | `8 * st_words`（递归展开） |
| 字段偏移 | `fi * 8` | `st_field_off`（逐字段累计） |
| 局部/全局槽分配 | `st_nfields` | `st_words` |
| 整体赋值拷贝词数 | `st_nfields` | `st_words` |

`st_words` 有深度上限 16，防结构体自引用导致无限递归。

DWARF 成员偏移（`.debug_info` 里的 `pos` 累加）与 `st_field_off` 必须是**同一套
规则**，否则调试器读到的字段和实际代码写的字段对不上。

### 验证

`tests/120_struct_layout.mo`（30 项）：嵌套在前/在中/三层嵌套、全局、相邻
byte 数组未被覆盖、字面量长度未被破坏、嵌套字段整体拷贝、结构体数组。

变异验证：把 `ty_size` 改回 `st_nfields`，`三层 mid.b` / `三层求和` /
`数组 a[0].b` 三项立即失败。

## 栈上数组基址：最后一个元素写到数组之外（1.106 修）

### 症状

```mo
let a: [3] W;      # W 含嵌套，24 字节
a[2].b = 9;        # 修复前：SIGSEGV（退出码 139）
```

- `a[1].b`、`a[2].inner.x/y` 都正常，只有最后一个元素的**最后几个字节**越界
- 数组前面还有别的局部变量时不崩，而是**静默篡改那个变量**

### 根因：栈槽是向上增长的

栈槽约定（从标量声明推出来的）：

- 变量 `off` 是它的**最低字节**，占 `[off, off+size-1]`（向上）
- 上一个变量占 `[p+8, ...]`（`p` 是本次声明时的 `K_CUROFF`）
- 声明后 `K_CUROFF = off - 8`，下一个变量占 `[off-8, off-1]`

所以数组的顶端最高只能到 `p+7`：

```
off + esz*n - 1 = p + 7    →    off = p + 8 - esz*n
```

原代码写的是 `p - esz*(n-1)`，**只在 `esz == 8`（i64 数组）时恰好等于正确值**。
`esz > 8` 时数组整体上移 `esz-8` 字节。

当数组是第一个局部变量时（`p = -8`），越界部分正好是：

| esz | 越界字节 | 盖到什么 | 后果 |
|---|---|---|---|
| 8 | 0 | — | 正常，所以 i64 数组从不暴露 |
| 16 | 8 | 保存的 rbp `[0,7]` | **静默**，通常不崩 |
| 24 | 16 | 保存的 rbp + 返回地址 `[8,15]` | **SIGSEGV** |

> 上一轮记录的推测是「元素大小 > 16 字节时不匹配」——**不对**。
> 真正的条件是 `esz > 8`；16 字节只是恰好没盖到返回地址才不崩。

### 修法

```mo
let off: i64 = p - esz * n + 8;     # 原：p - esz * (n - 1)
```

`K_CUROFF` 保持 `p - esz*n` 不变——它正好等于新的 `off - 8`，与标量规则一致。
`esz == 1`（byte 数组）的对齐分支也不变，因为 `off - 8 = p - n`，
与原表达式 `p - esz*n` 相同。

### 验证

`tests/121_stack_array_last.mo`（6 个场景）：

1. 数组是第一个局部变量，写最后一个元素的最后一个字段
2. 数组前有局部变量 → 那个变量不得被篡改（**静默**分支，靠这条守住）
3. 四元素逐个写满读回 → 元素之间不得重叠
4. 紧邻的后续局部变量不得被压到
5. `[3] i64`（旧公式在新旧两版下相同，守护别改坏小元素）
6. `[8] byte` 后跟 i64（对齐路径）

变异验证：把 `+ 8` 改回 `*(n-1)`：

- 场景 1 → 退出码 139（期望 0）
- 场景 2 → `m0` 从 111 变成 33（期望 111）—— **静默篡改被断言捕获**

### 为什么这个 bug 藏得住

它需要三个条件同时成立才崩溃：元素大小 > 16、**且**数组是第一个局部变量、
**且**写的是最后一个元素的最后几个字节。少一个条件就变成静默篡改或完全正常，
而静默篡改在只测「有没有崩溃」的用例里同样是绿的。
