# 保守式 mark-sweep 垃圾回收（`lib/gc.mo`）

## 它填补的是什么

评估表里「GC / ownership」此前是"手动 + arena"。本版补上真正的垃圾回收：

```mo
import "gc.mo";
fn main() -> i64 {
    gc_init();                      # 必须在 main 开头
    let p: i64 = gc_alloc(32);      # 分配
    ...
    gc_collect();                   # 回收
    return 0;
}
```

不改编译器、不改语言，纯库实现。

## 概念来源

Boehm-Demers-Weiser 保守式 GC。它在主流运行时里是经典方案，但
**没有主流框架把它做成可选库** —— 要么整个语言有 GC（Go / Java / JS），
要么完全没有（C / Rust / Zig）。这是做成可 import 库的动机。

### "保守"指什么

运行时不知道哪个 8 字节字是指针、哪个是整数，于是：

> 落在堆范围内、且确实指向某个块的字，一律当指针。

两类误差，本库都**量化**而不是含糊带过：

| 误差 | 后果 | 实测 |
|---|---|---|
| 误保留（整数恰好等于块地址） | 对象不回收 | 200 个全丢弃 → 剩 1（0.5%） |
| 内部指针（指向块中间） | 需查所属块 | 支持，整块保活 |

### 根集合

| 来源 | 怎么拿到 |
|---|---|
| 栈 | `/proc/self/maps` 求栈映射区间上界 |
| 数据段 | `/proc/self/maps` 求含 `0x10000000` 的区间上界 |
| 寄存器 | `setjmp` 保存到 `JB`（libc） |

⚠ 寄存器根依赖 libc 的 `setjmp` ⇒ **必须走 `molink`**。裸 moc 产物链接会
**明确报错**（undefined reference），不是静默少扫根。与 `csp.mo` 同类。

## 实测（`make gctest`，17 项）

| 场景 | 结果 |
|---|---|
| 10 块全可达 → collect | 10 存活，回收 0 字节 |
| 丢弃 5 个 → collect | 6（回收 4 个，1 个粘滞） |
| 1000 节点深链，只有 head 可达 | **1000** 全存活 |
| 深度 10 满二叉树，只有根可达 | **1023** 全存活 |
| 10000 次分配不回收 | live 10000，堆 1048576 |
| 同上、每 500 次回收 | live 2，堆 **262144**（一次都没再向内核申请） |
| 内部指针（只持有块内偏移） | 整块存活，内容完好 |
| 整数伪装成指针 | 对象被误保留（保守性，安全方向） |
| 局部变量持有的 8 个 | 全存活（栈根生效） |
| 200 个全丢弃 | 剩 1；再 collect 仍是 1 → **粘滞，不是泄漏** |

### 两条判据的分工

- **1000 / 1023**：证明标记**传播**生效。只扫根不传播的话是 1。
- **再 collect 仍是 1**：区分"误保留"与"每轮泄漏"。
  只看第一次的数字分不清这两者。

## 踩到的坑（三个都不报错）

### 一、数据段上界不能用 brk

链上 libc 之后，brk 已被推到 `0x36809000`，而数据段只占 `0x10000000`
起的一小段。按 `[0x10000000, brk)` 扫是**六百多兆，其中绝大部分未映射**，
一读就 SIGSEGV。

症状是段错误，看起来像"GC 坏了"，实际是根区间算错。
改为读 `/proc/self/maps` 求所属映射区间上界。

### 二、栈底不能用 `gc_init` 的局部地址

`gc_init` 是 main *调用*的，它的帧在 main **之下**。
于是区间 `[collect 帧, gc_init 帧)` 根本**不包含 main 的局部变量** ——
"栈是根"完全失效。

只表现为：局部变量持有的对象被静默回收。
改为从 maps 取栈映射区间的上界。

### 三、标记栈只清 `MSP` 个，等于一个都不清

`propagate()` 结束后 `MSP` 已经归 0，所以 `while i < MSP` 一次都不执行。
残留的块头在下一轮扫数据段时被当成根，**被回收过的对象又"复活"**：

```
GC 看起来从不回收，不报错
```

修法是清整段 `MS_MAX`。这个缺陷一度被另一个缺陷掩盖 ——
那时 `blk_of` 不认块头地址，MS 里存的正是块头，于是碰巧不命中。
**修好 A 反而暴露 B**，这是反复出现的模式。

## 变异验证（`make gctmut`）

只看"17 项全过"证明不了断言非空转。5 个变异全部被捕获：

| 变异 | 变红项数 |
|---|---|
| M1 去掉标记传播 | 3 |
| M2 清除判断取反 | 13 |
| M3 `blk_of` 只认块起始 | 6 |
| M4 不扫栈 | 1 |
| M5 标记栈只清 MSP 个 | 1 |

⚠ M4 / M5 各只有 1 项断言盯着 —— 捕获了，但冗余度低。
改这两处附近的代码时应先补断言。

## 已知限制

* **不移动对象** ⇒ 有外部碎片（非 copying / 非 compacting）
* **非增量、非并发**：`gc_collect` 是一次完整的 stop-the-world
* `blk_of` 是 O(块数) 线性查找（换二分需维护块索引，而块会分裂合并）
* 依赖 libc 的 `setjmp`
* 栈区间上界含 argv/envp ⇒ 那里若有"像指针"的字节也会误保留
* 块数上限 `BLK_MAX`、标记栈 `MS_MAX`，溢出置 `GCERR` 并**停止**，不静默

## 与 arena / heap 的关系

`arena`（整批丢弃）、`heap.mo`（malloc/free）都保留。它们不是"还没换完"：
`heap.mo` 提供确定性的手动释放，`arena` 提供零开销的批量生命周期，
GC 提供自动回收 —— 三种策略各有适用场景，且互为独立参照。
