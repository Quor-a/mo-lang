# 类：对标 C++ 的 class

版本 1.16.0（2026-10-09）

## 做法

**类 = 结构体（数据）+ 自由函数（方法）**。这正是 C++ 早期编译器
（cfront）的做法，也是在没有 vtable / 成员函数概念的语言里唯一现实的路径。

```mo
class Rect {
    w: i64;
    h: i64;
}

# 方法：形参声明成**类名**即 this 指针
fn Rect_area(self: Rect) -> i64 { return self.w * self.h; }

let r: Rect;
r.w = 3;
r.h = 4;
let a: i64 = Rect_area(&r);      # 12
```

## 已实现

| 能力 | 状态 |
|---|---|
| 类定义与字段（含 `byte`） | ✅ |
| **单继承**（字段内联） | ✅ |
| `this` 指针（形参写类名） | ✅ |
| 方法内 `self.field` 读写 | ✅ |
| 方法改状态对调用方可见 | ✅ |
| 派生类访问基类字段 | ✅ |

**继承采用字段内联**：基类字段复制在派生类前面，于是派生对象与基类
在内存上**前缀兼容**，向上转换天然成立。

```mo
class Shape { x: i64; y: i64; }
class Square : Shape { side: i64; }     # 布局：x, y, side
```

## 方法调用语法 obj.method(args)（1.43）

```mo
r.set(5, 6);        # 等价于 Rect_set(&r, 5, 6)
```

支持零参、多参、表达式参数、继承来的类。

### 🔴 上一版撤回的原因这次找到了

之前把语法糖放进 `parse_primary`，会破坏 token 流：
`parse_call` 消耗了右括号之后的 token，调用方再检查
`tok_is("=")` 判断"赋值还是表达式语句"时位置已经不对，
于是后续 `let a = ...` 的符号注册丢失。

**这次放在语句层**（`parse_stmt`），语句边界本来就在那里确定，
不存在"调用方还要再看一个 token"的问题。

### 但立刻撞上第二个坑：字段赋值被误判

`self.w = a;` 和方法调用 `r.set(5,6)` 都**以 `ident .` 开头**。

第一版先 `next_token()` 再判断、失败时用 `set_pos` 回退 ——
结果 **69_class.mo 直接编译失败**（syntax error 指向字段赋值）。

修法：**预扫描**（`peek_method_call`）—— 纯读字节判断后面是不是
`标识符 (`，不推进任何状态，就不需要回退。

> 需要回退的试探性解析，几乎总能改成"先判断再推进"。
> 回退要恢复的状态太多（行号、列号、token 缓冲…），极易漏。

### 第三个坑：expect("(") 写了两次

照抄 `parse_call` 结构时留了重复的 `expect("(")`，
于是零参方法调用把 `)` 当 `(` 期望 —— 报错正指向 `)` 那一列。

### 第四个坑：方法表已经废弃了

`method_find` 查的是方法表，但**方法登记早被移除**
（现在方法的函数名就是 `Class_method` 整体）。所以只能查符号表。

而 compiler.mo 是用 **seed** 编译的，seed 不支持局部数组/ptr/一元 `&`，
做不了字符串拼接 —— 所以不能拼出 `"Rect_set"` 再 `sym_lookup`。

**解法**：不拼接，改成**两段逐字节比较** —— 符号名是否以类名开头、
紧接着是不是 `_`、剩下部分是否等于方法名。全程只用字节读和 `streq`。

## 函数返回 ptr / 结构体 + 链式（1.44）

```mo
fn mk(a: i64, b: i64) -> Pair { ... return p; }
fn msg() -> ptr { return "hello"; }

mk(3, 4).sum();          # 链式
sfmt(&b, f"[{t}]");      # ptr 返回不用再写 ptr(t)
```

### 为什么之前只有 i64

结构体返回要按 System V 处理（≤16 字节走 RAX:RDX，更大走隐藏指针），
而所有返回值都塞 rax 最省事。代价是库函数只能返回 i64 —— 于是
`str_trim` 这类明明返回地址的函数，被 sfmt 当成数字打印
（只能靠 `ptr(v)` 绕过）。现在不用了。

### 三个坑

**1. 🔴 结构体返回必须走"变量"路径，不能用通用 parse_expr。**

结构体表达式在 rax 里留下的是**对象地址**（`load_sym` 对结构体取 lea），
而"地址"和"值"在生成的代码里都是 rax 中的一个数 —— 靠类型系统区分。
返回时要按值拷贝两字，必须明确知道基址。

所以限制成 `return <变量名>;`，返回别的东西**明确报错**。
第一版用通用 `parse_expr()` + 解引用，实测 `return 7;` 就把 7 当地址
解引用 —— 段错误。

**2. `rbx` 是栈顶缓存，不能用它做地址中转。** 用 `rsi`。

**3. 链式要先把值落到临时槽。** 返回值在 rax/rdx 里，而方法调用
需要**对象地址** —— 所以先存进一个新分配的 2 字槽，再用它当 this。

### 明确不做

- 字段数 > 2 的结构体返回（要走隐藏指针），明确报错
- `return <非变量>;` 的结构体返回
- **链式在循环里会让数据段线性增长**（每次链式分配一个新槽，
  编译期开销，不是运行期泄漏）

- **虚函数 / 动态分派**：没有 vtable
- 构造/析构函数：无 RAII 语义
- 访问控制（public/private）：符号表是扁平的
- 多继承、运算符重载、模板

## 关于方法调用语法 `obj.method()`

做过，但**撤回了**。

实现放在 `parse_primary` 里（试探读两个 token：`.` + ident + `(`）。
它能正确生成 `Class.method(&obj, ...)`，但会**破坏 token 流**——
后续 `let a = ...` 的符号注册丢失，报 `undefined symbol 'a'`。
另外方法表版本会让编译器**段错误**（`intern` 传入的偏移在拼接后失效）。

根因未定位，代价超过收益，所以撤回，改用 C 风格显式 this。
**撤回的代码与原因都记在这里**，不是假装没发生过。

替代写法完全够用：

```mo
Rect_area(&r)          # 而不是 r.area()
```

## 一个真实的 bug：ptr 变量的字段寻址

`field_addr` 原本无条件对形参取 `lea`（取形参槽地址）。
对结构体变量这没错，但对 **ptr 变量**就错了——ptr 的**值**才是对象地址。

```mo
fn field_addr(sy: i64) -> i64 {
    if ty_kind(sym_type(sy)) == 4 {
        load_sym(sy);              # ptr：取值
    } else { ...lea... }           # struct：取址
}
```

少这个分支时 `self.w` 读到的是"形参槽里值的高位字节"，
输出一堆天文数字然后段错误。

## 顺带修好的

`field_chain` 此前只接受结构体类型。现在 **ptr→struct 也能用 `.`**
（对标 C 的 `->`），这是 `self.w` 能工作的基础。

## 实战检验：wavobj.mo

`examples/wavobj.mo` 是 `wavinfo.mo` 的面向对象版 —— 同一份 WAV
解析逻辑，一个用 8 个全局变量（`CHANNELS` / `RATE` / `BITS` …），
一个用 `class Wav` + 方法。

```mo
let w: Wav;
if w.parse(argv(1)) < 0 { err_print(); return 1; }
w.describe(&OUT + strlen(&OUT));
```

验证方式（`tools/wavobjtest.sh`）：两个**独立实现**在同一份真 WAV
上跑，去掉 file 行后**逐字节比对**。另含三条错误路径
（文件不存在 / 坏魔数 / 退出码）与关键字段抽查。

单元测试只能证明方法语法"能跑"，两个实现输出一致才说明"结果对"。
