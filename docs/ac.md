# ac —— Aho–Corasick 多模式匹配自动机

`lib/ac.mo`，测试 `tests/145_ac.mo`（43 项断言），基准 `examples/acbench.mo`，
变异验证 `tools/acmut.sh`（5 个变异全部被捕获）。

## 概念来源

Aho & Corasick 1975（CACM 18(6)）"Efficient string matching: an aid to
bibliographic search"：goto / failure / output 三函数，构造 O(m)、扫描
O(n+z)，**与模式个数 k 无关**。

主流标准库一个都没有：Python 靠 pyahocorasick、Rust 靠 aho-corasick crate、
Go 靠 cloudflare/ahocorasick —— 全是第三方。

### 与 SAM / regex 的分工（不是替代）

| | 预处理什么 | 单次代价 | 回答什么 |
|---|---|---|---|
| `regex.mo` | 模式（Thompson NFA + Pike VM） | O(n·m) | 这个正则匹配吗 |
| `sam.mo` | **文本** | 查询 O(m) | 这个串是文本的子串吗 |
| `ac.mo` | **模式集合** | 扫描 O(n+z) | 这些模式在文本哪里 |

## 数据结构

转移用稀疏链表（稠密表要 |states| × 256，本规模下装不下），代价是
转移查询 O(出度) 而非 O(1)。

输出链表节点**共享**而不是复制：BFS 序保证处理 v 时 `fail[v]` 的链表已
定稿，且此后每个节点的 next 至多再被写一次（只有"该状态自己有输出时才写
自己链表的当前尾"）。复制的话最坏 |states| × |P| 个节点，装不下。

## 实测（`examples/acbench.mo`）

### 核心性质：AC 与 k 无关，朴素随 k 线性

固定 n=1000，字母表 a–d，模式长 2–3：

| k | AC 查询次数 | 朴素比较次数 | 倍率 |
|---|---|---|---|
| 4 | 2904 | 5166 | 1.7 |
| 8 | 2970 | 10166 | 3.4 |
| 16 | 2898 | 20536 | 7.0 |
| 32 | 2944 | 40489 | 13.7 |
| 64 | 2996 | 82085 | 27.3 |

**k 涨 16 倍，AC 查询数 2904 → 2996，变化不到 4%**；朴素 5166 → 82085，
涨 15.9 倍。这就是 O(n+z) 与 O(n·k·|p|) 的差别被钉成数字。

固定 k=16，n 变化时两边都线性，斜率差一个量级（AC ≈ 2.9n，朴素 ≈ 20.5n）。

### 均摊 O(n)

failure 回退总次数 `AC_NFB` ≤ 文本长度：每读入一个字符最多让深度 +1，
每次回退让深度严格减小且深度不为负 ⟹ 回退总次数 ≤ 前进总次数 ≤ n。
实测 n=1000 / k=64 时回退 998。这条被写成断言（20 组随机用例逐组检查）。

### 经典用例

`{he, she, his, hers}` × `"ushers"` → 3 个匹配：she@1、he@2、hers@2。
状态 10、边 9、回退 1、合并写 1。

## 🔴 本轮的三个真坑

### 一、插入排序用 `j = -1` 当退出标志 → 同一位置的 pid 全部退化

第一版 `ac_emit` 用插入排序把同一位置的 pid 排成升序，退出时把 j 设成 -1，
于是收尾那句 `AC_TB[j+1] = x` 落到**位置 0**，把原值覆盖掉。

实测：模式 `{\xc8\xe4, \xe4}` 扫 `"\x01\xc8\xe4\x02"` 应得 pid 0 与 pid 1，
实得**两个 pid 1**。不报错、不崩溃，只是 pid 全变成同一个。

改选择排序：不做元素搬移，就没有"退出时 j 已被改写"这回事。

### 二、AC 的输出顺序天然按「结束位置」，不是起始位置

第一版只记起始位置，于是同一结束位置上的短模式（起始更靠后）会让序列
在起始位置上**回退**，看起来像乱序。这不是 bug 而是 AC 的固有顺序，
已改成同时记录 `AC_ME`（结束位置）与 `AC_MP`（起始位置），并把
"end 单调不减"本身写成断言。

朴素暴力也按 (end 升序, pid 升序) 枚举，两边才能逐项比对。

### 三、BFS 是输出合并必需的，不是 failure 链必需的 —— 一条被推翻的预期

第一版注释写着"必须 BFS：DFS 会让 `fail[fail[v]]` 尚未确定"。
变异 M3（队列改 LIFO，即 DFS）实测推翻了它：

- **failure 链**：`ac_fchild` 只依赖 `AC_FL[v]`，而 v 是 u 的父，父必在
  子之前处理 ⟹ **DFS 下 fail 链依然正确**，专门的"fail 定义性质"断言
  （逐个状态验证 fail[v] == 最长且仍在 trie 中的真后缀）**全过**。
- **输出合并**：`ac_merge(v)` 依赖 `AC_FL[v]` 的链表**已合并完**，这要求
  按深度递增处理 ⟹ 只有 BFS 满足。M3 挂的正是"随机对照不一致组数"（3 组）。

注释已改成实际成立的版本。

### 四、变异脚本的"未捕获"是假阳性：写入不可见

`apply_mut` 写入变异后立即 `cp` 到测试目录，读到的却是**旧内容** ——
沙盒文件系统有写入可见性延迟。于是"变异没生效"被误报成"变异没被捕获"：
M2 手动应用时测试挂 6 项，脚本里却全过。

修法是写入后**立刻读回校验**（`bad not in reread` 就报 `WRITE-INVISIBLE`），
外加 `sync`。这个失败模式比"测试空转"更隐蔽：它让验证脚本**假装验证了**。

另有一次自愈方向错误：M5 的变异串 `let t: i64 = AC_TB[i];` 是干净串的
子串，反向替换把干净的三行又扩成五行（交换语句重复两遍），基线直接
failed 4。已把 M5 的变异串改成完整三行。

## 变异验证（`tools/acmut.sh`）

| 变异 | 结果 |
|---|---|
| M1 failure link 恒 0 | 7 项红 |
| M2 不做输出合并 | 6 项红 |
| M3 BFS 队列改 LIFO(DFS) | **1 项红**（冗余度薄，见下） |
| M4 失配直接回根 | 3 项红 |
| M5 同位置 pid 不排序 | 6 项红 |

⚠ **M3 只挂 1 项**：这轮补了"输出合并定义性质"断言（状态 v 的输出集合
应恰好等于 v 串的所有后缀里正好是模式的那些）后，M2 从 5 项升到 6 项，
但 M3 仍是 1 项 —— 该固定模式集在 DFS 下碰巧合并顺序仍对。改 `ac_build`
前应先补针对 M3 的断言。

## 已知限制

- 状态 ≤ 2100、边 ≤ 4200、模式 ≤ 64、匹配 ≤ 8192、输出节点 ≤ 512
- 模式总长 ≤ 4200；单模式长度不限但受状态上限约束
- 只处理字节，不按码点切分（UTF-8 串按字节匹配，跨码点边界不特殊处理；
  需要码点语义请先过 `lib/utf8.mo`）
- 一个模式重复插入会各自算一个 pid（不去重）
- 未做 `ac_reset`（重新用一批模式请 `ac_init()`）
- 匹配表满时置 `AC_ERR=4` 并返回 -1，不静默截断
