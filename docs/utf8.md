# UTF-8 位并行（SWAR）校验 —— `lib/utf8.mo`

## 概念来源

Muła / Kurz / Lemire，《Validating UTF-8 In Less Than One Instruction Per Byte》，
*Software: Practice and Experience* 48(5), 2018。

论文的载体是 SIMD。**这里实现的是它的 SWAR 变体**：把 8 个字节装进一个 `i64`，
用几次移位把「哪些字节必须是后续字节」一次性铺开，再与实际的后续字节做一次
异或。不需要任何 SIMD 指令，纯整数运算。

为什么算「概念」而不是「工程惯例」：主流标准库里的 UTF-8 校验至今大多是
Höhrmann 的标量 DFA（逐字节查表）——glibc、Go 1.18 之前、Python、多数嵌入实现
都是。SWAR/SIMD 版近几年才进 Rust / Go 1.19+，且都绑死在 SIMD 指令上；没有
SIMD 的环境只能退回逐字节。本实现证明：不绑 SIMD 也能位并行。

## 三条移位做了什么

```
x      = 8 个字节（byte j 占 bit 8j..8j+7）
a      = x & M80            → 每字节的 bit7（非 ASCII）
s1..s4 = (x<<1..4) & M80    → 把 bit6/bit5/bit4/bit3 搬到 bit7 位置
lead   = a & s1             → bit7、bit6 都置 = 前导字节（11xxxxxx）
cont   = a & (s1 ^ M80)     → bit7 置、bit6 清   = 后续字节（10xxxxxx）
l3     = lead & s2          → 1110xxxx / 11110xxx（长度 ≥ 3）
l4     = l3 & s3            → 11110xxx          （长度 = 4）
bad    = l4 & s4            → 11111xxx          （长度 ≥ 5）
```

期望的后续字节位置：

```
exp = (lead << 8) | (l3 << 16) | (l4 << 24)
```

前导字节在位置 `j` 时 bit7 落在 `8j+7`；左移 8 位正好落到 `8(j+1)+7`，即下一个
字节的 bit7。**三次移位分别对应「需要第 1 / 2 / 3 个后续字节」**。
于是 `cont ^ exp` 的每一位就是一处不一致：

| 情况 | 含义 |
|---|---|
| exp 有而 cont 没有 | 序列被截断 |
| cont 有而 exp 没有 | 孤立后续字节 |

## 范围检查也是位并行的

越长编码、代理对、超上界这几条，全部能化成「第一个后续字节的 bit5 / bit4」：

| 前导 | 要求 | 位条件 |
|---|---|---|
| `E0` | 后续 ≥ 0xA0 | bit5 = 1 |
| `ED` | 后续 ≤ 0x9F（排除代理对） | bit5 = 0 |
| `F0` | 后续 ≥ 0x90 | bit5 或 bit4 |
| `F4` | 后续 ≤ 0x8F | bit5、bit4 都为 0 |

「某字节等于常数」用 SWAR 零字节检测：`haszero(x ^ broadcast(k))`，
其中 `haszero(v) = (v - 0x0101..01) & ~v & 0x8080..80`。
借位会传到更高位字节，但那只会把一个 ≤0x7F 的字节减 1，bit7 仍为 0，
不产生假阳性。

## 跨块

序列可以跨 8 字节边界，最多延伸 3 个字节。块末把「下一块前 3 个字节必须是后续
字节」记进 `U8NEED`，下一块并进 `exp`。四种特殊前导字节（`E0/ED/F0/F4`）若落在
本块最后一字节，它们的范围要求也要带过去（`U8XE0..U8XF4`）。

输入结束时 `U8NEED != 0` 即序列被截断。

## 实测

| 检查 | 规模 | 结果 |
|---|---|---|
| 已知向量 | 26 条（越长 / 代理对 / 超上界 / 孤立 / 截断 / 跨块） | 全对 |
| 穷举 | 21 个边界字节值⁴ × 两个偏移 = **388962** | 与参照实现 0 处不一致 |
| 随机长串 | 20000 串，长度 1..24 | 0 处不一致 |

穷举里 **偏移 5 是关键**：4 个字节落在 byte5..byte8，跨过 8 字节边界，
五个跨块状态全被覆盖。只在偏移 0 上穷举的话，跨块逻辑一行都不会被执行到。

合法样本占比：穷举 1616 / 388962（0.42%），随机 415 / 20000。
**这两个数必须 > 0** —— 若样本全是非法，比对恒等，测试形同虚设。

## 交叉验证

`u8_ref()` 是刻意写成与 SWAR 版完全无关的逐字节状态机（Unicode Table 3-7 形式）。
两条独立路径给出同样结论，结论才可信；只跑一条证明不了什么。
这与 1.79 的教训一致：两种模式共用局部导数时，一致性检验会放行同类错误。

## 变异验证

`make utf8mut`：

| 变异 | 结果 |
|---|---|
| M1 去掉全部范围检查 | 被捕获（15 项变红） |
| M2 去掉跨块续接 `U8NEED` | 被捕获（11 项） |
| M3 去掉特殊前导跨块 `U8XE0` | 被捕获（1 项） |
| M4 去掉收尾截断检查 | 被捕获（2 项） |
| **M5 去掉 `bad`（11111xxx）检查** | **未被捕获** |

M5 是刻意保留的「预期不被捕获」：`bad` 检出的是 0xF8–0xFF，而
`l4 & ~{F0..F4}` 的范围检查覆盖 0xF5–0xFF，**前者是后者的子集，完全冗余**。
把它写出来是为了说明：”改了代码却没变红“这件事本身也要被看见，而不是被挑掉。

## 三个坑

**一、`var` 初始值不接受表达式。** 墨语言的 `var X: i64 = 0 - 1;` 与
`= -1;` 都是语法错误（只接受非负整数字面量）。三个常数改到 `u8_init()` 里算，
`u8_valid` 每次调用；**直接调 `u8_block` 的人必须自己先调一次 `u8_init`**。

**二、`>>` 是算术右移。** 取位 63 时若该位为 1，`v >> 63` = -1，`& 1` 仍得 1；
取位 47 / 55 同理不受符号扩展影响。但**不能**用 `>>` 做无符号移位。

**三、随机样本的分布会决定测试是否空转。** 一开始用纯随机字节，20000 串里
合法数为 0，比对全部恒等 —— 测试全绿却什么都没验。改成一半边界值、一半随机
字节后合法数才变成 415。

## 已知限制

- `bad` 检查冗余（见 M5），保留只是作为廉价提前退出
- 只做校验 / 解码 / 编码，**没有**大小写转换、归一化（NFC/NFD）、字符分类
- 码点按标量值处理，不做组合字符与字素簇切分
- 解码失败返回 -1，不区分失败原因
- `u8_valid` 每次调用都会重算三个常数，热路径上应先调一次 `u8_init` 再用
  `u8_block`
