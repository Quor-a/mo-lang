# mokern64 —— 自举内核跑在 ARM64 上

## 它证明什么

`mokerntest` 只证明「墨语言能造内核」：生成器 `examples/mokern.mo` 编译成
**x86-64** 程序，产出 ARM64 裸机内核。生成器的**运行架构**与产物的目标架构
不是一回事。

`mokern64` 补的是这一半 —— 生成器自己也是 **ARM64 程序**：

```
examples/mokern.mo ──mo2x cfs-aarch64 + zig──> ARM64 静态 ELF（生成器）
                                                  │ 跑在 Unicorn 模拟的 ARM64 CPU
                                                  ↓ 写文件
                                           kern.arm.elf（3414 字节）
                                                  ↓ kern64run.py（裸硬件：无 Linux/libc/安卓）
                                 MO-KERN / U OK / PF2 / DONE
```

四段闭环，每一段都是下一段的输入。判据 21 项，变异 7/7。

## 判据为什么这么定

| 层 | 判据 | 专门盯住什么 |
|---|---|---|
| ① | 生成器 e_machine=183、无 .interp | 交叉后端没生效（产物还是 x86） |
| ② | x86 端同源码真跑 | 参照端，用于比对 |
| ③ | 两端统计输出一致 + **非空守卫** | 两边都是空串也会"相等" |
| ④ | 两端产物 md5 相同 | 交叉后端算得不一样 |
| ④b | **静态解析三条页表描述符的 AP 依次 01/01/00** | 执行层看不见的缺陷（见下） |
| ⑤ | ARM64 产物在裸机启动，输出逐行比对 | 两端一起错时 md5 照样相同 |
| ⑤b | ksp / usp / svc / eret 逐一核对 | 内核状态是内核自己设的，不是模拟器默认 |
| ⑥ | 关掉 --mmu 后 PF2 必须消失 | 隔离不是程序自己的功劳 |
| ⑦ | 缺参数时不产出 | 静默"成功" |

### 🔴 ④b 是被 M5 逼出来的，不是预先设计的

M5（不建内核私有块描述符）让 EL0 访问变成**转换错误**而非权限错误，而内核
的 abort 处理不区分两者，照样打印 `PF2`。于是**裸机输出逐字不变，21 项里
19 项全过**：执行层对 M5 完全失明。

能抓到它的只有静态解析 —— 它比对的是**镜像自身的字节**（描述符的 AP 位），
不是"它跑出什么"。这再次说明：执行层判据再密，也覆盖不了"改了不影响输出"
的那类缺陷。

## 🔴 变异脚本第一版给出假的「7 捕获 / 0 未捕获」

`mokern64mut.sh` 沿用了 `mokernmut.sh` 里的判据字符串 `"失败 0 项"`，而
`mokern64.sh` 输出的是 `"19 通过 / 0 失败"` —— 两边**对不上**，于是每一个
变异都被判成"被捕获"，包括 M5 这种实测 19 通过 / 0 失败（＝真没抓到）的。

这类失效比"测试空转"更危险：空转只是不说话，它**主动给出漂亮分数**。

改成 `grep -qE '/ 0 失败$'` 后才暴露真实结果：6 捕获 / 1 未捕获。
（也不能只 grep `"0 失败"`：`"10 失败"` 里同样含它 —— v1.164 记过同一个坑。）

## 顺带修掉的：android_native.sh 不建输出目录

`android_native.sh app.mo out/app` 在 `out/` 不存在时，zig 报
`unable to open output directory ... FileNotFound`，接着脚本打印"构建失败" ——
失败原因是**路径没建**，不是源码有问题。已加 `mkdir -p $(dirname "$OUT")`。

## 🔴 已知限制：`make mo2x` 目前会失败

这一条必须说清楚，它阻塞了两件事。

**现象**：`tools/mo2x.mo`（2845 行）用当前 `bin/moc` 编译时报
`no main function`，没有语法错误。

**最小复现**：

```
var A: [524288] byte = 0;
var B: [1048576] byte = 0;
var C: [200000] i64 = 0;
fn main() -> i64 { return 7; }        →  no main function
```

去掉 `C` 就能编过。阈值在全局数据总量 **1.5MB ~ 3.1MB** 之间。

**根因**：编译器内部是一套**裸偏移的分区**（`src/mo/compiler_part1.mo`）：

```
O_DATA  = 5242880
O_NAMES = 6291456     ← 数据区只有 1048576 字节（1MB）
O_SYN   = 6815744     ← 符号名区
```

全局数组的初始化数据写进 O_DATA，超出 1MB 就写进 O_NAMES，把符号名冲掉 ——
`main` 的名字没了，最后报 `no main function`。报错指向"缺 main"，与真因
（全局数据太大）毫无关系。

**一次失败的扩容尝试**：把所有 ≥ O_NAMES 的偏移整体 +15MB（82 个常量），
并把堆从 96MB 提到 130MB。结果 `make boot` 时 `./moc1` **段错误**。原因是
源码里还有硬编码的分区假设没同步（例如 `compiler_part1.mo:296` 写着
"100663296 字节…故 91000000 之后安全"）。分区平移是架构级改动，需要逐处审计，
**这一轮没有完成，已回退**（自举恢复 `339d937d…`）。

**它阻塞什么**：

1. `make mo2x` —— 全新环境里 `make mokern64` 会挂在重建 mo2x 上。
   发布包里带 `bin/mo2x`（可用），所以解包后直接跑不受影响；
   但只要 `tools/mo2x.mo` 比 `bin/mo2x` 新就会触发重建并失败。
2. **把墨语言编译器本身交叉编译到 ARM64** —— `bin/mo2x` 是旧产物，
   内部 SRC 上限仍是 131072；翻译 `src/compiler.mo`（346889 字节）时
   在第 3622 行撞上缓冲边界：

   ```
   mo2x: src/compiler.mo:3622: expected operator at '<eof>'
   ```

   v1.179 曾把 `SRC` 上限改到 524288 —— 但**那个改动从未生效**：
   带它的 `mo2x.mo` 正是现在编不出来的这个版本。上一轮把它当成已完成的
   修复上报，是不对的。

## 验证

```
bash tools/mokern64.sh      21 通过 / 0 失败
bash tools/mokern64mut.sh   捕获 7 个，未捕获 0 个
make boot                   三级一致 ✅ 339d937d…（编译器未改）
```

解包后（保留包内 `bin/mo2x`）跑 `bash tools/mokern64.sh`：21/0、7/7 复现。
