# fmath —— f64 数学库

`lib/fmath.mo`，**不依赖 libc**：全部用 f64 四则运算 + 位操作实现。

```mo
import "fmath.mo";
fm_sqrt(x)  fm_exp(x)  fm_log(x)  fm_log2(x)  fm_log10(x)
fm_sin(x)   fm_cos(x)  fm_tan(x)  fm_pow(a,b) fm_hypot(a,b)
fm_floor(x) fm_ceil(x) fm_round(x) fm_trunc(x) fm_fmod(a,b)
fm_isnan(x) fm_isinf(x) fm_isfinite(x) fm_signbit(x)
fm_nan()    fm_inf()   fm_fabs(x)  fm_copysign(x,y)
fm_ldexp(m,e)   fm_exponent(x)      # 位操作实现的 2^e 缩放
```

## 为什么自己实现

墨语言此前只有 f64 的 `+ - * /` 与比较。调 libc 当然也能有，但那要链接器、
要 PLT，而且**不是自己的实现** —— 行为不可预测，误差无从测起。
自己实现的好处是每个函数的误差都可测、可断言。

## 依赖的两个内建

| 内建 | 作用 |
|---|---|
| `fbits(x)` | 取 IEEE754 位模式（不转换） |
| `ffrombits(x)` | 位模式 → f64（不转换） ← 1.114 新增 |

有了后者才能做 `ldexp`：改指数字段即可乘 `2^k`，不需要循环乘
（`1e300` 时循环要跑 500 次）。

## 精度口径：ULP，不用相对误差

与 Python（C library，正确舍入）算**同一批输入**，误差用 **ULP** 表示
（位模式在 total order 下的整数距离）。

相对误差在接近 0 处会失真、跨 0 时甚至无定义 —— 那会把真正的算法误差
和"口径问题"混在一起。

`tools/fmathtest.sh`（2200 个测试点，LCG 生成，两边序列逐位一致）：

| 函数 | 最大 ULP | 平均 ULP | 阈值 |
|---|---|---|---|
| sqrt | 1 | 0.27 | 2 |
| exp | 1 | 0.06 | 2 |
| log | 1 | 0.28 | 2 |
| log2 | 2 | 0.39 | 2 |
| log10 | 3 | 1.26 | **4** |
| sin | 1 | 0.20 | 2 |
| cos | 1 | 0.14 | 2 |
| floor / ceil / round | 0 | 0.00 | 2 |
| hypot | 1 | 0.61 | 2 |

`log10` 阈值单独给 4 而不是统一 2：它是 `log` 的派生，
`log` 的 1 ulp + `1/ln10` 的表示误差 + 乘法舍入，实测 3 ulp 是合理的。
**统一阈值会逼着把"合理的派生误差"伪装成通过。**

## 🔴 范围规约：一个被当成"已知限制"藏起来的 bug

`tools/fmathrange.sh` 测 sin/cos 的误差随 `|x|` 的变化。

**第一版实测**（看起来完全符合"理论预期"）：

```
2^0            1 ulp
2^6         2047 ulp
2^13       16114 ulp
2^21    48850774 ulp      ← 约 1e-8 绝对误差
```

误差随 `|x|` 单调增长，于是当时写进了"已知限制"：
> "这是单 double 表示 π/2 的固有损失，glibc 靠 Payne-Hanek 多精度解决，本库未做。"

**这是错的，是 bug。**

根因在 `fm_pio2_hi()`：用的是 **π/2 的最近双精度值** `0x3ff921fb54442d18`，
53 位全有效。范围规约要算 `k·(π/2)`，`k` 在 `|x|=2^21` 时约 1.34e6 ——
`53 + 21 > 53`，**这个乘积不精确**，舍入误差 `≈ ulp(2e6) ≈ 4.7e-10` 直接
进归约结果。

正解是 fdlibm 的**低位清零分裂**：

```
pio2_hi = 0x3ff921fb54000000   低 24 位清零，只有 28 位有效
pio2_lo = 0x3e110b4611a62633   残差 ≈ 9.92e-10
```

`k·pio2_hi` 在 `k < 2^25` 时**精确**（28 位 + k 的 25 位 ≤ 53）。
实测 `k` 从 1 到 `2^21` 逐点精确。

**修复后**：

```
2^0            1 ulp
2^6            1 ulp
2^13           1 ulp
2^21           1 ulp    ← 从 48850774 降到 1
```

8 个量级全部 ≤1 ulp。

### 这条教训值得单独写

1. **"已知限制"是 bug 最好的藏身处。** 看到误差随某个参数增长，
   先问"这是不是能修的"，再决定记不记。
2. **验证脚本的判据会把 bug 的特征固化成"正确特征"。**
   第一版 `fmathrange` 的判据是"误差必须随 `|x|` 单调增长" ——
   修好之后它反而**红**了。判据必须跟着反过来：
   现在要求**所有量级都 ≤2 ulp（平坦）**，一旦冒上去就说明退化成了旧行为。

## NaN 参与的比较（编译器级，1.114 修）

f64 比较走 `ucomisd` + `setcc`，但裸 `setcc` 在 **unordered**
（任一操作数为 NaN，此时 `ZF=PF=CF=1`）下给出：

| 指令 | 裸结果 | 应为 |
|---|---|---|
| `sete`（==） | 1 | **0** |
| `setne`（!=） | 0 | **1** |
| `setb`（<） | 1 | **0** |
| `setbe`（<=） | 1 | **0** |

于是 `x != x` 这个**最惯用的 NaN 判据恒为假**。

不报错、不崩溃，只是所有 `isnan` 检测、排序、最值、断言**静默失效**。
实测修复前六个比较里四个是错的。

修法是 unordered 时的 `setcc` 结果取反（`tests/126_fmath.mo` 逐条盯）。

## 浮点字面量 8 位截断

编译器解析浮点字面量时**小数最多 8 位**，超出就静默截断：

```
0.693147180559945309...  →  0.69314718     相对误差 1e-9
```

对数学库是灾难性的，而且不报错，只是结果悄悄不准。

**本库的做法是绕过**：所有常量一律用 **IEEE754 位模式**构造
（`ffrombits`），精度与 C 库一致。

⚠️ **编译器本身没修，仍是已知限制。** 未修是因为墨语言有**两套编译器实现**
（`src/compiler.mo` 与汇编 seed `src/asm/`），只改一处会破坏自举三级
字节一致。绕过不等于修好 —— 用户写 `0.693147180559945` 仍会得到截断值。

## 已知限制（实测）

- sin/cos 在 `|x| ≤ 2^21` 全程 ≤1 ulp。超出未测：需要 `k < 2^25`
  才能保证 `k·pio2_hi` 精确。
- **编译器浮点字面量只取 8 位小数并静默截断**（见上节）。本库靠
  `ffrombits` 绕过，但用户代码不受保护。
- 次正规数（denormal）一律返回 0，不保证精度。
- `pow` 走 `exp(b·log a)`，整数指数不特判，误差略大于 libc。

## 验证

```bash
make fmathtest    # 2200 点 ULP 交叉验证（Python 当标准答案）
make fmathrange   # 8 个量级的范围规约误差曲线
make test         # tests/126_fmath.mo：NaN 语义 + 特殊值
```

`make fmathtest` 有守卫：函数缺失或输出少于 2000 行**直接红** ——
否则程序只打印三行也会"全部通过"。
