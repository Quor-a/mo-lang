# hll —— HyperLogLog 基数估计

`lib/hll.mo`，测试 `tests/138_hll.mo`（29 项断言），变异 `tools/hllmut.sh`（5 个）。

## 概念来源

| 年份 | 工作 | 贡献 |
|---|---|---|
| 1985 | Flajolet & Martin | PCSA：用哈希值前导零的最大长度估计基数 |
| 1990 | Whang–Vander-Zanden–Taylor | Linear Counting：小基数区的无偏估计 |
| 2003 | Durand & Flajolet | LogLog |
| 2007 | Flajolet–Fusy–Gandouet–Meunier | HyperLogLog：**调和平均** + α_m 偏差修正 |
| 2013 | Heule–Nunkesser–Hall | HLL++：稀疏表示 + 大基数修正 + 经验偏差表 |

**没有进任何主流语言的标准库**：Python 靠 `hyperloglog` / `datasketch`、Java 靠 `stream-lib` / Apache Druid、Go 靠 `axiomhq/hyperloglog`，全是第三方；C++ 标准库无。Redis 有 `PFADD/PFCOUNT`，但 Redis 是存储而不是语言标准库。

它是"用 O(m·loglog n) 位估计 n"这条理论极限附近的算法：m=1024 个桶 × 6 bit ≈ 768 字节，就能估到百万级。

## 三条公式

```
原始估计    E = α_m · m² / Σ 2^(−M[j])            调和平均
小基数修正  E ≤ (5/2)m 且 V > 0 ⇒ E = m·ln(m/V)    Linear Counting
大基数修正  E > 2^64/30 ⇒ E = −2^64·ln(1 − E/2^64)
合并        (A ∪ B) 的 sketch = 逐桶 max
```

## 与 HDC / SDM / LSH 的关系（项目内对照）

本库是项目里第四个"随机性换空间"的库，但丢掉的东西最具体：

| 库 | 保什么 |
|---|---|
| HDC | **代数结构**（⊕ ⊙ ⊗ 可逆，向量即符号） |
| SDM | **内容寻址**（噪声地址能找回原模式） |
| LSH | **相似度序**（概率的，会漏） |
| HLL | **只有一个数**（|A|；集合本身、成员查询全部丢掉） |

## 实测

### 标准误差 1.04/√m

n=10000、每种 m 各 24 次独立试验（元素区间互不相交）：

| m | 实测 σ | 理论 1.04/√m |
|---|---|---|
| 1024 | **29.9‰** | 32.5‰ |
| 256 | **83.0‰** | 65‰ |
| 64 | **113.1‰** | 130‰ |

三个量级都落在理论附近，且随 m 增大按 √m 缩小（σ 由「平均 |rel| / 0.7979」换算，半正态分布下 E|X| = σ√(2/π)）。

### 小基数修正是必需的，不是美化

m=1024、n=100：

| | 估计 | 相对误差 |
|---|---|---|
| 原始估计（调和平均） | 786.6 | **6866‰** |
| 修正后（Linear Counting） | 94.2 | 58‰ |

差两个数量级。只看修正后的数字，分不清"修正有效"和"本来就这么准"——所以测试里**两条都断言**。

### 桶覆盖

| n | 空桶数 V |
|---|---|
| 1 | 1023 |
| 100 | 934 |
| 2000 | ~145 |
| 100000 | **0** |

### 合并

A（5000 个）、B（5000 个，与 A 完全不相交）：

| 算法 | 估计 |
|---|---|
| sketch 合并（逐桶 max） | ~10000 |
| 直接插并集 | ~10000 |
| est(A) + est(B) | ~10000 |

三者同量级；`hll_merge(c, a)` 对已有 A 内容的 c 是幂等的。

## 🔴 本轮最大的坑：哈希的 bit63 恒为 0

第一版 `hll_mix` 直接照抄 `lib/lsh.mo` 的 `lsh_mix`，而它用的是 `a ^ (a >> k)`。墨语言的 `>>` 是**算术**右移，于是

```
y = a ^ sar(a, k)  ⇒  y 的 bit63 = a63 ^ a63 = 0
```

**输出的 bit63 恒为 0。**

- 在 **LSH** 里无所谓：SimHash 用 64 位投票，少一位随机性看不出来，`lsh_mix` 一直是绿的。
- 在 **HLL** 里致命：桶号取哈希的**最高 p 位**，bit63 正是桶号的最高位 ⇒ 只有低 m/2 个桶可能被选中，另外一半永远空着。

症状（p=10 / m=1024，实测）：

| n | V | 估计 |
|---|---|---|
| 1 | 1023 | 1.00 ← 完全正常 |
| 1000 | 570 | 599 ← 只是"偏低" |
| 10000 | **512** | 709 |
| 100000 | **512** | 709 ← 与上一行**逐位相同** |

不报错、不崩溃，估计值始终是个像样的数。能揪出它的只有两个数字：**bit63 的占比**、**V 恰为 m/2 且不再下降**。

修法是换成真 splitmix64 + 逻辑右移（`hll_shr`）。修复后 10000 个样本里 bit63=1 的比例回到 4999/10000。

> **教训**：从别处抄来的原语，要检查它在**新场景**下的前提是否还成立。这和 LSH(v1.137) 里「`a·x+b` 不是 min-wise」是同一类错——那个也是"抄来的哈希在原场景够用、在新场景不满足理论前提"。

## 验证过程中的一个观察：临时目录不隔离会制造"假失败"

跑 `make test` 时，控制台出现过

```
cp: cannot create regular file '/tmp/mot/pack.mo': No such file or directory
通过 114 / 失败 70
```

清掉 `/tmp/mot` 后重跑是 **184 / 0**。

原因是多个脚本**共用** `/tmp/mot` 这一个固定路径：一个脚本 `rm -rf` 的同时另一个正在 `cp`。失败是假的，但它和真回归长得一模一样 —— 都是"一堆测试突然红了"。

本项目 v1.129 记过同一处的另一个变体（残留进程让基线偶发失败）。两个方向相反，根子相同：**验证脚本的临时区不隔离**。这次没有去改全项目的脚本（那是一轮独立的工作），只是如实记录，避免下一轮把这类假失败当成回归去"修"。

## 已知限制（都没静默）

- **大基数修正不可端到端测**：64 位哈希下阈值是 2^64/30 ≈ 6.1e17，要插 6e17 个元素。它是"正确但不可达"的代码，只做了**单元级**验证（`hll_bigfix` 直接喂值），不假装端到端测过。
- 桶值不做 6 bit 截断（存成 i64），省掉一条静默丢失的路径；代价是内存比论文版大。
- 池 20480 字，p=10 时约 19 个 sketch；超限置 `HLLOVF` 并返回 −1。
- `p` 必须在 [4, 16]：`(1 << (64-p))` 在 p<4 时溢出；越界置 `HLLBAD` 并返回 −1。
- 只做基数估计与合并，**没有**成员查询（这是 HLL 的本质：不支持）。
- `hll_clz64` 是线性扫描（最多 64 步）。实测 ρ 平均落在 p+2 附近，所以每元素约 12 步；n=10^6 量级可接受，更高应换二分版——但那需要无符号右移判据，见函数内注释。
