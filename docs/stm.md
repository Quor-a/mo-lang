# 软件事务内存（TL2 风格）

`lib/stm.mo` —— encounter-time locking + undo log。

## 概念来源

- Treiber 1986 / Herlihy–Moss 1993（事务的硬件雏形）
- Shavit–Touitou 1997（软件事务内存）
- Dice–Shalev–Shavit 2006「TL2」（全局版本时钟 + 版本化写锁 orec）

至今**没有主流语言标准库内建**：C/C++ 只有 GCC 的 `-fgnu-tm` / libitm，
Rust 无，Go 明确不做，Java 只有 research 实现。Clojure / Haskell 有，
但都是语言级而非标准库。

## 为什么是 TL2

encounter-time locking：**写的时候**就把 orec 锁住，于是提交阶段只需校验
读集、不必再抢锁，也不存在"读到一半别人提交"的窗口。

代价是锁持有时间变长、以及可能死锁 —— 后者靠"抢不到锁就直接放弃
（abort 而非等待）"规避，这也是 TL2 论文里的做法。

## API（显式事务，没有 `atomic{}`）

```
stm_begin(tid);
v = stm_read(tid, &X);
stm_write(tid, &Y, v + 1);
ok = stm_commit(tid);        # 0 = 冲突/放弃，调用方整段重跑
```

墨语言当前不能把函数当回调传出，所以没有 `atomic{...}`，重跑由调用方写
`while` 循环完成 —— 这正是 libitm 之外多数 STM 库的显式接口形态。

## 三个限制（都不静默）

1. **假冲突**：orec 只有 1024 个，地址按 `(addr/8) % 1024` 映射，两个不相干
   的变量可能共用一把版本锁，表现为"莫名其妙地 abort"。这是 TL2 的真实
   性质而非 bug，`STM_FALSH` 会把它计出来。
2. 读集/写集上限各 64；超了置 `STM_OVF` 并 abort(3)，不静默截断。
3. 统计计数器（`STM_OK` / `STM_ABT` / ...）是**非原子**自增，只作观测量，
   **不参与正确性判据**。正确性判据一律是"共享变量最终值 / 不变式的值"。

## 验证

- `tools/stmtest.sh` —— 判据不是"有没有崩"，而是每一项给出**具体数字**：
  丢失更新必须**正好 4000**、无保护对照必须 **< 4000**（两个数都必须出现，
  只有 4000 说明对照没做）；原子性要求抢锁失败时先前已写的位置**恢复到原
  值**（不报错、不崩溃，只表现为数字不对）；假冲突用相隔 8192 字节的两个
  地址必然同桶来验证。另有一条守卫：示例必须真的 `import "stm.mo"`，
  否则退化成别的东西而测试照样全绿。
- `tools/stmmut.sh` —— 五个"改坏"必须各自被抓到。**从不改仓库源码**：
  每次把 lib 拷到独立临时目录只改那份拷贝，于是"脚本被强杀导致源码停在
  变异态"这类失效根本不存在（本项目在 scopemut / lfmut / sdmseqmut 上
  各栽过一次）。
