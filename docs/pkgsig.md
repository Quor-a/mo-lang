# 包签名（`examples/pkgv3.mo`）

```bash
make pkgv3test     # 82 项（ARM64 模拟器 + x86-64 真机，各 41）
make pkgv3mut      # 5 个变异验证
```

## 为什么需要它：校验和证明不了「来源可信」

v1.158 的 `MOPK1` 只有校验和。它能发现包**被意外改坏**，但校验和是公开算法 ——
任何人都能自己算一个合法的，伪造一个 `MOPK1|...` 字节串让手机装上并跑起来。

签名解决的是后者：只有持有密钥的一方才能生成能通过验签的包。

| | 能证明 | 不能证明 |
|---|---|---|
| 校验和 | 没被意外改坏 | 来源可信 |
| 签名 | 由持有密钥的一方生成 | — |

## 概念来源

**SipHash-2-4**（Aumasson–Bernstein 2012）。它本来是为哈希表抗 HashDoS 设计的
带密钥伪随机函数（PRF），作为 MAC 同样成立。

选它而不是自造一个 ARX 混合，是因为它有**公开定义和官方测试向量**，可以独立验证。
自造混合无法证明自己是对的 —— 只能「跑通」，而「跑通」什么都证明不了。

## 格式

```
MOPK2|<name>|<version>|<deps>|<len:8hex>|<code:hex>|<ck:8hex>|<sig:16hex>
```

比 `MOPK1` 多一个签名字段。**签名覆盖 `name|version|deps|len|codehex`（段 1..5），
不只是 code。**

只签 code 是不够的：`ck` 只算 code，攻击者改掉 `version` 或 `deps` 之后
`ck` 仍然相符，于是可以悄悄换掉依赖关系或版本号。

## 验签顺序：故意放在校验和之后

```
容量(-7) → 长度(-5) → 校验和(-6) → 签名(-9)
```

这样两个错误码都有**独立可达**的场景：

| 情形 | 返回 | 该做什么 |
|---|---|---|
| 篡改 code | -6 | 意外损坏，重传 |
| 换密钥 / 改元数据 | -9 | 来源不可信，报警 |

如果先验签，篡改 code 也会直接落到 -9，**-6 永远走不到，变成死代码**。
一个永远不可达的分支，和没有这个分支是一样的。

## 实测（`make pkgv3test`）

| 场景 | 结果 |
|---|---|
| SipHash 官方 16 个向量 | **0 错** |
| 篡改 code | -6 |
| 篡改 version（元数据） | **-9** |
| 正确密钥 | 6（装上） |
| 换错密钥 | **-9** |
| 换回正确密钥 | 6 |

最后一条是关键：它证明「换密钥失败」确实只由密钥引起，而不是包本身已经坏了。

## 三个真缺陷（全是静默的）

### 一、`常量 << 常量` 在 cfs 后端按 32 位折叠

```
1936682341 << 32   →  0      （常量折叠）
v << 32            →  正确   （v 是变量）
```

不报错、不崩溃，只表现为哈希值恒错。第一版用它拼 SipHash 的 64 位常数，
于是四个常数全部变成 0。改用**完整十进制字面量**写常数。

### 二、`(1 << r)` 与 `load8(...) << (j*8)` 是 32 位 int 移位 UB

mo2x 生成的 C 里，字面量 `1` 是 `int`，`load8` 返回的字节会被提升成 `int`。
移位量 ≥ 32 时是未定义行为，LLVM 直接折成 0：

```
rotl64(1, 13) = 8192        ✓
rotl64(1, 32) = 0           ✗（应为 4294967296）
```

修法是让 i64 变量承载：`let one: i64 = 1;` 然后 `(one << r)`；
字节也要先落进 i64 变量再移位。

**这类缺陷最阴的地方**：小移位量下完全正常，只有 `<< 32` / `<< 56` 才发作，
所以抽查 `rotl(1,13)` 这类值是永远碰不到的。

### 三、`tohex16` 是字节逆序

第一版按 `(v >> (i*8))` 输出（小端），而对端 `unhex16` 把前 8 个字符当高位。

**两边各自看起来都对** —— pack 侧打印出 `797d02c1868a1706` 是个像样的 hex，
unpack 侧也解析出一个像样的数。只有把**两侧的签名值都打印出来对比**才发现
它们互为字节逆序（`u calc` 与 `pack sig` 相等，而 `u got` 是它的逆序）。

现在 `tohex16` 输出大端，与 `hex8` 一致。

## 变异验证（`make pkgv3mut`，5/5 被捕获）

| 变异 | 失败模式 |
|---|---|
| M1 签名 hex 退回小端 | unpack -9 |
| M2 unpack 不验签 | 篡改的元数据被接受（tamper ver = 6） |
| M3 签名只覆盖 code | **篡改 version 被接受** |
| M4 rotl64 退回 `(1 << r)` | 官方向量 16 项全错 |
| M5 SipHash 常数差一 | 官方向量 16 项全错 |

M3 最有价值：它证明「签名必须覆盖元数据」这条不是写在注释里好看的，
而是真的在被断言盯着 —— 改掉之后测试立刻红。

## 已知限制（都没有静默）

- **不是公钥签名**：SipHash 是对称密钥 MAC。分发方和验签方共享同一把密钥，
  能验签就能签名。它防不了「持有密钥的人自己作恶」，只防「第三方伪造」。
  真正的「来源不可抵赖」需要公钥签名（Ed25519），本轮没做。
- **密钥来自口令**：`key_derive("mo-pkg-secret")` 用 SipHash 自身把口令展开成
  两个 64 位半密钥。口令强度就是密钥强度。
- CODE 上限 64 字节、字段数固定 8 个 —— 沿用 v1.158 的限制。
- 官方向量只取了前 16 个（`i < 16`），尾部路径（含 8 字节块）由 `i ≥ 8` 覆盖。
