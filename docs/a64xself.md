# a64xself —— 墨语言写的汇编器，**跑在 ARM64 上**再产出 ARM64 系统

`examples/a64as.mo` 是墨语言写的 AArch64 汇编器。此前所有 a64 系列验证
（a64test / a64ldtest / a64datatest / a64bsstest / a64artest …）里，这个汇编器
**只在 x86-64 上跑过**：它读 `.s`、写 aarch64 机器码，但**汇编器自己**的宿主
一直是 x86-64。

于是「墨语言能在 ARM64 上干什么」这句话，此前只有一半成立：

- 能**产出** ARM64 代码（交叉后端 `cfs-aarch64`）—— 成立
- 墨语言写的**工具**能在 ARM64 上**运行** —— **此前从未验证过**

`tools/a64xself.sh` 补的就是这后半句，闭环如下：

```
examples/a64as.mo ──mo2x cfs-aarch64──> ARM64 静态 ELF（无 libc）
                                            │ 跑在 Unicorn 模拟的 ARM64 CPU 上
tools/a64sys.s   ──────────────────────────┘
                                            ↓
                                        sys64.arm.elf
                                            ↓ kern64run.py（裸机：无 Linux / libc / 安卓）
                              MO-A64 BOOT / SUM=5050 OK / FIB=55 OK / MEM OK / IMM OK
```

同一份源码在 x86-64 上也编一遍、也汇编一次，两台机器上的产物**逐字节相同**。

## 实测

| | x86-64 端 | ARM64 端 |
|---|---|---|
| 指令条数 | 114 | 114 |
| 数据字节 | 4163 | 4163 |
| 标签数 | 23 | 23 |
| 产物 md5 | 相同 | 相同 |
| 产物大小 | 4739 字节 | 4739 字节 |

ARM64 端产出的 4739 字节镜像，在**裸机模拟器**里跑出：

```
MO-A64 BOOT
SUM=5050 OK
FIB=55 OK
MEM OK
IMM OK
```

判据 14 项（`tools/a64xself.sh`），分六层。

## 判据为什么分六层

**① 构建层**：`e_machine == 183`。构建前**先删产物** —— 否则构建失败时旧 ELF 残留，
"执行"跑的是上一版，判据全绿而什么都没验（v1.153「源码干净 ≠ 产物干净」）。

**② x86-64 参照端**：同一份源码本机真跑一次，作为"正确结果"的独立来源。

**③ ARM64 端真读了输入**：统计输出两端必须一致。若 `--preload` 失效，程序拿到空输入
却可能照样"成功"退出 —— 所以还要求统计行**非空**（两边都是空串也会"相等"）。

**④ 两端产物逐字节相同**，外加**单独校验 ARM64 端产物的 `e_machine`**。

**⑤ 端到端裸机执行**（真正的"算得对"）。

**⑥ 负例**：越界立即数必须被拒绝且**没有产物**。

第 ④ 层里那条 `e_machine` 校验不是摆设，它和 ⑤ 一起构成一条**互补**关系，
下面 M4 会说明为什么两层都要有。

## 🔴 最有价值的发现：M4 未被捕获，暴露的是我自己的错误注释

`tools/a64xselfmut.sh` 的 M4 把 `examples/a64as.mo` 里 `st16(18, 183)` 改成
`st16(18, 62)`（把 ELF 的 `e_machine` 写成 x86-64）。我在注释里写：

> 两端用同一份源码，所以 md5 会**一起**变、仍然相同 —— md5 这一层抓不到它。
> 能抓它的是裸机层（load_elf64 断言 machine==183）。

**实测 M4 未被捕获（13 通过 / 0 失败）。** 顺着查下去：

```
$ grep -n "machine" tools/kern64run.py
（无输出）
```

`kern64run.py` 的 `load_elf()` **从来没读过 `e_machine`**。那句"断言"只存在于我的
注释里 —— 我把**打算做的事**当成了**已经做了的事**，而注释写得越自信，
后来的人越不会去核。

这比"测试空转"更值得记：它不是判据太松，是**文档与实现不符**，而且方向正好是
"声称自己有保护"。如果当时没跑变异，它会一直以"已被裸机层覆盖"的面目留在注释里。

修法两层，都补上：

1. **`kern64run.py` 的 `load_elf()` 真去读 `e_machine`**，不等于 183 就
   `raise SystemExit`。理由不是"为了抓 M4"，而是**裸机加载器本就该拒绝非本架构的
   镜像** —— 真硬件不会把 x86-64 代码当 AArch64 执行。放在模拟器里而不是只放在
   测试脚本里，是因为这条性质属于"加载器语义"，不属于"某次测试的要求"。
2. **`a64xself.sh` 单独校验产物的 `e_machine`**，不依赖模拟器的实现。

修完 M4 被捕获（12 通过 / 2 失败），判据变成 14 项。

## 🔴 变异脚本第一版给了**假的好看结论**

第一版 `a64xselfmut.sh` 报「5 捕获 / 0 未捕获」。这个结论是假的。

原因是 `mut()` 里的顺序写反了：

```
make bin/mo2x      ← 用**变异版**源码重建
cp bak 源码         ← 之后才还原源码
```

于是 `bin/mo2x` 里留着上一个变异的坏后端，源码却是干净的。此后每个变异都在
**污染态**上跑，它们"被捕获"其实只是撞上了前面残留的坏东西 —— M4/M5 的
"未捕获"结论同样不可信。

修正为 **先还原源码、再重建**，基线才恢复干净，M4 的真实结果才浮出来。

这类失效比"测试空转"更隐蔽：空转只是什么都不说，而它**会主动给出漂亮分数**。

## 变异验证（`tools/a64xselfmut.sh`）

| | 改坏的是哪条因果链 | 结果 |
|---|---|---|
| M1 `write` 号 64→63 | ARM64 端既打不出统计、也写不出产物 | 捕获（8/5） |
| M2 `--preload` 失效 | 输入文件根本没被读到 | 捕获（7/6） |
| M3 `store8` 写偏一字节 | 逐字节拼 ELF，写偏则两端产物不同 | 捕获（8/6） |
| M4 `e_machine` 写 62 | 两端同源改坏，md5 层抓不到 | 捕获（12/2，裸机层 + 产物校验） |
| M5 `e_flags` 写 7 | 不影响执行的位 | **预期未捕获** |

M5 保留在脚本里并注明原因，是为了钉住一件边界：**a64xself 证明不了"每条编码
都正确"** —— 那是 `a64test` 的四层判据（含独立解码对拍）负责的。改了代码
不等于改到了那条因果链，M5 就是例子。

## 打通路上修掉的四个"卡脖子"缺陷

要让 1500 行的 `a64as.mo` 真的过 `cfs-aarch64` 后端，撞上四个静默失败：

1. **十六进制字面量**：`moc` 认，`mo2x` 不认 —— 被切成 `0` 和 `x…` 两段，
   然后在文件**末尾**报一个看不懂的语法错，方向完全不指向真因。
   汇编器里到处是 `0x…`（机器码就是这么写的），所以直接卡死。
2. **浮点字面量** `10.0` 同样不认，报错甩锅给被引用的库文件。
3. **`f64` 形参类型标注**不认，一遇到就一路吃到文件结束。
4. **最阴的一个**：`mo2x` 逐文件处理却**不给"文件处理完"做记号**。
   当后一个文件比前一个短时，前一个的残留会被当成当前文件继续读 ——
   报错指向错误的文件和错误的行。这解释了为什么小程序从来不出事，
   **上千行的大程序必然发作**。

另补了一个真缺口：浮点转换内建在交叉后端里没有对应物，只有用到浮点打印的
程序才会撞上。

## 已知限制

- ARM64 端跑在 **Unicorn 模拟的 CPU** 上，未经真实硬件；
- 汇编器本身是静态 ELF、无 libc，文件 IO 走裸 `syscall` + `*at` 适配；
- 只验证了**汇编器**这一个工具在 ARM64 上的自举；链接器 `a64ld.mo`、
  归档器 `a64ar.mo` 的 ARM64 自举尚未做；
- 两端产物相同**证明不了编码正确**（见 M5），只证明交叉后端没有算偏。
