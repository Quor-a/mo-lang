# switch

`switch` / `case` / `default` / `fallthrough` 都是**上下文关键字**：`switch`
只在语句起始位置识别，`case` 等只在 switch 主体里识别。于是 `case`、`default`
仍然可以当普通标识符用，不会占用标识符空间。

```mo
switch (e) {
    case 1: r = 10;
    case 2:
    case 3: r = 20;      # 多个标签共享一段 body
    default: r = 0;
}
```

## 两条与 C 不同、且是有意为之的语义

**一、case 之间不穿透。** 每个 case 末尾隐含 break，要穿透必须写
`fallthrough;`。C 的隐式穿透让"漏写 break"成为一类**既不报错也不崩溃**的
经典错误——这正是本项目一直在排除的形状。空 case（`case 1:` 后面直接跟
`case 2:`）仍视为穿透，否则"多个标签共享 body"这种最常见的写法会失效。

**二、`continue` 在 switch 里作用于外层循环**（与 C 一致）。为此 switch 压
循环栈时 `cnt` 传 -1，表示"这层不是循环"；`parse_continue` 会往下跳过这类层
去找真正的循环。若直接取栈顶，continue 会跳到 switch 出口（语义错），或者
因为 cnt=-1 被当成"不在循环里"而报错（更迷惑的错）。

## 不只是 if/else 语法糖：两种策略自适应

这才是 switch 值得作为独立特性的地方——判据是**值密度**，不是 case 个数：

| 条件 | 策略 | 复杂度 | 额外体积 |
|---|---|---|---|
| `n >= 4` 且 `范围 <= 4*n` 且 `范围 <= 1024` | 跳转表 | O(1) | `8 × 范围` 字节 |
| 否则 | 比较链 | O(n) | 0 |

稀疏值建表是纯浪费：`case 1 / case 1000000` 会生成 8MB 的表，所以必须能退回
比较链。测试里 `t_sparse()` 就是盯着这条的（`tests/133_switch.mo`）。

跳转表的边界检查只用了两条指令而不是四次比较：

```
sub  rax, mn        # 无符号视角下 val < mn 会回绕成巨大正数
cmp  rax, (mx - mn)
ja   dflt           # 一条无符号比较同时抓住"太小"和"太大"
jmp  [rcx + rax*8]
```

## 🔴 修掉的四个真缺陷

**一、表地址漏掉 ELF 头的 176 字节。** 表放在代码末尾，绝对地址必须加
`4194304 + 176`。此前所有跳转都是 RIP 相对的，**从来不依赖基址**，所以这个
偏差一直没暴露——直到引入绝对地址。表现是：跳转表路径**无一例外段错误**，
而比较链路径全对。只看"能不能编译"或"有没有跑通某个 switch"都会漏掉。

**二、有 default 时它的标签被末尾又覆盖了一次。** 整段 default 代码变成死
代码：取不到值，但不报错。

**三、嵌套时多推进了一格。** 把外层下一个 case 整个吃掉，报错还指向完全不
相干的位置。

**四、嵌套时括号计数的起点错了**，扫描一路吃到文件末尾 → 编译器**卡死不动**。
不报错、不崩溃，就是停在那儿——这是最难查的一类。

后三个的共同根源是"嵌套时外层记录的状态被内层覆盖"。本项目已在共享临时
变量上栽过多次（HDC、SDM、SDM 序列、GC），这次换了个载体：**token 位置**
和**括号计数**。`sw_scan()` 因此改成**只走词法、不做任何解析**，并整段跳过
嵌套 switch——这样内外层根本不共享 token 位置。

## 实测（`tests/133_switch.mo`，24 项断言）

判据全是具体数值，不是"能不能编译/会不会崩"：

- 跳转表模式下若槽位填错（比如全部指向 default），命中任何 case 都会得到
  default 的结果而**不崩**——只有具体数字能区分。
- `t_break()` = 4：若 break 错误地跳出外层 while，s 会停在 2。
- `t_continue_in_switch()` = 18（`1+2+4+5+6`）：若 continue 跳到 switch
  出口，s 会包含 3。
- `t_continue_for()` = 12：continue 必须走 for 的 step，否则**死循环**。
- `t_neg()` = 32：负数 case 值 + 负数下界，`sub rax, mn` 里 mn 是负数。
- `t_after_table()` = 103：表放在代码末尾，后面的代码不能被当成指令执行。

## 变异验证：`tools/switchmut.sh`

24 项断言全绿**证明不了** `parse_switch` 是对的——判据必须能区分"生成正确"
和"恰好没碰到"。五个变异把编译器改回一种**具体错法**，每个都必须让测试变红：

| 变异 | 错法 |
|---|---|
| M1 | 跳转表 case 槽不回填（全部走 default，不崩） |
| M2 | 表地址漏掉 +176（真实踩到的那个坑） |
| M3 | case 末尾不补 jmp end（退回 C 的隐式穿透） |
| M4 | continue 取栈顶，不跳过 switch 层 |
| M5 | 空 case 不再视为穿透 |

⚠ 每个 `run_one` 都套 `timeout`：M2 会让测试**段错误**、M1 会让它静默走
default，两者都不会自己退出，没有 timeout 会把 CI 挂住。

脚本自身的两个坑（与 `formut.sh` 同源，一并修掉）：

- **备份取自 `src/mo/` 分片拼接，而不是 `cp $SRC`**。第一次被强杀后 SRC 停在
  变异态，于是备份把污染版当成基线，下一轮一开工就"基线没通过"。
- **必须 `rm -f bin/moc` 强制重建**。`make` 只看 mtime，`cp` 与上次构建可能
  落在同一秒，make 会认为 bin/moc 仍更新而**跳过重建**——于是每个变异测的
  都是**上一个**变异编译出来的 moc，结果整体错位一格。

## 🔴 v1.136 收尾时挖出的：变异脚本留下了"被改坏的编译器"

`make test` 报 `FAIL empty case: got 0, want 42`。查下去发现**源码是干净的**——
`if any == 0 { fell = 1; }` 明明就在 `parse_switch` 里，反汇编却显示空 case
那一格确实发出了 `jmp end`。

真正的原因是 `bin/moc` 是**变异版**：

1. `switchmut.sh` 的最后一轮 `check` 用 M5（空 case 不穿透）编出了一个 moc；
2. 脚本收尾 `restore` 把 `src/compiler.mo` 还原干净；
3. 但**没有重建 `bin/moc`**；
4. `cp` 与上一次构建落在**同一秒**，make 只看 mtime，认为 `bin/moc` 仍比
   `src/compiler.mo` 新 —— **跳过重建**。

于是跑完变异脚本之后，整个项目一直在用一个被改坏的编译器跑测试，而源码
本身干干净净，**看代码永远看不出来**。变异脚本里那句"必须强制重建"的注释
说的正是这个陷阱，但它只管住了脚本**内部**，没管住脚本**结束之后**。

> **源码干净 ≠ 产物干净。** 还原动作必须把两个都还原。

三处修法：

- 五个变异脚本（`switchmut` / `formut` / `timermut` / `scopemut` / `lfmut`）
  收尾一律 `rm -f bin/moc; make bin/moc`（此前只有 `escxmut.sh` 做对了）。
- `build.sh` 每次构建写 `bin/moc.srcmd5`（这一版 moc 是由哪份源码编出来的）。
- `projcheck` 新增第 11 项：拿 `bin/moc.srcmd5` 与当前 `src/compiler.mo`
  的 md5 比对，不一致直接报红并提示 `make -B bin/moc`。

顺带：M5 的捕获输出正是 `FAIL empty case: got 0, want 42`，与上面那条
`make test` 的报错一字不差 —— 这条报错其实就是"M5 变异残留在 bin/moc 里"
的指纹。

## 已知限制

- 嵌套上限 8 层（超过明确报错）。
- case 值必须是编译期常量（整数或 enum），超出 32 位明确报错。
- 重复的 case 值明确报错。
- `switch` 自带一层作用域，各 case 里可以各用同名 `let`。
