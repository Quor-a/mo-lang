# a64exec —— 自举 AArch64 的 ELF 加载器：运行内核之外的程序

## 它证明的是什么

a64svc / a64mmu / a64irq 里被运行的"用户代码"，都是**链接进内核镜像**的
一段 —— 内核和它本来就是同一个可执行文件的两部分。这一版被运行的东西
来自内核之外：

```
main.s ─a64as -r→ main.o ─a64ld→ kern.elf   （内核，BASE 0x40000000）
user.s ─a64as -r→ user.o ─a64ld --base→ user.elf  （用户，BASE 0x40200000）
                                    │
                    --initrd user.elf@0x40410000
                                    ↓
内核解析程序头 → 复制 PT_LOAD → 按 p_memsz 清零 bss → eret 进 EL0
```

于是"用户空间"第一次有了可验证的含义：**内核跑的东西不是它自己的一部分。**

判据里"改 ELF 的一个字节，输出就跟着变"（见 `tools/a64exectest.sh` 第 ⑥ 层）
就是为此存在的。若内核镜像里内嵌了一份用户程序，⑧（不给 initrd 必须报错）
会立刻变红。

## 布局（每块 2MB）

| 块 | 地址 | 权限 | 内容 |
|---|---|---|---|
| 0 | 0x40000000 | AP=01 | 内核代码/数据 |
| 1 | 0x40200000 | AP=01 | 用户区：text / data / bss / 栈 |
| 2 | 0x40400000 | AP=00 | 内核私有：栈、页表、secret、**initrd 镜像** |
| 3 | 0x40600000 | 未映射 | EL0 访问 = 转换错误 |

initrd 放在内核私有块是刻意的：用户程序若读得到它，就读得到还没被加载的
东西 —— 那等于没有隔离。用户读它会触发 data abort（判据 `PF2`）。

## 八个错误码

| 码 | 含义 |
|---|---|
| -1 | magic 不是 `\x7fELF`（也覆盖"根本没有镜像"） |
| -2 | e_type 不是 ET_EXEC |
| -3 | e_machine 不是 183（AArch64） |
| -4 | e_phentsize ≠ 56 |
| -5 | e_phnum 不在 [1, 4] |
| -6 | e_entry 不在用户区 |
| -7 | 段的 [p_vaddr, p_vaddr+p_memsz) 越出用户区 |
| -8 | 一个 PT_LOAD 都没有 |

八种失败必须是**八个不同的码**。统一返回 -1 的话，调用方分不清"文件坏了"
和"架构不对"，而这两件事该做的反应完全不同（重传 vs 报警）。

## 真缺陷（四个，都不报错）

**① `ldrb w21, [x18, x20]` 会静默退化成 `ldrb w21, [x18]`。**
本汇编器对字节类加载的寄存器偏移编码与 `ldr` 的 scale 不同，写成带索引的
形式时索引被吃掉。结果是 215 个字节全部填成第一个字节 —— 用户第一条指令
成了未定义指令（Unicorn 报 UDEF），而**加载器自己认为一切正常**（所有校验
都过了，entry 也返回了）。改成指针递增后才真正在复制。

**② 内核块设成 AP=00 会让内核自己取不到指。**
模拟器用**页级** `mem_protect` 模拟 MMU，同一页在 EL0 / EL1 只能是同一种
权限。内核块一旦在 EL0 视图里没有 X，svc 陷入后内核自己也取不到指，症状是
`UC_ERR_FETCH_PROT` 且 PC 落在向量表 —— 极易被误读成"向量表建错了"。
真硬件按异常级分别判权，没有这个限制。所以内核的**秘密**放在 block2，
不放 block0。

**③ initrd 地址算错：`movk #0x4040 + 8 × add #2048` = 0x40404000**，
正好压在 L2 页表上，于是"镜像"读出来是一张页表 → 报 `E-1`。用
`movk #0x4041, lsl #16` 一步到位。

**④ `ldrh` 的立即数偏移同样要求 8 的倍数**，读不到 e_machine@18 与
e_phentsize@54。改成按 8 字节对齐读、再移位取半字。

## 链接器 `--base` 的三个坑（顺带修的）

1. **`argc()` 含程序名**（`argv(0)` 是程序自身），所以输入从 `argv(2)` 起；
   带 `--base` 时从 `argv(4)` 起。按"argv(1) 是第一个实参"写，loadfile 拿到
   的是基址字符串本身 —— 报的却是 `cannot open input`。
2. **`write_elf(argv(1))` 写死了输出名**，带 `--base` 时产物被写进一个名叫
   `--base` 的文件。链接器照样打印成功、返回 0，而期待的 out.elf 根本不存在
   —— 症状在下一步才爆发。
3. **0x40200000 是 1075838976，不是 1074790400**（后者是 0x40100000）。
   这个错让"用户 entry 在用户区"的校验失败，报 `E-6`，方向却指向 ELF 文件，
   很难想到是命令行上的常数写错。

## 判据八层（tools/a64exectest.sh，43 项）

| 层 | 抓的是 |
|---|---|
| ① 两个 ELF 都产出 | 根本没产出 |
| ② 用户字符串与首条指令**不在**内核镜像里 | 其实链接进了内核，加载是演的 |
| ③ python 独立读 ELF 头 | 链接器 `--base` 没生效 |
| ④ 端到端逐行输出 | 加载了但跑错 |
| ⑤ 模拟器计数 svc=6 / eret=7 | 走了别的路径、碰巧也对 |
| ⑥ 改一个字节 → 输出随之变 | 其实没从文件读 |
| ⑦ 八个负例给出八个不同码 | 校验被跳过 / 统一返回 -1 |
| ⑧ 不给 initrd 必须报错 | 内核自己内嵌了一份用户程序 |

第 ⑥ 层有两个方向：改字符串首字节 → 输出 `V1` 且不再有 `U1`；改 `e_entry`
+0x14 → 不再有 `U1` 但仍算出 `5050`。后者专门盯"入口到底取不取自 ELF 头"。

## 污染用户区的必要性

内核在加载**之前**把 `[0x40200000, 0x40210000)` 填成 `0xA5A5A5A5`。不做这
一步，"加载器有没有清零 bss"根本测不出来 —— 模拟器里用户区本来就是全 0，
不清零用户读到的也是 0，判据恒绿。

这是本项目第三例"样本充分 ≠ 覆盖充分"（前两例：SAM v1.141 的 `SA_NCL=0`、
CMS v1.144 的 `w=200`）。

## 变异验证（tools/a64execmut.sh，6/6）

| 变异 | 抓它的判据 |
|---|---|
| M1 不校验 e_machine | 负例 mach 不再报 E-3 |
| M2 不清零 bss | 用户读到 0xA5A5A5A5，"bss=0" 变红 |
| M3 不复制 PT_LOAD | 用户第一条指令 UDEF |
| M4 用户区 AP=00 | 用户取指被拦 |
| M5 不校验段越界 | 负例 seg 不再报 E-7 |
| M6 入口写死 | 改 e_entry 不再起作用 |

M5 的锚点必须是 `b.gt le_seg`（越过上界）那条：越界负例改的是 `p_memsz`，
走的是上界分支。第一版改成了下界的 `b.lt`，**完全不起作用**，于是"不校验
越界"这个缺陷照样全绿 —— 改了代码 ≠ 改到了那条因果链。

变异脚本不重跑整套 43 项（会超时），而是每个变异只重编内核、跑一次模拟器、
比对那一条会变的关键行。

## 已知限制

- 只处理 `e_phnum ≤ 4`、单个 PT_LOAD 的 ET_EXEC；无动态链接、无重定位。
- 段必须整体落在用户区 2MB 内；不支持按需分页。
- 内核代码区在 EL0 视图下也可执行（模拟器页级保护的局限，见缺陷 ②）。
- 无签名校验：加载器只验证格式，不验证来源。
- 只在 CPU 模拟器里跑过，未经真实硬件。
