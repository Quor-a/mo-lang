# aifix —— 修复墨语言 bug 的闭环

`tools/aifix.sh`

```
bash tools/aifix.sh --file <路径> \
                    --old '<原文>' --new '<新文>' \
                    --test '<验证命令>' [--rebuild '<重建命令>'] [--boot]
```

## 为什么需要它

用户要的是「AI 可以直接修复墨语言 bug」。能改代码不等于能修 bug——
"改完跑一遍测试"最少有三种假象：

| 假象 | 后果 |
|---|---|
| 改的是 `src/compiler.mo`（生成物） | 下一次 `make sync` 把改动冲掉，测试照绿 |
| `bin/` 里还是上一轮变异留下的编译器 | 源码干净 ≠ 产物干净，测的是旧东西（v1.136） |
| 测试本来就通过 | 改对改错都一样（v1.141：`SA_NCL=0`，克隆分支从未进入） |

aifix 把这三条做成硬步骤，并多做一件事：**修完自动把修复撤掉一次，
测试必须失败**。失败 = 这条修复真被钉住了；仍然通过 = 测试没覆盖到，
直接报出来，不许写成"已修复"。

## 四条守卫

1. **拒绝生成物** —— 传 `src/compiler.mo` 直接 exit 2。改编译器必须改
   `src/mo/compiler_partN.mo`，aifix 会自动 `make sync`。
2. **唯一匹配** —— `--old` 出现 0 次或多次都拒绝。用 Python 精确子串替换，
   不用 sed（v1.137：sed 正则在手工验证时能匹配、脚本里恒判"未生效"）。
3. **强制重建** —— 分片改完 `make sync` + `rm -f bin/moc`；另可用
   `--rebuild` 删掉被测程序自己的产物。
4. **变异即判据** —— 把 `--new` 换回 `--old` 再跑一次，必须失败。

`--old` / `--new` 支持 `@文件`，多行补丁一律用这个：
shell 引号和转义会改变内容，而内容被改过的补丁会静默变成"没找到"。

## 实证：包管理器的 VM 静默执行坏包

包是"AI 开发的"，字节码可能写错、被截断、或是恶意的。
`examples/pkgv2.mo` 与 `examples/pkgmgr.mo` 各自带一份栈式 VM，
此前**没有任何边界检查**：

```
VS[sp - 2] = VS[sp - 2] + VS[sp - 1];      # sp=0 时读 VS[-2]
```

喂进去五组字节码，修复前（x86-64 真机实测）：

```
[9a] legal     ret=0 out=42     ← 合法包仍然正确，所以谁也没发现
[9b] underflow ret=0            ← 单独 ADD，栈下溢，静默"成功"
[9c] print uf  ret=0            ← 单独 PRINT，把 VS[-1] 的垃圾当输出
[9d] trunc     ret=0            ← PUSHI 立即数被截断，读上一包残留字节
[9e] overflow  ret=0            ← 65 次 PUSHI 越界写，还顺手改坏了 VM_OUT
```

**五个全部静默返回 0。** 栈上溢那一条尤其阴：`VS[64]` 的下一格正好是
`VM_OUT`，写坏了也只表现为"输出个数不对"，看着像普通的逻辑错。

修复后，两端逐位相同：

```
[9a] legal     ret=0 out=42     合法包不受影响
[9b] underflow ret=-2           栈下溢
[9c] print uf  ret=-2
[9d] trunc     ret=-4           指令跨过末尾
[9e] overflow  ret=-3           栈上溢
```

错误码刻意分开：`-1` 非法 opcode · `-2` 下溢 · `-3` 上溢 · `-4` 截断。
合成一个"坏包"码就分不清是包写错了还是被截断了——而这两种要下的决定不同
（前者让 AI 重生成，后者要重新传输）。

aifix 的完整输出：

```
=== aifix : examples/pkgv2.mo ===
✓ 补丁已应用（--old 唯一匹配）
✓ 已强制重建
✓ 修复后测试通过 (rc=0)
✓ 变异后测试失败 (rc=1) ← 修复被钉住了
✓ 已还原到修复态

=== 结论：修复有效，且被测试钉住 ===
```

`examples/pkgmgr.mo`（v1.155）里那份重复的 VM 同样修了——
重复实现正是"改一处漏两处"的温床（v1.120）。

## aifix 自己也要被验证：aifixmut

`tools/aifixmut.sh`，14 项。四个场景各配一个变异，判据是
「aifix 的行为是否改变」：

| 变异 | 场景 | 结果 |
|---|---|---|
| M1 去掉「拒绝生成物」 | `--file src/compiler.mo` | 不再 exit 2 → 捕获 |
| M2 「变异必须失败」改恒真 | 假修复（改注释） | 从 exit 1 变 exit 0 → 捕获 |
| M3 去掉 NO_MATCH 检查 | `--old` 不存在 | 不再 exit 2 → 捕获 |
| M4 去掉 MULTI_MATCH 检查 | `--old` 出现 4 次 | 不再 exit 2 → 捕获 |

M2 那条最关键：**用一个假修复**（改一行注释，测试本来就通过）。
合格的 aifix 必须说"没被钉住"；判据改恒真之后它会说"修复有效"——
那正是最坏的一种失效：验证工具自己骗自己。

备份放在 `build/aifixmut/` 而不是 `/tmp`（v1.128：`/tmp` 被清理后
源码停在变异态、备份也没了），并且收尾保留备份副本。

## 已知限制

- **不做定位** —— aifix 只管"改 + 证"，定位还是靠人和编译器诊断
- **一次只能改一处**（唯一匹配是刻意的；要改多处就调多次）
- `--test` 里若没有重建被测程序，aifix 检不出来 —— 请用 `--rebuild`
- 失败时默认**保留修复态**便于继续迭代（`--revert-on-fail` 可自动还原）
- `VS` 容量 64 在检查里写死，与 `var VS: [64] i64` 需同步
- 不支持删除型补丁之外的重构（移动函数、改签名请用普通编辑 + `--no-mut`）
