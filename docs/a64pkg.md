# a64pkg —— 自举 aarch64 的包管理与执行环境

## 它是什么

`tools/a64pkg/main.s` 是用墨语言写的汇编器（`examples/a64as.mo`）汇编、
链接器（`examples/a64ld.mo`）链接出来的 **AArch64 裸机内核**。它从 initrd
读进一个**包**，解开、校验、然后把包里的 payload（一个独立的用户 ELF）加载
执行；用户程序运行时还能通过 `svc` 使用内核的文件系统。

裸机跑出来的样子（`tools/a64pkgtest.sh` 的判据）：

```
MO-PKG
PK n=515          ← 解包长度，必须等于 user.elf 的文件大小
U1                ← 用户程序的输出
5050              ← sum 1..100
0                 ← create 返回的 id
8                 ← 写入字节数
8                 ← 读回字节数
5050              ← 从文件读回的值（证明 FS 往返）
1                 ← 文件数
0                 ← bss（内核加载前把用户区污染成 0xA5A5A5A5）
PF2               ← 用户直读文件内容区，被页表拦下
D
EXIT 7
V OK              ← secret 与包首字节都没被用户改动
```

模拟器诊断：`svc=14`、`eret=15`（14 次系统调用 + 1 次 abort 返回）。

## 与 a64exec 的差别

| | a64exec | a64pkg |
|---|---|---|
| initrd 里放 | 赤裸的 ELF | **包**（可打印字节串） |
| 装得进装不进 | 只看 ELF 头 | 还要过校验和 |
| 用户能用的东西 | 打印、退出 | 打印、退出、**文件系统** |

包是一串可打印字节：

```
MOPK1|app|1|515|7f454c46...|<fnv>
 └─┬─┘ └┬┘ │ │   └──┬──┘   └─┬──┘
  magic name ver len  hex     sum
```

任何能传文本的渠道都能送它进来（剪贴板、串口、HTTP body）。**运行时不依赖
外部工具链**——给它这串字节，它就能自己装上并跑起来。

校验和是 **FNV-1a(32)**（offset basis `0x811C9DC5`、prime `0x01000193`），
由测试脚本用 Python **独立**实现：内核能跑通本身就证明它的 FNV 与公开算法
一致，判据不照抄内核输出。

## 为什么用户程序必须只能用 svc 碰文件

文件的**内容**放在内核私有块（`0x40430000`，AP=00），用户只能通过
`svc 200..204` 读写；直接读那个地址会被页表拦下，内核打印 `PF2`。

这是"文件由内核保管"与"用户自己有块内存"的分界。它是**可验证**的：
变异 M4 把内核私有块的 AP 从 `00` 改成 `01`，`PF2` 立刻消失。

## 八个错误码为什么必须分开

`-1 magic` · `-2 段数≠6` · `-3 hex 长度不符` · `-4 非法 hex` ·
`-5 校验和不符` · `-6 超出容量`（外加 ELF 加载的 `E-1..E-8`）

统一返回 `-1` 的话，调用方分不清"包被截断"和"包被改过"——前者该重传，
后者该拒收并报警。顺序也刻意是 **容量 → 长度 → 内容**：反过来会把超大包
误报成被截断。

## 判据分八层

| 层 | 判据 | 抓的是 |
|---|---|---|
| ① | 汇编 + 链接产出两个 ELF | 根本没产出 |
| ② | 用户 ELF 不在内核镜像里（字符串 + 首条指令） | 其实链接进了内核，装包是演的 |
| ③ | 头部字段独立用 python 读 | 链接器 `--base` 没生效 |
| ④ | 端到端逐行输出，`PK n=` 等于文件长度 | 解包长度错 / 加载了但跑错 |
| ⑤ | 模拟器计数 `svc=14` `eret=15` | 走了别的路径、碰巧也对 |
| ⑥ | 六个负例给出**六个不同**的码 | 校验被跳过 / 统一返回 -1 |
| ⑦ | 改 payload 内容并**同步改 sum** → 输出随之变 | 其实没从包里读 |
| ⑧ | 不给 initrd 必须报 `BAD 1` | 内核自己内嵌了一份用户程序 |

⑦是关键：只改 payload 不改 sum 会被 -5 拦下，测不出"有没有真的从包里取
代码"；只有把 sum 也算对、程序照跑、但输出从 `U1` 变成 `V1`，才证明内核
执行的确实是包里那段字节。

## 过程中挖出来的坑

**一、svc 参数读错了栈槽。** 用户用 `x0=id, x1=buf, x2=n`，内核却从
`[sp,#8]/[sp,#16]/[sp,#24]` 读（那是 `x1/x2/x3`）。症状是打印出 10 位大数
——其实是 `-14`（地址不在用户区）和 `-1`（id 越界）被 `printdec` 按
**无符号**打了出来。看起来像"返回了垃圾"，其实是参数错位。

**二、`-3` 和 `-4` 曾不可区分。** `hexdec` 遇到非法字符返回 `-1`，调用处
却拿它和 `len` 比、判成"长度不符"。于是"非法 hex"永远报 `-3`，`-4` 是死
代码。补了 `cmp x0, #0; b.lt up_hex` 才分开。

**三、payload 容量上限 512 太小。** 用户程序多写 7 条指令就到 515 字节，
于是直接 `BAD 6`——症状看起来像"包坏了"，实际是上限太紧。payload 区到
文件区之间有 64KB，上调到 1024。

**四、M4 变异第一版设计错了。** 想把文件区挪到用户区来验证隔离，但用户
程序硬编码读 `0x40430000`：挪走之后它读的**仍是**内核私有块，`PF2` 照样
出现，判据根本没变。能验证"内容区真的隔离"的，只有让内核私有块不再私有
（改 AP）。**改了代码 ≠ 改到了那条因果链。**

**五、M2 变异第一版也没改到。** `-3` 由**两道**检查共同保证：先比 hex 段
长度是否 `2*len`，再比 `hexdec` 解出的字节数是否等于 `len`。只改一道，
另一道仍把 hlen 负例拦成 `-3`。必须两道一起失效才抓得到。

## 变异验证 8/8 被捕获（`tools/a64pkgmut.sh`）

| | 变异 | 探针 |
|---|---|---|
| M1 | 不比校验和 | `BAD 5` 消失 |
| M2 | 两道长度检查都失效 | `BAD 3` 消失 |
| M3 | 非法 hex 不报错 | `BAD 4` 消失 |
| M4 | 内核私有块不再私有 | `PF2` 消失 |
| M5 | create 不递增计数 | 文件数不再是 1 |
| M6 | write 不记录长度 | 第二个 5050 变 0 |
| M7 | 容量检查放宽 | `BAD 6` 消失 |
| M8 | 不清零 bss | `0` 的个数从 2 变 1 |

其中 M5、M6、M7、M8 各只有一条断言盯着，冗余度偏薄，如实记录。

## 已知限制

- **文件没有持久化**：掉电即失。真正的持久存储要接块设备（v1.164 的
  virtio-blk 是在 cfs 后端做的，这一版没有）。
- 8 个文件槽、每槽 256 字节、名字 ≤7 字节。
- payload 上限 1024 字节；包格式字段数固定为 6。
- **校验和不是签名**：FNV-1a 是对称的，能验就能算，证明不了来源可信。
- 只有 5 个文件相关的 `svc`，没有目录、没有权限、没有打开/关闭语义。
- 内核代码区在 EL0 视图下也可执行（模拟器用页级 `mem_protect` 模拟 MMU，
  不区分异常级），真硬件没有这个限制。
- 只在 CPU 模拟器里跑过，未经真实硬件。
