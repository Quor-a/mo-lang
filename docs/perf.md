# 代码体积优化

## 度量先行

`tools/codesize.py`（`make codesize`）统计代码段体积与各冗余模式占比。

**为什么单做这个工具**：一开始我凭直觉列了 6 个 peephole 模式，
实测下来只占 **0.09%** —— 拍脑袋的"优化"全是寂寞。真正的大头是
统计出来的：**2649 个调用点**，每个 12 字节。

> 没有度量就没有优化。每一点改动都要能说出"省了多少字节"。

## 已做：调用点 12 → 5 字节（-14.81%）

原来每个调用点发 `movabs rax, imm64; call rax`（12 字节），
因为发射时目标地址可能还不知道，得留 8 字节空位回填。

改成：被调函数**已定义**时直接发 `call rel32`（5 字节）。

**为什么"已定义"就够了**：代码是**线性发射、从不重排**的 —— 函数
地址在 `parse_func` 里确定（`4194304+176+K_CLEN`），之后不再移动。
所以向后调用的目标地址此刻就是最终地址。

| | 优化前 | 优化后 |
|---|---|---|
| 代码段 | 110592 | **94208**（-14.81%） |
| 走 rel32 的调用点 | 0 | 2564 / 2649（97%） |
| 仍走回填（前向调用） | 2649 | 85 |

剩余空间只有 0.63% —— 这项已接近极限。

### 🔴 顺序是关键（两个坑，症状都极隐蔽）

**坑 1：`spill_cache()` 可能发射 1 字节 `push rbx`。**

第一版在 spill **之前**就算好了 `here` —— 位置差 1，**所有 rel32 全错**。
症状：简单程序不触发 spill（`K_CRBX==0`）所以全对，只有编译
`compiler.mo` 这种大文件时才段错误，而报错点离调用点很远。

**坑 2（seed 汇编里）：`rax`/`r8`-`r11` 都是 caller-saved。**

`call emit1` 之后就被破坏。第一版拿 `r9`/`r10`/`r11` 跨 call 保存
`ta` 和 `rel`，生成的代码跳到垃圾地址 —— **seed 自己段错误**。
所以 `ta` 用栈保存，`rel` 在最后一次 call 之前才算好。

## 🔴 为什么 IR 是"自举以来最难"：双实现同步

这个优化**必须改两处**：`src/mo/compiler_part2.mo`（moc）和
`src/asm/base.s`（seed，手写汇编）。

只改 moc 的后果：seed 产 115003 字节、moc 产 98619 字节
—— **自举直接不一致**。

seed 是独立实现（手写汇编），只实现了编译 compiler.mo 所需的语法
子集。**任何改变编译期副作用的改动，两边都要做一遍**，这不是抽象的
"技术难"，而是自举编译器的固有成本。这也是 IR 被列为最大改动的
真实原因：IR 要在两个实现里各写一套。

## 试过并放弃：前向调用也走 rel32（+0.63%）

思路：前向调用的地址此刻未知，但 **rel32 的偏移与"地址是否已知"无关** ——
回填时函数地址一定都有了，照样算得出。所以两条路都能用 5 字节
（emit1(0xe8) + emit4(0)），省下的 7 字节是白拿的。区分方式：回填时读
占位处**首字节**（0xe8 = rel32 写 4 字节，0x48 = movabs 写 8 字节），
patch 类型就写在它自己身上，不需要额外 kind 表。

**结果：已回滚。** moc 侧改完、seed 侧（base.s 慢路径 + main.s
resolve_all）同步改完后，seed 产物失效 —— 自举时 moc1 段错误。

虽然收益确实存在（实测代码段 94208 → 90112，约 -4KB），但
**0.63% 不值得让两个实现再冒一次不一致的风险**。

> 记在这里避免以后重复尝试：**同一处改动两边都要对，成本是双倍的。**
> IR 被列为最大改动，真实原因也在这里 —— 真 IR 要在 seed（手写汇编）
> 和 moc（墨语言）里各写一套。

## 下一步

剩下的体积空间（~15%）要靠真 IR：

| 项 | 预估 | 依赖 |
|---|---|---|
| 前向调用也走 rel32 | +0.63% | 无需 IR |
| 寄存器分配（不止 rbx 一个槽） | 大 | **需要 IR** |
| 指令选择（如 push imm 折叠） | 中 | 部分已做 |
| 消除 `push rbx/pop rbx` | 0.10% | 需要基本块分析 |

## 体积构成实测：`make codecompose` / `tools/codecompose.py`

```
代码段 132620 字节 / 42528 条指令
指令        字节     占比    条数   均长
mov        40601   30.6%  11892  3.41
call       19158   14.4%   3906  4.90
push       16824   12.7%   7228  2.33
movabs     12922    9.7%   1846  7.00
pop         8285    6.2%   8075  1.03
cmp         8209    6.2%   2204  3.72
je          6636    5.0%   1106  6.00
```

### 🔴 一个反直觉的结论：寄存器分配会**增大**体积

原本的预期是"寄存器分配能把 push/pop 换成寄存器传送，省下 30%"。
实测数据不支持这个预期：

```
push+pop 合计 25109 字节（18.9%），**均长 1.64 字节**
```

`pop rcx` 只要 1 字节、`push rax` 只要 1 字节，而换成寄存器传送
（`mov rcx, rbx`）需要 **3 字节**。

也就是说：**在这个架构下，栈传递比寄存器传递更省空间。**
寄存器分配带来的是**性能**收益，代价是体积变大 ——
方向恰好与"压缩 30%"相反。

这条结论改变了"真 IR + 寄存器分配"的价值主张：
它不是体积优化，而是纯性能优化。而本项目目前**没有性能基线**
（没有 benchmark 跑分），所以收益无法量化验证。

### 体积的真正大头是 mov（30.6%）与 movabs（9.7%）

- **movabs** 1846 条，10 字节/条，用于加载全局地址与函数地址。
  改成 RIP-relative `lea rax, [rip+d]`（7 字节）可省约 5500 字节 ≈ 4%。
  发射时地址与代码位置都已知，距离约 251MB < 2GB，disp32 够用 —— 可行。
  但需区分"加载地址"与"加载大整数常量"，后者不能改。
- **je** 1106 条，6 字节/条。若能用短跳（2 字节）可省约 4400 字节 ≈ 3.3%。
  但线性发射架构下，发射时标签位置未知，**回填时改长度会移动全部代码**，
  因此不可行 —— 除非改成多遍发射。

### 为什么 peephole 只剩 0.12%

`make codesize` 报告的可省空间只剩 164 字节。因为短编码的
push/pop 本身就是紧凑表示，没有冗余可榨。剩下的都是"换编码就
要移动代码"或"要区分语义"的硬骨头。

### 结论

| 方向 | 预期 | 实测 |
|---|---|---|
| 寄存器分配省体积 | 30% | **负值**（均长 1.64 → 3） |
| peephole 省体积 | — | 已榨干（0.12%） |
| movabs→lea | — | ~4%（可行，需 seed 同步） |
| 长跳→短跳 | — | 不可行（需多遍发射） |

**"真 IR"的收益应重新定位为性能，而不是体积。** 若要做，
必须先建立性能基线（benchmark + 计时），否则无从判断改善与否。

## 性能基线：`make bench` / `tools/benchtest.sh`

```
=== 性能基线（5 次，去掉极值取均值）===
  arith    11981784 ns  (11 ms)
  call      7420865 ns  (7 ms)
  recur      390570 ns  (0 ms)
  array     5493422 ns  (5 ms)
  local     7185249 ns  (7 ms)
```

`examples/bench.mo` 刻意以**表达式计算**为主（push/pop 密集），
因为那正是寄存器分配会影响的部分。`tools/benchtest.sh` 跑多次取
去极值均值，与 `docs/perf_baseline.txt` 对比，超出 ±25% 即失败。

### 🔴 微基准：栈传递 vs 寄存器传递 —— **没有差异**

`tools/passcost.sh`（两亿次迭代）：

```
push/pop  传递: 109492793 ns
寄存器    传递: 108684348 ns
差异: +0%
```

两个版本**指令条数相同**，只换传递方式。差异在噪声内（<1%）。

原因：现代 x86 有**栈引擎**（stack engine），专门消除 push/pop 的
rsp 依赖链；栈顶内容几乎总在 L1 缓存里。所以 push/pop 并不比 mov 慢。

> 这条修正了一个常见直觉："寄存器分配能提速"。实测表明，
> 提速的来源是**少发指令**，不是"用寄存器代替栈"。

### 与 gcc 的对比

| workload | 墨语言 | gcc -O0 | 倍数 |
|---|---|---|---|
| arith  | 11.98 ms | 4.07 ms | 2.9× |
| call   | 7.42 ms  | 2.68 ms | 2.8× |
| local  | 7.19 ms  | 3.31 ms | 2.2× |
| array  | 5.49 ms  | 2.62 ms | 2.1× |

拆解发现：**除法和取模占了 arith 的 63%**

```
full(含除法取模)  11743471 ns
nodiv(纯乘加)      4289734 ns
```

墨语言循环体 56 条指令（含 2 次 idiv），gcc -O0 约 25 条。
差距来自**指令条数**，不是传递方式。

### 综合结论：寄存器分配的收益需要重新评估

| 维度 | 预期 | 实测 |
|---|---|---|
| 体积 | 省 30% | **增大**（均长 1.64 → 3 字节） |
| 性能（换传递方式） | 提速 | **无差异**（<1%） |
| 性能（少发指令） | — | 有效，但取决于能消除多少 spill |

所以"真 IR + 寄存器分配"的真实收益是**减少指令条数**，
代价是体积增大。它不再是那个"🔴 最大改动、收益最大"的选项。

相比之下，**除以常量 → 乘法倒数**（strength reduction）可能是
性价比更高的优化：arith 里除法占 63%，而这是编译期常量即可
判定的纯代码生成改动，不涉及 IR。

## 强度削减：除以 2 的幂用移位代替 idiv（1.65.0）

实测收益（同一份 `examples/bench.mo`）：

```
arith   11981784 ns → 6354210 ns   (-46%)
```

算术 workload 里除法和取模原本占 63%，idiv 是几十周期指令、
移位是 1 周期，所以这一项就把整体压掉近一半。

### 序列（向零截断必须与 C 一致）

```
mov rax, rcx        ; rax = n
mov rdx, rax
sar rdx, 63         ; rdx = n<0 ? -1 : 0
and rdx, 2^k-1      ; rdx = n<0 ? 2^k-1 : 0
add rax, rdx
sar rax, k          ; q = n / 2^k（向零截断）
```

取模再补：`shl rax,k` → `mov rdx,rcx` → `sub rdx,rax` → `mov rax,rdx`，
即 `n - (n/2^k)*2^k`。

### 🔴 负数偏置不能省

`sar` 是**向下取整**，C 的整数除法是**向零截断**。少了偏置，
`n = -1, k = 1` 时 `-1/2` 会得到 `-1`（正确为 0）。
这是这类优化最经典的错法，且只在负数上暴露 ——
所以测试用「与除数是变量的 idiv 路径逐值对照」覆盖 -40..40。

### 🔴 生成代码里的寄存器 ≠ 编译器自己的寄存器（seed 侧踩到）

seed 第一版担心 `emit1/emit4`（**宿主**函数）会破坏 rcx，
于是把 n 转存到 r14 再发 `mov rdx, r14`。结果：

```
seed 发 4C 89 F2（mov rdx, r14）
moc  发 48 89 CA（mov rdx, rcx）
```

两边自举不一致。而 moc 是对的 —— **生成代码里的 rcx 全程没被
生成代码改过**。宿主函数破坏什么寄存器，与生成代码无关。
这与 1.31 那条「生成代码里的地址必须是被生成程序的地址空间」
是同一类错。

### 覆盖范围

`/` 与 `%` 右侧是编译期常量 2^k（1 ≤ k ≤ 31）。
k > 31 时 `and` 的 imm32 会符号扩展、无法编码 2^k-1，退回 idiv。
非 2 的幂（如 `%7`）仍走 idiv —— 要覆盖它们需要「乘法倒数」，
那要在编译期算 128 位魔数，seed（手写汇编）侧实现代价过大。

## 任意常量除数的魔数（1.66.0）

覆盖 `/` 与 `%` 右侧为任意常量 d（2 ≤ |d| ≤ 2^31-1，非 2 的幂）。

```
q = mulhi(M, n)                 ; 128 位乘法取高 64 位
if M < 0 { q += n }             ; 仅当 d > 0 且 M < 0
q = q >> s                      ; 算术右移
q = q - (n >> 63)               ; n < 0 时等价于 +1：floor → 向零截断
```

用 gcc -O2 交叉验证过序列与常数：`d=7` 得 M=5270498306774157605、s=1，
`d=100`（M<0）确认为 `mulhi → +n → >>s → -(n>>63)` 的顺序。
取模再补 `n - q*|d|`。

### 收益（交替测量，压住噪声）

```
魔数 5611695 ns   idiv 11252020 ns      → 快约 45%
```

`tools/divcost.sh` 在**同一次运行内交替**测两个版本。
必须这样做：`make benchtest` 里同一个 arith workload 实测在
**6.5ms ~ 10.1ms** 之间波动（±50%），分开跑根本比不出差异。
这本身就是一条方法论：**噪声大于效应时，任何单次测量都没有意义**。

### 🔴 两个真 bug

**一：`r2` 初值写错，M 差整整一倍。**
`r2` 必须是 `2^63 mod ad`，第一版写成 `rb`（= `(2^63-1) mod ad`，少 1），
于是 `delta` 偏大、多迭代一次：`d=7` 算出 M=10540996613548315209/s=2，
而正确值是 M=5270498306774157605/s=1。
是拿 gcc 的常数逐位比对才定位到的 —— 只看"结果错"会以为是最后一步的方向问题。

**二：seed 侧把全局放进 `.text` 段。**
`MG_M`/`MG_S`/`pow2d` 追加在 base.s 末尾，落进了**代码段**，
而代码段不可写 → seed 一运行就段错误。移到 `.data` 段即恢复。
（这也是"确认修改生效"的老教训重演：中途 `cp` 备份把刚做的修复回滚了，
多查了一轮。）

### 已知限制

- 只覆盖 2 ≤ |d| ≤ 2^31-1；更大的除数退回 idiv
- 复合赋值（`x /= 7`）未走魔数，仍用 idiv
- 魔数路径比 idiv 长约 20 字节/处，是**以体积换性能**

## 复合赋值 `/=` `%=`（1.67.0）

`x /= 7`、`x %= 100` 此前一律走 idiv，现在与二元运算一样做强度削减：
2 的幂走 `g_div_pow2`，任意常量走 `g_div_magic`。

### 🔴 seed 侧不用改，但这**不是**好消息

seed 只实现编译 compiler.mo 所需的语法子集，**完全不支持复合赋值**
（compiler.mo 自身也不用）。所以：

- 自举三级一致 ✅ —— 但**这项优化根本不在自举验证范围内**
- 只能靠 `tests/98` 穷举兜底：复合赋值、二元魔数、变量除数 idiv
  **三条路径逐值对照**（−1500..1500 × 12 个除数 × 除/取模）

这正好是「自举只能证明被测到的路径一致」的另一面：**未覆盖的路径要靠
别的验证手段补上**，不能因为 `make boot` 通过就认为没问题。

### 另一个发现：墨语言没有 C 风格 for 循环

`for` 关键字只用于 `impl Interface for Type`（`parse_for` 实际解析的是
impl 块）。全仓库没有任何 C 风格 for 循环用例。`g_compound` 的 4 个调用点
中有一个因此无法从用户代码单独区分，记为本轮未覆盖。
