记录这一轮遇到的两类问题：**环境故障**与**一个真实的编译器诊断 bug**。
分开写，因为它们的性质完全不同——前者不是项目的错，后者是。

## 一、环境故障：沙盒 502 与我的错误处理

### 现象

连续多次工具调用返回 `50201 sandbox call failed`（HTTP 502），
同一条命令反复失败，看起来像"一直在同一个地方出错"。

### 我犯的错误

遇到失败就**原样重试同一条命令**。502 是服务端不可用，重试同一条
命令不会让它变好，只会让同一个错误重复出现。

正确做法应该是：换路径、缩短命令分步执行、或先确认环境是否恢复。
盲目重试既浪费轮次，也误导观察者（让人以为代码有问题）。

### 教训

> 区分"命令错了"和"环境坏了"。前者的报错稳定且可复现于具体内容，
> 后者的报错与命令内容无关。判断错了就会原地打转。

## 二、真 bug：缺少 import 时报「undefined symbol ''」（误导性诊断）

### 复现

```mo
fn main() -> i64 {
    print("hello");      # 没有 import "io.mo"
    return 0;
}
```

报错：

```
t.mo:2:18: error: undefined symbol ''
        print("hello");
                     ^
```

加上 `import "io.mo";` 后正常编译运行。

### 为什么这是个 bug

报错有**三处误导**，每一处都把人往错误的方向带：

1. **符号名为空**（`''`）—— 真正未定义的明明是 `print`，却显示空字符串
2. **位置指向行尾**（列 18，是 `;` 的位置）—— 不是 `print` 所在的位置
3. **没提 import** —— 真正的原因是缺 import，错误信息里一个字没提

三者叠加的实际效果是：看到这个报错，没有人会想到"我忘了 import"。

### 排查过程（走了弯路，如实记录）

1. 怀疑 `print` 这个内建函数坏了 → 但 `print_i64` 同样报错，排除单个函数
2. 怀疑 8 个参数超限 → 查过，第 7 个参数起的 bug 早已修复，且本例只有 1 个参数
3. 怀疑字符串转义有问题 → 用 `od -c` 确认源文件字节完全正常，排除
4. 怀疑 `bin/moc` 是坏产物 → 跑 `make boot` 重建，三级自举一致，但问题依旧
5. **加 `import "io.mo"` 后正常** → 才定位到真正原因

第 4 步是明显的浪费：自举一致只说明"编译器能稳定编译自己"，
与"这个源文件为什么报错"无关。当时是病急乱投医。

### 影响范围

**所有内建函数**都会这样（已验证 `print` 与 `print_i64`）。
凡是忘了 import 标准库的情况，都会收到这条空符号名的报错。

### 建议的修法（尚未实施）

在符号查找失败时，若该名字是**已知内建函数**，应给出针对性提示：

```
t.mo:2:5: error: 'print' is a builtin — add: import "io.mo";
```

关键是**指出这是内建函数、并给出 import 建议**，而不是报一个空符号名。

### 尚未实施的原因

这一轮的目标是 CNN，中途被环境故障打断，编译器诊断部分还没动。
已记录在此，避免遗忘。

## 四、新发现的两个编译器 bug（本轮二分出来的）

排查 CNN 段错误时，用二分法挖出两个**此前从未暴露**的编译器缺陷。
它们都很严重，因为都是**静默的**：不报错，直接挂死或给出错的值。

### bug A：参数列表跨行 → 编译器死循环  ✅ **已修复**

```mo
fn g(a: i64, b: i64,
     c: i64) -> i64 { return a + b + c; }
```

`moc` 会**无限循环**，不输出任何错误，一直挂到被 timeout 杀掉
（退出码 124）。

已确认的边界：

| 写法 | 结果 |
|---|---|
| 参数列表中间换行 | 死循环 |
| `fn g(\n) -> i64` 空参数 + 换行 | 死循环 |
| `fn g(a: i64, b: i64\n)` 换行在 `)` 前 | 死循环 |
| 表达式 / 赋值里换行 | **正常** |

即：**只有函数参数列表内的换行会触发**，其它位置换行没问题。

词法层 `skip_ws()` 确实跳过换行（不是 token），所以问题在
`parse_func` 的参数循环，而不是分词。精确定位尚未完成。

### bug B：超过 6 个参数 → 参数整体错位  ✅ **已明确报错（不再静默）**

```mo
fn h(x: i64) -> i64 { return x * 2; }
fn f(a,b,c,d,e,g,hh,i: i64) -> i64 { return h(a) + hh + i; }
# f(1,2,3,4,5,6,7,8) 应得 2+7+8 = 17
```

**实测返回 9。**

单独测 8 参数只做加法（`a+b+...+i`）是**正确**的（得 36），
所以触发条件是「参数 >6」**且**「函数体内调用了别的函数」。

指向栈顶缓存的 spill 时机：第 7 个起的参数走栈，而函数内调用时的
spill 把栈帧内容冲掉了。这与 CHANGELOG 里记过的"跨函数调用会泄漏
——被调函数会把调用者缓存的值压进自己的栈帧"是同源问题。

### 绕过方式

把 `cnn_set_conv` 的卷积核固定为 3×3，参数从 8 个压到 6 个；
同时确保参数列表不换行。两个限制叠加，才有了那个看起来很长的签名。

### 为什么这两个 bug 一直没暴露

- 墨语言自己的编译器源码（`src/mo/*.mo`）从来没写过 >6 参数且在函数
  体内调用其它函数的函数
- 也从来没把参数列表换行写
- 所以自举三级一致**完全测不到**它们

> 自举只能证明"被测到的路径一致"，覆盖不到的地方照样有 bug。
> 这条在之前的寄存器分配文档里写过一次，这里再次印证。

## 五、两个 bug 的后续处理（本轮完成）

### bug A 已修复：根因在 predeclare()

用探针二分定位（`PROBE-MAIN` → `PROBE-PARSEPROGRAM` → `PROBE-PARSEFUNC`），
发现 **PROBE-PARSEFUNC 从不打印** —— 死循环发生在 `parse_func` 之前。

根因在 `predeclare()`（预扫描登记顶层 fn 名）数形参个数的循环：

```mo
while sbyte(j) != 41 {                  # 扫到 ')'
    if sbyte(j) == 10 { j = j - 1; }    # ← 遇换行"回退"
    ...
    j = j + 1;                          # ← 末尾又前进
}
```

`j-1` 再 `+1` = 原地不动。本意应是"遇到换行就停"，但写成了回退。
参数列表只要跨行，这里就无限循环 —— 且**没有任何输出**（连报错都没有），
表现为 moc 挂死，必须靠 timeout 才能发现。

修法：换行当作普通分隔跳过，继续扫到 `)`；并加 `j >= n` 边界保护
（文件末尾没有 `)` 时不能越界扫）。

```mo
let go: i64 = 1;
while go == 1 {
    if j >= n { go = 0; }
    else {
        if sbyte(j) == 41 { go = 0; }
        else {
            if sbyte(j) == 44 { np = np + 1; }
            else { if sbyte(j) != 10 { any = 1; } }
            j = j + 1;
        }
    }
}
```

已加正式测试 `tests/75_multiline_params.mo`（三种跨行写法：中间换行、
每个参数一行、换行在 `)` 前），全部通过。

### bug B 已明确化：参数上限 6，超限直接报错

定位到**调用约定不匹配**：`parse_call` 顺序 push 实参，再 pop 前 6 个
到寄存器。na=8 时：

| 位置 | 实际拿到 | 应该是 |
|---|---|---|
| rdi..r9 | 参数 3,4,5,6,7,8 | 参数 1..6 |
| 栈 [rbp+16] | 参数 2 | 参数 7 |
| 栈 [rbp+24] | 参数 1 | 参数 8 |

实测 `h(a)+hh+i` 得 **9** = `h(3)+1+2`，与推算完全吻合。

**只做加法的函数完全看不出来**（加法可交换，和仍是 36）——
这正是它一直没被发现的原因。

正确修法要按 System V 重新布置栈参数，改动面大、风险高。
在此之前**先明确报错**：

```
pc.mo:2:5: error: too many parameters (limit 6)
```

> 静默地算错，比明确告诉你"不支持"糟糕得多。

### 一个流程教训（本轮真实踩到）

```bash
cp ... && grep -c "PROBE" file && python3 fix.py
```

`grep -c` **没有匹配时退出码是 1**，`&&` 链就此断开，
修复脚本**从未执行**，而我一度以为已经修好（因为后面的 make 照常跑、
hash 还"恰好"没变）。

确认修改生效必须看**脚本自己的输出**或事后 grep 验证，
不能只看整条命令有没有报错。

## 六、bug B 的完整修复（参数上限 6 → 9）

### 根因确认

调用方顺序 push 实参，再 pop 前 6 个到寄存器。na=8 时：

| 位置 | 实际拿到 | 应该是 |
|---|---|---|
| rdi..r9 | arg3..arg8 | arg1..arg6 |
| 栈 | arg2, arg1 | arg7, arg8 |

实测 `h(a)+hh+i` = `h(3)+2+1` = 9，与推算完全吻合。

### 修法

- `emit_store_arg` 的栈参数偏移改为递增 `16 + (i-6)*8`
- 调用方先把 argNa..arg7 pop 到 **rax/r10/r11** 暂存，
  再照常 pop 6 个到 r9..rdi，最后"先 pop 者先 push"压回栈
- 调用方 `add rsp` 清理栈参数

### 上限为什么是 9

暂存只能用三个空闲寄存器。试过用内存：

```
ops2(0x49, 0xbb); emit8(heap + O_TARG);   → 运行即段错误
```

**生成的代码跑在用户程序的地址空间，不能访问编译器自己的堆。**
要支持更多参数，得在数据段分配临时槽并回填地址（类似
`emit_call_patch` 的机制），改动更大，暂未做。

### 教训

> 生成代码里出现的地址，必须是**被生成程序**的地址，不是编译器自己的。
> 这个区别在写发射代码时极易混淆，因为它俩在源码里都是"某个数"。

## 七、尝试「参数上限 9 → 32」失败（已回退，未解决）

### 想做的事

用**数据段临时槽**替代寄存器暂存，彻底解除参数上限。

- 数据段头预留 32 个 i64 作暂存区（`reserve_arg_slots()`）
- `arg_spill`：pop 出 argNa..arg7 → 存到数据段 `[ARG_OFF + j*8]`
- `arg_restack`：从数据段读回并按序 push
- `ARG_OFF = 0x10000000 + 16`（**被生成程序**的数据段地址，合法）

### 结果：自举不一致

```
Stage1 (seed 编译): ...  数据段 3586 字节
Stage2 (moc  编译): ...  数据段 3842 字节
差 256 = 32 × 8
```

**seed 编译 compiler.mo 少写 256 字节，moc 编译则不少。**

### 定位过程（排除了三个假设）

| 假设 | 验证方式 | 结论 |
|---|---|---|
| 全局 var 非 0 初值在 seed 下不对 | 最小用例 `var N: i64 = 32` + while | ❌ 两者都得 32 |
| 暂存区 dquad 数量导致 | 把 32 改成 0 | ❌ 仍不一致 |
| main 函数体过长 | 抽成独立函数 `reserve_arg_slots()` | ❌ 仍不一致 |

三个都不是。**真正原因未定位。**

### 已回退

恢复到已验证的 9 参数寄存器方案（自举一致、118 测试全过）。

**已确认可用的结论**（这部分有价值）：

> 生成代码里的地址必须是**被生成程序**的地址空间。
> 曾用 `emit8(heap + O_TARG)` 存到编译器自己的堆 → 运行即段错误。
> 改用数据段 `0x10000000 + 16` 后不再段错误（说明地址本身是对的），
> 卡在自举一致性上。

### 下一步若要继续

建议先做这个诊断：把新增的 `arg_spill` / `arg_restack` **逐个**
加回去（每次只加一个），定位到底哪个函数让 seed 与 moc 分道扬镳。
怀疑方向是函数数量触及某张表的边界，或 while 循环内声明局部变量。

## 八、🔴 重大发现：seed 与 moc 不等价（比参数上限重要得多）

在尝试「参数上限 9 → 32」时，撞到一个**更根本的问题**。

### 现象

**在 compiler.mo 里增加任何 `dquad(0)` 调用（增大数据段），自举就立即不一致。**

```
seed 编译 compiler.mo → m1   数据段 3539 字节
m1   编译 compiler.mo → m2   数据段 3571 字节
差 32 字节 = 4 个 dquad(0)
```

首个不同的偏移是 42：m2 那里是我新加的 4 个 0，m1 那边是别的数据。
即 **m1（moc）正确写入了，seed 漏掉了**。

### 二分排除（全部证伪）

| 假设 | 验证 | 结论 |
|---|---|---|
| 全局 var 初值在 seed 下不对 | 最小用例 `var N: i64 = 32` | ❌ 两者都对 |
| 暂存区数量导致 | 32 → 16 → 8 → 4 → 0 | ❌ 4 个就不一致，0 个才一致 |
| `while` 循环内的 dquad 有问题 | 展开成 34 行顺序调用 | ❌ 仍不一致 |
| `main` 函数体过长 | 抽成独立函数 `reserve_arg_slots()` | ❌ 仍不一致 |
| 只在 `main` 里有问题 | 移到 `parse_program()` 开头 | ❌ 仍不一致 |
| 新函数本身有问题 | 定义了但不调用 | ✅ 一致 |

**唯一成立的事实**：只要**实际执行**了新增的 `dquad` 调用（无论在哪、
无论用不用循环），seed 编出的产物就会少写那些字节。

### 这意味着什么

**seed 与 moc 不是等价的两个实现**，它们存在一个具体的分歧点。

之前我们一直说"自举三级一致"——它只能证明**当前 compiler.mo 这条
路径上**两者一致。一旦源码触碰某个未覆盖的模式，分歧立刻暴露。

> 自举只能证明被测到的路径一致。这句在寄存器分配文档里写过一次，
> 在两个编译器 bug（跨行死循环、多参数错位）上印证过一次，
> **这是第三次，而且是最根本的一次** —— 它说明 seed 本身有缺陷。

### 为什么这件事重要

.seed 是手写汇编的引导编译器，是整条自举链的**信任根**。它若有缺陷，
那么"编译器能编译自己"这个证明的可信度就打了折扣——因为我们验证的
是"seed 与 moc 在当前源码上吻合"，而不是"seed 是正确的"。

### 现状

已回退到已验证的 9 参数方案（自举一致，118 测试全过）。

**参数上限仍是 9。32 参数方案未实现。**

### 若要继续

建议的诊断顺序：

1. 确认 `dquad` 在 **seed 汇编源码**（`src/asm/*.s`）里的实现，
   与 compiler.mo 里的 `dquad()` 逐条比对
2. 检查 seed 是否有语句数 / 数据段大小的固定上限
3. 写一个最小复现：一个只有几行的小程序，包含一个写数据段的循环，
   分别用 seed 和 moc 编译并比对数据段大小
