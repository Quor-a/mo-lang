# 任意精度整数：对标 Python 的计算能力

版本 1.14.0（2026-10-09）

## 为什么做

Python 最标志性的计算能力是 **int 不溢出**。墨语言只有 i64，
算 `2 ** 1000` 会静默回绕——这正是本项目一贯要消灭的
"安静地给出错的结果"。

## 对标关系

| Python | 墨语言 |
|---|---|
| `a ** n` | `big_pow(a, n)` |
| `pow(a, n, m)` | `big_modpow(a, n, m)` |
| `pow(a, n, m)`（大指数） | `big_modpow_big(a, e, m)` |
| `math.gcd(a, b)` | `big_gcd(a, b)` |
| `math.factorial(n)` | `big_fact(n)` |
| `math.isqrt(n)` | `big_isqrt(n)` |
| `a // b` / `a % b` | `big_div(a, b)` / `big_mod(a, b)` |
| `random.randint` | `rand_range` / `rand_between` |

## 实现要点

### 表示

句柄 → 堆上：`[0]=len, [1]=neg, [2+i]=limb i`
每 limb 存 **4 位十进制**（基数 10^4）。

**为什么不是 2^32**：
- `limb*limb + carry` 最大约 10^8，在 i64 内绝对安全，不需要 128 位
- 打印/解析十进制不用做除法，4 位一段直接拼

代价是空间与速度，换来"不会静默算错"，这个交换是值的。

### 乘法的关键：及时进位归约

朴素写法会把所有乘积累加到一个 i64 里，limb 数一多就溢出。
做法是**每次累加后立即把值压回 [0, RADIX)**，
于是累加器里永远只有 `limb*limb + 小量`（< 10^8）。

### 除法：二分试商

基数 10^4 → 试商范围 [0, 9999]，14 次比较定位一位。
比 Knuth D 慢，但好写、好验、不会错。

### 取整方向采用 Python 语义

不是 C 的截断：

```mo
big_div(-7, 3)   # -3（C 会给 -2）
big_mod(-7, 3)   #  2（C 会给 -1）
```

异号且余数非零时：`q = -(q0+1)`，`r = 除数符号 × (|b| - r0)`。

### isqrt：牛顿迭代 + 收敛后修正

只靠迭代会在边界差一。最后两段循环把结果夹到
`x² ≤ n < (x+1)²`。测试专门覆盖了"完全平方数"与"完全平方数减一"
这两个最容易差一的点。

## 验证方式：拿 Python 当标准答案

`tools/bignumtest.sh` 用 Python 生成期望输出，与墨语言**逐字节 diff**。

理由很直接：任意精度算术最容易"看起来对"——
打印出一长串数字，人眼根本看不出第 200 位错没错。
逐字节 diff 能抓出任何一位的偏差。

实测 16 行输出全部一致，包括：
- `2^1000` 位数 302、数字和 **1366**（Project Euler 16 的答案）
- `100!` 158 位
- `fib(500)` 105 位
- `pow(2, 1000, 1009)` = 942

## 踩到的真 bug：句柄与整数同类型

`big_modpow(a, n, m)` 的指数是 **i64**。
调用方传了 `big_from_i64(1000)`——一个大数**句柄**（堆地址）。

两者在类型系统里都是 i64，编译器分不清，
于是静默算成了 `2^那个地址 mod 1009`，输出 634 而不是 942。

这是本项目的真实局限：**没有用户自定义类型的类型区分**，
大数句柄和整数都是 i64，写错了编译器不会说话。

对策：
- 命名区分（`big_modpow` 收 i64，`big_modpow_big` 收大数）
- 文档与注释明确标注
- 靠"与 Python 逐字节比对"来兜底——这次就是这个测试抓到的

## 已知限制（诚实列出）

- **浮点**：语言没有浮点类型。`sin` / `log` / `sqrt(小数)` 不做。
  需要小数的场景用 `lib/matrix.mo` 与 `lib/stat.mo` 的定点（SCALE=1000）
- **素数测试是费马测试**，不是 Miller-Rabin，会被卡迈克尔数骗过（最小 561）
- **除法较慢**：二分试商 14 次比较/位，`big_modpow_big` 因此明显慢于 i64 版本
- **分配器只增不减**：bump 分配，大规模运算会持续推高 brk
- 单个大数上限 1024 limb（4096 位十进制）
